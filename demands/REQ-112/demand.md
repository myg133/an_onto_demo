# 需求：REQ-112 · 审核界面接入 AI 建议

## 基本信息

| 项 | 值 |
| --- | --- |
| 需求编号 | REQ-112 |
| 优先级 | **P1** |
| 状态 | 进行中 |
| 代码基线 | `develop` `4178a4e`（REQ-111 已合并） |
| 前置 | REQ-108（置信度）、REQ-109（AI 语义分）、REQ-111（审核界面） |

## 需求描述

### 现状：审核界面有了，但「该不该签」还得人自己判

REQ-111 的界面能签、能看置信度分数，但**没有「建议」**：

```
[4] 活动 · 分数 1.00 · 高 · 采样 5/5 · AI fit 1.00
    → 人自己判断：接受还是拒绝？
```

而置信度里已经隐含了判断依据（分数、档位、采样命中、AI 语义分、veto）。**这些信号已经在了，只是没被翻译成一句话。**

### 目标

每个条目给一句**可解释的建议**：

```
[4]  活动          建议：接受      依据：采样 5/5 全命中 + AI fit 1.00
[97] 用量明细→授权  建议：拒绝      依据：采样 0/5 全不命中（硬反驳）
[88] 客户返点→客户  建议：人工      依据：采样 5/5 支持，但 AI 判定 0.00 —— 证据与语义冲突
[12] 后台角色       建议：无        依据：规则抽取，无置信度
```

## 核心设计判断

### 1 · 建议**不新增任何模型调用**

v1 的建议**完全由已有 `confidence` 确定性推导**（分数 / 档位 / 采样 / veto / `semantic_fit`）。

| 理由 | 说明 |
| --- | --- |
| 成本 | 审核 135 条目，若每条问一次模型 ≈ 十几万 token，且每审一次就重算 |
| 幂等 | 确定性推导 ⇒ 同一份提案两次打开，建议**逐字相同** |
| 可解释 | 每条建议必须能指向具体信号（见 §2 的规则表） |

⇒ 这也是为什么 v1 **不**给「无置信度」的实体条目编建议（83 个实体）：编了就是**凭空造判断**。

### 2 · 建议规则（确定性，落成纯函数）

| 条件 | 建议 | 依据文案 |
| --- | --- | --- |
| 有 veto `zero_hit` / `type_incompatible` | **拒绝** | 「采样 0/N 全不命中（硬反驳）」等 |
| `band = high` 且 `semantic_fit ≥ 0.8` | **接受** | 「采样 M/N + AI fit X」 |
| `band = high` 且 `semantic_fit < 0.5` 且 `matched == sampled` | **人工（冲突）** | 「证据支持但 AI 否定 —— 谁对谁错需要人判」 |
| `band = middle` | **倾向接受** | 「证据中等，建议看一眼再签」 |
| `band = low` | **存疑** | 「证据不足，建议人工核对」 |
| `band = rejected` | **拒绝** | 见 veto 或「分数低于阈值」 |
| 无 `confidence` | **无建议** | 「规则抽取，无置信度可依赖」 |

⚠️ **冲突规则是重点**：REQ-109 实测过 3 条「5/5 命中却被 AI 判 0.0」。若程序直接把这类判成「接受」或「拒绝」，都是**替人做决定**。必须显式标「冲突」。

### 3 · 建议是**只读**的

建议**不写库**，不改变任何条目状态。批量「按建议接受」仍需：
1. 先预览（返回将影响的条数与 id 列表）；
2. 逐条 `POST /api/decide`（沿用 REQ-111 的唯一写点）。

⛔ 不许新增写端点；⛔ 不许「点一下全接受」。

## 范围

### 做

1. `suggestion` 纯函数（`confidence → {kind, reason, signals}`），与 REQ-108 的评分卡同模块
2. `/api/review` 每个条目带 `suggestion`
3. 页面：建议列 + 依据 tooltip + 「按建议筛选」+「按建议批量接受（先预览）」
4. 冲突条目**单独分组**，不与「接受/拒绝」混排
5. 测试：规则表逐条覆盖；确定性；无模型调用

### 不做

- ⛔ 不新增模型调用（v1 零 token）
- ⛔ 不给无置信度的条目编建议
- ⛔ 不改 `review decide` 的语义
- ⛔ 不让建议自动落库

## 风险

| # | 风险 | 缓解 |
| --- | --- | --- |
| 1 | 人把建议当结论，不再看依据 | 每条必须显示依据；冲突条目强制人工 |
| 2 | 建议规则与评分卡漂移 | 同一模块、同一组常量；测试断言两者一致 |
| 3 | 页面批量误操作 | 预览 + 白名单（沿用 REQ-111） |
| 4 | 「无建议」被误读成「可以随便签」 | 文案明确「规则抽取，无置信度」，且该组不参与按建议批量 |
