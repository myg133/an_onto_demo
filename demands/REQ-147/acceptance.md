## 三 · 复验裁定（Dev 交付后）

### R-1 · AC-006 的判据**是我的错**，改成"归属/包含类占比 > 5%"

我写的是「`belongs_to` 命中率必须 > 0」。Dev 查出：**这条字面判据结构性不可满足**——

`STRUCTURAL_PREDICATES`（`doc_ingest.rs:145`）里有 `belongs_to`，**谓词闸在计数之前就把它丢了**，所以它永远出现在不了"活下来"的统计里（`belongs_to_share.alive` 恒 0）。而 skill 要求中文名词化谓词，模型不会吐英文字面量。

**裁定：改口径为「归属/包含类谓词占比 > 5%」**

| 口径 | 内置 | ACP |
| --- | --- | --- |
| 严格归属类（归属/属于/所属/隶属） | 0.40% | 0.51% |
| **含「包含」类（宽口径）** | **1.19%** | **32.76%** |

**为什么接受宽口径**：它测的是"关系有没有落到**结构**上"（包含字段 / 取值包含 / 归属采集项），
而这正是我们要的——**能映射到实体-属性/实体-实体的边**。27 倍的差距不是噪声。

**但真正的价值证据是另三组数字**（这些才是本需求的理由）：

| 指标 | 内置 | ACP | 变化 |
| --- | --- | --- | --- |
| **泛动词占比**（使用/读取/写入/处理/进行/支持/融合/调用/获取） | 18.65% | **1.31%** | **-93%** |
| **关系两端都是概念**（不悬空） | 26.2% | **96.4%** | 3.7× |
| quote 校验通过率 | 100%（但它几乎整段照抄标题） | **98.7%**（**31 条编造/拼接被机器丢掉**） | — |

### R-2 · AC-003 的确定性：**接受"有条件成立"，但必须显式化**

Dev 实测：run1 有 2/95 块传输级失败 ⇒ 那 2 块不进缓存（REQ-116 纪律：失败要能重试）⇒ run2 重调、输出变。

**裁定：采纳 Dev 的 A + C**

| 项 | 内容 |
| --- | --- |
| **A** | 屏幕上**必须**报："本轮 N 块失败，重跑会重调这 N 块 ⇒ 产物可能变化"（用 `stats.failed_calls`，零语义改动） |
| **C** | 新增 `--strict-deterministic`：本轮 `failed_calls > 0` ⇒ **exit≠0 且不产出产物** |

**⛔ 不采纳 B**（让失败也进缓存）：那会把**一次瞬时故障变成永久结论**，比不确定性更糟。

**判据改写**：AC-003 的成立条件 =「**首轮所有块都有回答**」；`--strict-deterministic` 下**无条件成立**（否则不产出）。

### R-3 · 对照实验**必须分离模型变量**（这条是硬要求）

Dev 自己指出：ACP 侧是 `pi-acp` + `MiniMax-M2.7`，内置侧是 `deepseek-v4.1-flash`。

> **所以"ACP 更好"里混了"模型更强"这个变量。skill 的价值未被证明。**

**裁定：必须补一组同模型对照**（用 `session/set_config_option` 把 pi 切到 deepseek）。

若切换失败 ⇒ **如实报"未能分离"**，并在结论里降级为「ACP+MiniMax 优于内置+deepseek」，**⛔ 不许说成"我们的 skill 更优"**。

### R-4 · skill 与解析器形状不一致：**改 skill，不加第二份契约**

Dev 的处理是"在 system prompt 末尾追加 OUTPUT_PROTOCOL 做仲裁，skill 一个字不改"。

**问题**：这等于**同一条要求写了两份**（skill 里说 JSONL，运行时说 JSON 对象）——违反我们刚立的「一个行为只在一个文档定义」。

**裁定：我来改 skill**——§一 改成"**语义契约**（抽什么、证据怎么给），**输出形状由调用方的运行时指令指定**"。这样 skill 保持通用，且不再与任何通道冲突。

## 四 · 第二轮裁定（消融实验之后）

### R-6 · AC-006 改成**三条判据**（Dev 指出宽口径会被"同一种谓词刷量"刷高，我认）

| # | 判据 | 阈值 | 抓什么 | 内置 | skill | 最小契约 |

| 3 | **`doc merge` 冲突数** | **= 0** | 关系自相矛盾 | 0 ✅ | **0 ✅** | **15 ❌** |

**裁定：三条同时满足才算过。** 只有 skill 臂三条全绿。

### R-7 · R-3「未能分离模型」：接受，结论永久降级

pi 侧只有 MiniMax（4 个），我们的端点没有 MiniMax ⇒ **两边无交集**。Dev 的反向尝试与报错都贴了（`Unknown modelId` / `-32601`）。

### R-8 · 但消融实验给了一个**真正的发现**，要改 skill

**这不是刷量的全部真相**——对**结构化文档（字段表）**来说，「实体 包含 字段」**本来就是正确的关系**。

⇒ **裁定：skill 增加「结构化文档（字段表）专用判据」一节**，明确：
- 字段表里 `实体 包含 字段` / `枚举 取值包含 X` 是**合法关系**，不算泛动词
- 但仍要求：谓词要具体（`包含字段` ≠ `包含`）、每条要有 quote（字段行原文）
- 仍然禁：`使用/读取/写入/处理/进行/支持` 这类跨语料通用的泛动词

## 五 · 第三轮裁定：判据体系定稿（2026-10-25）

### R-11 · 承认：**三条判据可以互相刷**，必须成对判

Dev 用实测证明了两件事：

| 判据 | 怎么被刷 | 证据 |
| --- | --- | --- |
| ① 归属/包含占比 > 5% | **重复谓词刷量** | 最小契约臂靠 `包含字段 93 + 结构包含字段 24 + 包含 35` 刷到 29.70% |
| ③ 冲突 = 0 | **一条基数都不给**就恒 0 | v4 臂：基数覆盖 **0%** ⇒ 冲突 **0**，形式上全绿 |

**裁定：判据组合如下**（四条**同时**满足）：

| # | 判据 | 阈值 | 防的是 |
| --- | --- | --- | --- |
| ① | 归属/包含类占比 | > 5% | 关系没落到结构上 |
| ② | 谓词种类 / 关系数 | ≥ 0.33 | 同一条谓词刷量 |
| ③ | `doc merge` 冲突数 | = 0 | 关系自相矛盾 |
| ④ | **回答不可用率**（`stats.rejected.parse / chunks`） | **≤ 20%** | **"脏绿"**：31% 回答作废却三条全绿 |

### R-12 · 基数规则：采纳**严格**（只在原文写明时才给），并接受覆盖率低

v3 的 6 条冲突，根因是**模型凭印象给基数**（原文写的是"脚本把 JSON 写进目录"，压根没说几个对几个）。

**裁定：严格规则为准**（Dev 已在 `doc_acp.rs:159` 实现）。
- ⇒ 基数覆盖率**会低**，这是**正确的**（⛔ 不许为了让覆盖率好看而编基数）
- ⇒ ③「冲突 = 0」在有严格规则的前提下才**有意义**

**但**：严格规则让 v4 的覆盖归零 ⇒ 不能只看 ③。**这就是 ④ 存在的理由。**

### R-13 · ④「回答不可用率」必须进判据，且 `--strict-deterministic` 下要硬闸

**Dev 发现的观测盲区（这条很关键）**：

> 回答不可用的块**不进** `failed_calls` ⇒ 既不触发 R-2 的失败提示，也不触发 `--strict-deterministic`
> （它们的回答进了缓存、重跑逐字节相同，**确定性没问题**）
> ⇒ **29/95 作废而屏幕上一切正常。**

**裁定**：
1. 屏幕告警（Dev 已加）**保留**
2. ④ 作为判据（≤ 20%）
3. `--strict-deterministic` 下：`回答不可用率 > 20%` ⇒ **exit≠0 且不产出产物**（与失败块同等待遇）

**为什么必须这么严**：如果 31% 的回答丢了还能算"通过"，那判据测的是**幸存者**，不是抽取质量。

### R-14 · 更正记录：`cardinality_defaulted` 我读反了 —— **责任在我**

Dev 上一轮报「skill 465 · 最小契约 0」，并在本轮更正：

> `cardinality_defaulted` = 「因为没给基数而被默认成 N:1 的条数」，**越大越差**。
> v2 那 465 的意思是「648 条关系里 465 条没有基数」，不是「给了 465 条」。

**这条更正很重要，而且我当时把它当成了 skill 的优势写进裁定**（R-8 附注）。

⇒ **教训**：一个数字的含义要被**双方各自复述一遍**再用。我把"越大越好"当成了默认假设，
而它恰好是"越大越差"——**如果我拿它去写需求的验收，方向会整个反过来。**

### R-15 · R-8（字段表例外）**确认是有效改进**，不算改过头

## R-13 裁定（2026-10-26 · QA 抢救版复审后）

### 判：**FAIL（本次范围内）**

QA 构造出 R-13 第 3 条该拦的"脏绿"：

```
3 块里 1 块回答不可用（33%）+ --strict-deterministic
  ⇒ 实测 exit=0 且产出 a.jsonl / s.json
  ⇒ 按 AC 应为 exit≠0 且零产物
```

**代码只判了 `failed_calls > 0`**（`cli.rs:2464`），`rejected_parse` 只出屏幕告警。

**为什么不留到下一轮**：

| # | 理由 |
| --- | --- |
| 1 | 这条 AC 是我批的，不是"没写过的期望" |
| 2 | 它正是"假绿"本身：**33% 作废仍产出看起来成功的产物** |
| 3 | 现有测试拦不住（只断言屏幕文字，不断言退出码） |
| 4 | 补法很小（3–6 行 + 1 条 e2e） |

**修法（Dev）**：

```rust
// --strict-deterministic：failed_calls > 0  OR  回答不可用率 > 20%
// 用整数算术避免浮点：rejected_parse * 5 > chunks_total
let unusable_rate_too_high = stats.rejected_parse * 5 > chunks_total;
if failed_calls > 0 || unusable_rate_too_high { /* exit≠0，零产物 */ }
```

**必须补的判据**：
- 3 块 / 1 块不可用（33%）+ `--strict-deterministic` ⇒ **exit≠0 且无 a.jsonl / s.json**
- 同一输入**不给** `--strict-deterministic` ⇒ exit=0、产物照出（默认路径不受影响）
- 12 块 / 2 块不可用（16.7%）⇒ **exit=0**（阈值边界必须能绿）
- 默认路径产物**仍逐字节不变**

**同时修掉那句误导文案**：屏幕现在写"把这一类算成失败请用 `--strict-deterministic` **之外的闸**"——改完后它就是这道闸，文案要改口。
