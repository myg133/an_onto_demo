# 验收标准：REQ-140

## 一 · AC

### AC-001 · 三个入口都能取到 JSON-LD

- REST：`Accept: application/ld+json` ⇒ 返回 JSON-LD
- REST：`?format=jsonld` ⇒ 同上
- MCP：`sparql_query` 带 `format: "jsonld"` ⇒ `structuredContent` 是图
- 判据：三处各一次，形状一致

### AC-002 · 形状完整

- 顶层含：`@context`（`ontok` 前缀 + `xsd`）、`@graph`（数组）、`meta`
- 每个节点含：`@id`、`@type`、至少一个属性
- 判据：贴一份真实输出

### AC-003 · 同实体合并（**这是"图"与"表"的分水岭**）

- 构造一个查询：同一实体在**多行**出现（如 `?o :order__customer ?c. ?c :customer__name ?n`，两条订单同一个客户）
- ⇒ `@graph` 里该 `@id` **只出现一次**，属性合并
- 判据：节点数 < 行数；贴节点原文

### AC-004 · 节点 vs 字面量

- 类变量 ⇒ `{"@id": "…"}` 形式（或字符串 IRI + `@type: @id`）
- 普通值 ⇒ 字面量（数字/字符串/布尔）
- 判据：三种各一条（IRI / 数字 / 字符串）

### AC-005 · `meta` 必须带上限定条件（**不许吞警告**）

- 用一个**有覆盖警告**的查询（如查 `deductions`）
- ⇒ JSON-LD 的 `meta.warnings` / `meta.coverage` 与 `format=rows` 时**完全一致**
- 判据：两处对比

### AC-006 · 聚合进 `summary`

- `SELECT (COUNT(?o) AS ?n) WHERE { ?o a :order }`
- ⇒ `@graph: []`、`summary.n = 数字`
- ⛔ 不许在 `@graph` 里造假节点
- 判据：贴输出

### AC-007 · 确定性（**硬判据**）

- 同一查询两次请求 ⇒ 响应体 **sha256 相同**
- 且属性键顺序、节点顺序稳定
- 判据：两次 sha256 + 一次 `@graph` 逐字节对比

### AC-008 · 空结果

- 查一个不存在的实体 ⇒ `@graph: []`（数组），`summary` 可缺省
- 判据：贴输出（⛔ 不许 `null`、不许缺字段）

### AC-009 · 默认回执零变化

- 不带 `format` / 不设 Accept ⇒ 与基线 `600ae76` 的 rows 回执**逐字节相同**
- 判据：三条查询对比 sha256

### AC-010 · 不退化 / 零依赖

| 项 | 约束 |
| --- | --- |
| ⛔ 禁改 | 四红线 + `tools.rs` + `guard()` + `property_filter.rs` |
| ⛔ 禁 | 新依赖（JSON-LD 手动拼 `serde_json` 即可）；删测试；放宽断言 |
| 出口 | 若新增响应构造点，登记进 `OUTLETS` |
| 基线 | 同机 `develop` 实测 |

### AC-011 · 单份输出（不双份）

- `format=jsonld` 时**不回 `rows`**（避免内存与带宽翻倍）
- 判据：响应体里没有 `rows` 字段（或为空）

## 三 · 裁定（Dev 提的两处"替 BA 做的决定"）

### R-1 · `summary` 的四种形状：**接受，但冗余必须被测试钉住**

Dev 实现：

| 情形 | `summary` |
| --- | --- |
| 非聚合 | `{"nodes":N,"row_count":M}` |
| 聚合（单行） | `{"n":42}` |
| 聚合 + GROUP BY | `{"n_groups":k,"groups":[…]}` |
| 投影里没有实体 | `{"nodes":0,"row_count":M,"detached":[…]}` |

**裁定：接受。** 理由：

| 情形 | 如果硬按"只有聚合才给 summary" | 后果 |
| --- | --- | --- |
| 只有字面量的投影 | 那些值**没有去处** | ⚠️ **静默丢数据**——正是我们一直在防的 |
| GROUP BY | 分组结果无处可放 | 同上 |

所以 `detached` 这一格是**必要的诚实**，不是擅自扩形状。

**但有一条附加要求（R-1a）**：

> `summary.nodes` 必须**恒等于** `@graph.length`；`summary.row_count` 必须**恒等于** `meta.row_count`。

因为这两处是**同一事实的两个表示**。我们不禁止冗余，但**禁止漂移**——必须各有一条测试把它们钉死。

（这正是前面踩过的坑：同一件事两处各算一次，迟早算出两个数。）

### R-2 · `xsd:date` / `xsd:dateTime` 用值对象：**接受，是我的 AC 写得不准**

Dev 给：

```json
{ "@value": "2026-10-01", "@type": "xsd:date" }
```

我 AC-004 写的是"字面量按原生 JSON"，**这句话对日期类型不成立**——JSON 没有日期类型，硬塞字符串就丢了类型信息。

**裁定：**

| 类型 | 输出 |
| --- | --- |
| 字符串 / 数字 / 布尔 | **原生 JSON**（`"abc"` / `0` / `true`） |
| `xsd:date` / `xsd:dateTime` / 其它带类型的 | **值对象** `{"@value":…,"@type":…}` |

**AC-004 的口径以此为准**（原文表述不准，已订正）。

### R-3 · 一条 Dev 自己发现的判据缺陷（值得记）

Dev 说：

> 变异①「节点不排序」时，**只比"两次请求"抓不住**（PG 可能碰巧同序），
> 判据必须是「**同一份数据两种行序 ⇒ 同一份字节**」。

**这条比 AC-007 更严，采纳为 AC-007 的实现口径**：

- AC-007 原判据（两次请求 sha 相同）保留
- **追加**：同一数据集按**不同行序**输入 ⇒ 输出必须逐字节相同（这才真正证明排序，而不是碰巧）

> 这是「判据有牙」的又一例：**两次请求相同**可能只是运气，**换行序仍相同**才是排序。
