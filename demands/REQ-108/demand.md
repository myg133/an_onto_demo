# 需求：REQ-108 · 带证据与置信度的关系抽取

## 基本信息

| 项 | 值 |
| --- | --- |
| 需求编号 | REQ-108 |
| 优先级 | **P0**（本体质量的地基：现在 42% 的推断关系要么错、要么无证据） |
| 状态 | 进行中 |
| 代码基线 | `develop` `4573269`（REQ-107 已合并） |
| 来源 | 2026-10-21 用真实源库 `anspire_open_uat` 构建本体时的实测发现 |

## 需求描述

### 问题不是「抽得少」，是「抽错了没人知道」

该库 **0 个外键约束**，81 条关系全部由列名约定（`*_id`）推断。2026-10-21 用 5 行采样逐一验证后：

| 判定 | 条数 | 占比 |
| --- | --- | --- |
| 成立（5/5 命中） | 47 | 58% |
| **不成立（0 命中）** | **7** | **8.6%** |
| 存疑（部分命中） | 5 | 6.2% |
| 无法验证（源列全空） | 20 | 24.7% |
| 类型不匹配 | 2 | 2.5% |

**这 34 条错误或不可验证的关系，目前和 47 条正确关系长得一模一样**——都进提案、都进客户视图、都没有任何标记。

### 三类错误（已实测，是可复现的缺陷，不是理论风险）

| 类型 | 实例 | 根因 |
| --- | --- | --- |
| **目标列选错** | `llm_model_peak_config.model_id → llm_model.id`（0/5）；改成 `→ llm_model.model_id` 后 4/5 | 规则只认「同名 + 主键」，没考虑目标表用**业务键**被引用 |
| **同名不同义** | `balance_operation_log.batch_id → gift_code_batch.id`（0/5）；`instance_manager.session_id → simulate_login_sessions.id`（0/5） | `batch_id` / `session_id` 是**泛化名**，名字不指向任何具体实体 |
| **类型不兼容** | `dim_customer_binding.channel_code`（text）→ `marketing_channel.id`（int） | 没有类型相容性校验 |

### 目标

让每条推断关系**带证据、带置信度、按置信度分档处置**：

```
规则/AI 抽候选 ──▶ 采样验证（5 行）──▶ 置信度评分 ──▶ 分档：折叠 / 逐条 / 待查 / 不提案
```

### 为什么现在做

1. 本体已经交付给业务看过一轮（83 对象 / 28 概念），**关系质量是下一步最明显的短板**；
2. 关系错了会直接体现在客户问答上（「这台设备和哪个工单有关」答错，比答不出更糟）；
3. 后面要接 AI 抽取（REQ-109 候选），**AI 更需要置信度**——没有分档机制，AI 的产出无法被自动分拣，只能全量人审。

## 范围

### 做

1. **勘查补采**：`ontok-introspect` 增加主键、单列唯一索引信息（现在完全没有，导致「目标列是不是键」无法计算）
2. **采样器**：只读会话、每关系 5 行、**确定性取样**（`ORDER BY 主键 LIMIT 5`）、**只落聚合不落原值**
3. **置信度评分卡 v1**：5 个信号 + veto 上限，`method` 必填
4. **提案条目携带 confidence**：落库，建模视图与审核界面可见
5. **分档路由**：≥0.90 默认折叠 / 0.60–0.90 逐条 / 0.30–0.60 待查清单 / <0.30 不提案
6. **校准闭环**：记录人工决定 → 一条命令输出分箱命中率

### 不做

- ⛔ **不接 AI 语义项**（`semantic_fit` 只在评分卡里**预留权重位**，v1 不调用任何模型）——理由：先把确定性部分做对，AI 才有意义
- ⛔ **不支持复合键**（识别到就降级，见 AC-004）
- ⛔ **不做动作层（ActionType）**（独立需求）
- ⛔ **不改抽取出的 items**（只新增 confidence，不改现有 164 条内容）
- ⛔ **不在客户视图暴露置信度**（内部质量指标，不是对外承诺）

## BA 预先裁定（开发前已定，Dev 不必再猜）

| # | 问题 | 裁定 |
| --- | --- | --- |
| **R1** | 采样读业务数据行，与「零业务数据行」承诺冲突 | **允许**，但四条硬约束：① 只读会话（`SET default_transaction_read_only = on`）② 每关系最多 5 行 ③ **只落命中数/样本数，不落任何原值** ④ `--no-sample` 可整体关闭（关闭时 confidence 只由结构信号算，且必须标 `data_evidence: none`） |
| **R2** | 复合键 | v1 **识别但不支持**：检测到复合唯一键 ⇒ `confidence` 上限 **0.50**，信号 `composite_key_unsupported` |
| **R3** | 多态列（`*_type` + `*_id` 同表并存） | 目标表不确定 ⇒ 上限 **0.40**，信号 `polymorphic_target` |
| **R4** | 自引用（`parent_id` 指向本表） | 允许，但目标列必须唯一；否则上限 **0.50** |
| **R5** | 客户视图是否显示置信度 | **不显示**。只在 `--model-view` 与审核界面出现 |
| **R6** | 分档阈值 | ≥0.90 折叠 · 0.60–0.90 逐条 · 0.30–0.60 待查 · **<0.30 不提案** |
| **R7** | 客户视图里那 34 条低分关系怎么办 | 分档后 `<0.30` 的自然不进提案；`0.30–0.60` 进「待查」但**不进客户视图** |

## 风险

| # | 风险 | 缓解 |
| --- | --- | --- |
| 1 | 采样在生产库上造成压力 | 每关系 5 行、只读、主键排序走索引；大表用 `LIMIT` 提前终止 |
| 2 | 采样泄漏敏感值 | 只落聚合；`--no-sample` 可关 |
| 3 | 分数成为「免审背书」 | 阈值只决定**审核顺序**，双轨审核不变；校准不达标即调权重 |
| 4 | 权重拍脑袋 | 用 81 条真实关系做初始验证（7 条已知错误必须落「拒绝」），后续靠校准数据调 |
