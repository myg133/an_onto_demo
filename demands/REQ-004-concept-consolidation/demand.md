## 1. 问题：91 张表 ≠ 91 个业务对象

REQ-003 从真实源库（`<业务库名>`，91 表 / 1051 列）抽出
**91 个实体**，客户视图里是 **91 个独立对象**。

按业务概念聚类（共享前缀）后：

| | 数量 |
| --- | --- |
| 源库表 | 91 |
| **实际业务概念** | **约 65** |
| 由 ≥3 张表组成一个概念 | 6 组 |
| 受影响表数 | 18 / 91（19%） |

典型的一概念多表：

| 概念 | 被拆成的表 |
| --- | --- |
| **客户** | 客户意向 · 客户折扣返利 · 客户订阅 · 客户权限 · 客户限流 · 客户账号绑定 …（10+ 张） |
| **套餐** | 套餐模板 · 套餐产品 · 套餐权益 |
| **子账号** | 子账号权限 · 子账号额度 · 子账号绑定权限快照 |
| **服务商** | 服务商分组 · 服务商分组明细 · 服务商备份 |
| **鉴权缓存** | 缓存变更事件 · 缓存消息事件 · 缓存触发状态 |
| **活动** | 活动 · 活动关键词 · 活动推荐表 |

客户视图里「客户意向」「客户折扣返利」「客户订阅」并排出现 —— 
客户的反应大概是「这不是同一个客户吗？」。**认知负担没降下来。**

## 2. 但「抽取时聚合」是错的

考虑过直接在抽取层把同前缀的表合成一个实体。**三条理由否决它**：

1. **物理结构是事实，归并是判断。** `package_templates`/`package_products`/`package_benefits`
   确实同属「套餐」；但 `activity` / `activity_recommendations`（活动 / 活动推荐）
   **该不该合？前缀匹配回答不了。**
2. **零外键下自动聚合准确率上不去。** 91 表、0 外键、注释覆盖不均。
   聚合要靠语义推理 —— **错了比不聚合更糟**：
   不聚合只是啰嗦，**聚合错了是误导**。
3. **写入路径是按表来的。** `apply` 按 `entity_type.key`（= 表名）落库，
   聚合会让「一次 apply 改了哪张表」不可追溯。

> **所以：一表一实体作为默认值是对的，作为终点是不够的。**
> 缺的那一层是**归并**，它属于展示层，不属于数据层。

## 3. 模型里缺的那一类关系

现有模型只有**层级**：

```
层级（parent / belongs_to）:  设备 ──属于──▶ 资产
    「A 是 B 的一部分」
```

但「套餐模板 / 套餐产品 / 套餐权益」**不是层级** —— 它们是**同一概念的三个侧面**。
这是第三类关系，现在缺着：

```
概念归并（新增）:  套餐模板 ┐
                   套餐产品 ├─▶「套餐」    「它们共同表达同一个东西」
                   套餐权益 ┘
```

| 类型 | 语义 | 现状 |
| --- | --- | --- |
| 层级 `parent` / `belongs_to` | A 是 B 的一部分 | ✅ 有 |
| 引用 `references` | A 指向 B（`N:1`） | ✅ 有 |
| **概念归并** | 多个实体共同表达一个业务概念 | ❌ **缺** |

## 4. 方案：概念组（Concept Group）

### 4.1 数据形状（示意，未定稿）

归并组是**本体里的一等对象**，不改动实体本身：

```json
{
  "kind": "add_concept_group",
  "target": "套餐",
  "payload": {
    "key": "package",
    "display_name": "套餐",
    "members": ["package_templates", "package_products", "package_benefits"],
    "extracted_by": { "agent": "...", "version": "...", "round": 1 },
    "evidence": [
      { "table": "package_products", "claim": "套餐下可买的产品" },
      { "table": "package_benefits",  "claim": "套餐包含的权益" }
    ]
  }
}
```

**关键：实体仍然按表独立存在、按表落库。** 概念组只是**额外的展示层声明**。

### 4.2 三条设计原则

| 原则 | 为什么 |
| --- | --- |
| **不合并实体，只声明分组** | 抽取层保持确定、可回退。归并判断错了，去掉分组声明即可，**底层结构不动** |
| **成员必须全是本项目内的实体** | 否则客户视图里会指到不存在的对象（`usable_as_human_name` 会过滤） |
| **嵌套归并必须被拒** | 组里不能有组。否则 A∪B、B∪C、A∪C 三个声明可能相互矛盾，且无法判定归并优先级 |

### 4.3 客户视图按概念组投影

- 概念组 → 对客户显示**一个**对象，`name` = 组的中文名
- 属性 = 组内所有成员的属性并集，**同名去重**（不同表可能有 `created_at`）
- 关系 = 组内成员的关系，**指向其他概念组时也要重定向**
- **未被任何组覆盖的实体，照旧单独显示**（向后兼容：没有组 = 现在的行为）

### 4.4 归并组从哪来

**LLM 从 schema 元数据提议 → 双轨审核 → 冻结。** 复用现成流程，不新增机制。

⚠️ **但提议只是草稿。** 真正���定「哪些该合」的是客户，不是模型 —— 见 §6。

## 6. AC-013 判读设计（本需求的核心产出之一）

### 6.1 为什么归并规则要靠判读拿

我列的 6 组聚类里，**哪些该合是我的猜测**。
「套餐该合、推荐不该合」是判断，不是事实 —— **这是业务问题不是技术问题**。

所以：**不要先猜一轮聚合规则再去问客户**。直接拿真实客户视图去问，
客户的答案**就是**归并规则本身。

### 6.2 判读对象

**3 名非开发者外部评审人**（客户方业务人员）。
BA、审核 agent、实现者**均不得代判** —— 代判等于没验。

### 6.3 判读材料

| 材料 | 形式 | 要求 |
| --- | --- | --- |
| 客户视图 | HTML 页面（建议） | **不得出现任何建模术语**；每个对象可展开看属性与关系 |
| 随机抽样 | 8~12 个对象 | 覆盖高密度对象（如「客户」相关）与稀疏对象，避免全看 |

### 6.4 问题清单

> ⚠️ **所有问题都用客户的语言**，不许出现「实体」「基数」「归并」这类词。

| # | 问题 | 验证什么 | 判据 |
| --- | --- | --- | --- |
| Q1 | **这个东西是什么？** | 对象可识别性 | 答对率 ≥ 80% |
| Q2 | **它有哪几个属性？** | 属性完备性 | 与视图对比，识别率 ≥ 70% |
| Q3 | **有没有哪个词你看不懂 / 不像业务说法？** | 零术语（AC-005 的真实检验） | **必须 0 个** |
| Q4 | **「A」和「B」是什么关系？谁有谁？** | 关系**方向** | 正确率 ≥ 80% |
| Q5 | **「A」对「B」是一个还是一个多个？** | 关系**基数** | 正确率 ≥ 80% |
| Q6 | **下面这些里，哪些其实是同一个东西？** | ⭐ **归并真值** | 直接产出概念组草稿 |
| Q7 | **这些名字里，有哪个你更习惯叫别的？** | 命名 | 产出别名候选 |
| Q8 | **用一句话说：它帮你理解了什么？** | 整体价值 | 定性 |

**Q6 是本轮新增的核心问题**，给判读人一份**打散的候选列表**（含 3~4 组我认为该合的、
混 1~2 组我认为不该合的作对照），让他们挑。

⚠️ 3 名评审人独立作答，**不看彼此答案**。分歧大的项单独复盘。

## 7. 与关系基数问题的耦合

`★ Q4/Q5` 验的是**关系方向与基数**。REQ-003 把 51 条关系全标成 `N:1`（多对一），
但零外键下**单列 `*_id` 多数其实是 `1:N`** —— 「一个客户 → 多条订阅记录」。

这跟归并是同一件事的两面：客户视角里「客户 → 订阅」本来就该是一对多。
**标反了客户会觉得别扭，Q5 会直接暴露。**

**所以：关系基数的语义重判不单独做，交给 AC-013 的 Q5 一次验完。**
