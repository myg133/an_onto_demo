# 验收标准：REQ-040 `test_backfill_…` 的前提竞态

> 依据 REQ-039 两轮验收带出（QA 独立复核）写成。基线：`ab2f56c`（develop）。
> **既有缺陷，非 REQ-039 引入** —— 但 REQ-039 修掉排他锁后它浮出水面，且**当前就在污染每一次全量测试**。

---

## 背景：竞态在哪

三方对不齐，这是根子：

| 侧 | 作用域 | 位置 |
| --- | --- | --- |
| **写入** | 版本内，**但 3 条 INSERT 各占一个自动提交事务** | `tests/test_snapshot_write_paths.rs:609` `insert_legacy_actions` |
| **断言** | **版本内**（`WHERE version_id = $1`） | 同文件 `ordinals_of` |
| **回填** | **全局**（子查询**无 `version_id` 过滤**） | `src/db/pg.rs` 的 `BACKFILL_PATCH` |

于是：并发 `migrate()` 的回填 `UPDATE` 落在 INSERT 2 与 3 之间时，
会把本测试**刚插入的行**一起回填掉 ⇒ 断言读到的前提被污染：

```
left: [0, 0, 1]   ← 回填只看到 2 条
left: [0, 1, 2]   ← 回填看到全部 3 条
right: [0, 0, 0]
```

## 归因已被 QA 独立复核（两轮都验过）

- **不是 REQ-039 引入的**：确定性探针在**基线与修复版上都复现**同样的 `[0,0,1]`
- **REQ-038 时代的归因是错的**：「基线那个 `AccessExclusiveLock` 串行化掩盖了它」
  —— **站不住**。基线少失败的真因是 `40P01` 把污染事务**整个回滚**了
- **生产侧无锁可解**：QA 验证过 `SHARE ROW EXCLUSIVE` 仍会落在 INSERT 2 与 3 之间。
  **修法只能在测试侧**

## 两个候选修法（选一个，或组合）

1. **把 3 条 INSERT 合成一条多行 INSERT** —— 一个语句即一个隐式事务，中间没有窗口
2. **把插入与前提断言包进同一个显式事务** —— 靠事务隔离把并发回填挡在外面

**两者都不放松任何判据。** 合成多行 INSERT 后，回填测试要验的三条性质
（确定性、保序、幂等）一条不少 —— 变的只是「怎么把行放进去」。

## AC-001 · 前提竞态不再复现

- 测试步骤：跨进程并发跑 `tests/test_snapshot_write_paths.rs`
  （至少 **15 次进程运行**，须与 REQ-039 验收用的口径可比）
- 预期结果：`test_backfill_is_deterministic_preserves_and_idempotent` **0 次**因前提失败
- 类型：功能

> ⚠️ **不得写死复现率**。REQ-039 两轮实测数据彼此不可比：
> Dev 报「baseline 9/15、fixed 1/15」（字面像修复后更差），QA 测得 **13/15 与 10/15**。
> **同一竞态、不同负载采样**。所以验收看「修复后 15 次里 0 次前提失败」，
> 不看「相对基线改善了多少」。

> 📌 **残留窗口（Dev 如实交代，BA 已知悉并接受）**：多行 INSERT 提交后到前提读取之间
> 仍有约 **1 个 RTT**（共享集群 ≈ 157 ms）的窗口 —— 一个恰好在此窗口内启动的回填
> 会把 3 行整批改掉，前提读成 `[0,1,2]`。要彻底归零需让前提读与 INSERT 同语句
> （`RETURNING`），但那会让前提从「回表读」变成「读 INSERT 自己的返回」，
> **改变 AC-002 想保住的前提语义**。**本需求不要求归零**，
> 但 QA 须独立评估这个残留窗口是否可接受。

> 📌 **第二条污染通道（Dev 新发现）**：除 `[0,0,1]` 前提失败外，同一竞态还有第二种落点 ——
> 命中**确定性性质断言**，签名 `[("a_first",0),("m_mid",1),("z_last",1)]`，
> 机制是 PG 的 **EvalPlanQual**（并发回填的 UPDATE 提交后本测试的 UPDATE 重走 EPQ，
> `a.ordinal = 0` 不再成立 ⇒ **静默跳过**）。Dev 称被同一条多行 INSERT 一并堵死
> （原子插入后回填要么看见 0 行、要么看见 3 行，**子集这个前提消失了**）。
> **QA 须独立验证这个「同源同解」的判断**，并确认修复后两种签名都不再出现。

## AC-002 · 三条回填性质一条没少

- 测试步骤：读改后的测试，确认它仍然验证：
  - **确定性**（`v_legacy` 的插入顺序故意与 key 字典序相反，结果仍按字典序）
  - **保序**（`v_written` 已有非 0 序且故意不连续，不得被改写）
  - **幂等**（重复 `migrate()` 结果不变）
- 预期结果：三条性质**全部仍在**，`migrate()` 调用次数与语义不变
- 类型：功能
- **理由**：这是本需求最容易滑进去的坑 —— 「消除竞态」很容易顺手把断言也删了

## AC-003 · 合成 INSERT 不得改变被测语义

- 若选方向 ①：确认多行 INSERT 的**行序**与原来逐条插入一致
  （原代码靠 `for k in keys` 的顺序制造「插入顺序与字典序相反」这一前提，
  合成一条时**必须保留这个顺序**，否则确定性判据失效而测试仍然全绿）
- 若选方向 ②：确认事务边界没有把 `migrate()` 也包进去
  （`migrate()` 自己要取排他锁，包进同一事务会引入新问题）
- 类型：测试有效性
- **这是本需求真正的判别力考验** —— 合成 INSERT 写错顺序，
  测试会安静地失去它最核心的那条性质

## AC-004 · 判别力自证（变异必做）

- 测试步骤：对修好的测试做变异，至少覆盖：
  1. **还原成逐条 INSERT**（即缺陷原形）⇒ 须在跨进程并发下复现前提失败
  2. **打乱多行 INSERT 的行序**（若选方向 ①）⇒ **见下方修订**
  3. 把 `migrate()` 的幂等调用删掉一次 ⇒ 须被幂等性质抓住
- 预期结果：每条变异**真的跑过**，报告**二进制名 + 运行条数**
- 类型：测试有效性
- **存活变异必须逐条论证**：是「等价变异」还是「判据本身有洞」？

> **注意**：本判据是**概率性**的（依赖跨进程并发）。变异 1 必须
> **多轮采样**才能下结论，单轮绿不算杀死。报告须给出采样次数。

### ⚠️ 2026-10-09 修订：第 2 条按字面写**不可满足**（BA 起草时的盲点）

原文写的是「打乱行序 ⇒ 须被**确定性性质**抓住」。**这条按字面做不到**，
Dev 实测确认，理由是结构性的：

确定性性质比较的是**回填之后**的状态，而正确的按 key 回填对**任意**插入顺序
都给出同一答案。唯一能让 outcome 断言变红的行序是「物理行序 ≠ 按 key 序」的那种 ——
而**字典序恰好让两者重合**。于是字典序这个唯一危险的排列，
恰好是唯一 outcome 断言永远看不见的那个。

**修订为**：在 `insert_legacy_actions` 里**就地加一条前提自检**，
把「插入顺序 ≠ key 字典序」这条不变式钉在产生它的地方。
变异 2b（行序改成字典序）须**确定性**变红（不依赖并发采样）。

**为什么接受这个修订**：就地断言比核对 `ctid` 可靠 ——
Dev 实测同一页 `offset ≥ 10` 时按 `ctid` **文本**排序就排错（自然序是数值序），
物理量本身不可靠；而不变式本来就写在调用点的代码里。

**边界**：这条自检**不放松任何断言**，只是多了一条更严的前提。
BA 已判定**在范围内**，理由是没有它 AC-004 第 2 条无法满足。

  （仅 `information_schema` / `pg_catalog`，零业务数据行）。

  测试库 `.env` 里库名是 `notol`，要用 `ontol`。
