## 1. 形态机制 vs 换地方堆词

### 1.1 实际加了多少后缀 vs 多少词根

**比例：21 个后缀 : 118 个词根 ≈ 1 : 5.6。**

这个比例**不是** Dev 描述的「不是补 147 个词条」那个量级 —— 实际就是补了 118 个词。
但**比例失衡不等于打补丁**，关键要看这 21 个后缀是否真的在产生乘数效应（§1.2）。

### 1.2 新词根 / 多层嵌套 / 同族变体的实测

我写了一个探针（`tests/zz_audit_probe.rs`，只调 `pub fn humanize_column`，**未改任何实现**，审核后已删除），
在 **462 个真实源库列名** + **234 个构造输入**上跑。

**A. 已知词根 `hit` × 全部 21 个形态后缀**（这些组合 Dev 的测试里一个都没枚举过）

```
hit_at→命中时间   hit_time→命中时间   hit_date→命中日期   hit_until→命中截止时间
hit_count→命中数量 hit_times→命中次数  hit_num→命中数量   hit_amount→命中金额
hit_total→命中合计  hit_rate→命中比率  hit_ratio→命中比例  hit_percent→命中百分比
hit_unit→命中单位   hit_cycle→命中周期  hit_period→命中周期  hit_by→命中操作人
hit_status→命中状态 hit_type→命中类型  hit_name→命中名称   hit_version→命中版本
hit_size→命中大小
```

**21/21 全部命中。** 只加了 `hit` 一个词根，就自动认得 21 种列形态 ——
**这是「规则会自己长出来」的硬证据，不是枚举。** Dev 的这条论证成立。

**B. 词表里没有的新词根 → 全部 `None`（fail-closed 正确）**

```
zzz_count→None  qqq_at→None  wombat_rate→None  mystery_by→None
frobnicate_cycle→None  xylophone_at→None
```
没有「凭空翻出来」。**机制是「剥后缀 + 查词根」，不是猜词根。**

**C. 多层嵌套：一层形态后缀 + 复合词根 —— 支持**

```
last_hit_at→最近命中时间      auto_renew_at→自动续费时间
current_usage_count→当前用量数量  used_quota_total→已用额度合计
customer_quota_total→客户额度合计  last_retry_at→最近重试时间
```
`resolve_stem` 按 `_` 切词元逐个查，所以「复合词根 + 形态后缀」能递归组合。

**但两个上限**：
- **双形态后缀不支持**：`hit_at_count`→`None`、`create_at_count`→`None`（只剥一层）
- **词元只要有一个不认得就整体丢弃**（这是 S-2 的设计，代价是覆盖率）

**D. 同族变体：行为一致，但暴露一个系统性缺口**

| 输入 | 结果 | 输入 | 结果 |
| --- | --- | --- | --- |
| `a_count` | None | `ab_count` | None |
| `a_b_count` | None | `a_bc_count` | None |
| `hit_count` | 命中数量 | `hits_count` | **None** |

brief 指定的 `a/ab/a_b/a_bc` 四例行为**完全一致**（都丢弃），无不一致问题。
但 `hit`→`命中数量` 而 `hits`→`None`，暴露出**屈折形态（复数/派生词）完全没处理**。

### 1.4 恢复量分解实验（量化「机制 vs 词」）

我把 `view.rs` 分别改成四种状态，各自实测丢弃率（每次备份 + `cmp`+`sha256` 还原 + 强制重编译）：

| 状态 | 丢弃 | 丢弃率 | 该状态下的恢复量 |
| --- | --- | --- | --- |
| REQ-006 前（`view.rs` 回退 `4586c78`） | 172 | 17.8% | — |
| **只加 118 个词，关掉形态后缀** | 106 | 11.0% | **+50**（词贡献） |
| **只加 118 个词，关掉无后缀复合词** | 97 | 10.1% | **+16**（复合词贡献） |

**91 条恢复 = 词 50 + 形态后缀 25 + 无后缀复合词 16。**

即：**按恢复条数，词表增补占 55%，形态机制占 45%。**

### 1.5 结论

**形态处理器是真机制，不是换了地方堆词** —— 这一点 Dev 是对的，证据充分（§1.2 A 组 21/21、§1.2 B 组 fail-closed）。
但有两点必须说清楚，Dev 的表述把它们盖过去了：

1. **规模上确实是「118 词 + 21 后缀」，词是后缀的 5.6 倍**，按恢复条数词表贡献还略多于机制。
   「不是补 147 个词条」这个说法回避了「补了 118 个词」这个事实。
2. **机制只覆盖了「派生后缀」，没覆盖「屈折形态」** —— 而这恰恰是**同类问题的下一层**。
   实测（下表）大量真实列因此仍在丢弃：

   | 词表里有单数 | 复数/派生词 | 结果 | 真实影响（被丢弃的 81 条里） |

   | `cycle`→周期 | `cycles` | **None** | `套餐模板/available_cycles` |
   | `price`→价格 | `prices` | **None** | `套餐模板/prices`、`original_prices` |
   | `week`→周 | `weekdays` | **None** | `服务高峰配置/weekdays` |
   | `hour`→小时 | `hours` | **None** | `套餐模板/cooling_hours` |
   | `month`→月 | `monthly` | **None** | `授权额度配置/used_monthly` |
   | `day`→天 | `daily` | **None** | `授权额度配置/used_daily` |
   | `model`→模型 | `models` | **None** | `套餐产品/models` |
   | `is_deleted`→是否删除 | `is_delete` | **None** | `服务应用/is_delete` |
   | `operator`→操作员 | `operation` | **None** | `内部操作记录/operation_type` |

   另有 `current_period_start` / `current_period_end` 被丢弃 ——
   **`period` 在 `FORM_SUFFIXES` 里当后缀（`_period`→周期）却不作为独立词元在 `BUSINESS_WORDS` 里**，两张表不一致。

   **下个客户库只要列名带复数，同样的静默丢弃会再来一次。**
   按项目自己的判据（「判据是规则不是词」），这是本轮**没做完的同一件事**，不是新问题。

3. 把「丢弃的属性清单」也断言成基线快照，防止**无声的覆盖率回退**

### 5.5 我自己踩了同一个 mtime 坑（诚实记录）

我的分解实验第一版用 `shutil.copy2` 还原文件，**`copy2` 保留 mtime**，
cargo 认为文件没变、**不重编译**，导致「当前状态」那一测读到了上一个变异的陈旧二进制，

Dev 用的是 `cp`（会更新 mtime），所以他的脚本没踩到；但**任何用 `cp -p` / `tar` / `rsync -a` /
`shutil.copy2` 做还原的脚本都会踩到**，而且症状是「数字看起来很合理」，最难发现。
**建议把「还原后必须看到 `Compiling ontok`」写进变异脚本的硬性判据**，而不只验 `cmp`。

**顺畅的部分（约占 70%）**：
- 双击就开，首屏 40 个首字分组、13 个 ★ 重点默认展开 —— **导航设计是有效的**，
  Dev 「按首字分组、抽样默认展开」的取舍我认可。
- 搜索框真的能用（我实测：搜「代理操作授权」→ 命中 3/90，分组同步收敛到 3/40）。
- 关系问句是人话，「一个客户，有几个 API 调用日志？」不需要任何解释。

**三处会卡住的地方**：

1. **同一个「客户」有 4 种叫法**（§3.5）。判读人一旦要回答「客户和什么有关」，
   得先花时间确认 `所属客户` / `客户标识` / `客户` 是不是一回事。
   **这是最大的时间黑洞。** 而且 `客户` 还和对象名撞车，页面上完全看不出这是有意为之。

2. **属性名重复显示两遍（598/868 = 68.9%）**。
   页面上「过期时间　过期时间」「状态　状态」这样并排出现。
   判读人的第一反应会是「**这工具是不是坏了**」，然后要么怀疑材料、要么怀疑自己。
   **我实测：属性名和它的说明文字在 598 条上完全相同** ——
   源库注释和列名本来就是同一句话，渲染层照抄了两遍。
   **这是一行判断就能修的**（说明 == 名字时就不重复输出），但对判读第一印象伤害最大。

3. **72 条属性名含英文、6 条把枚举值域当属性名**。
   最典型的四个在**「客户」这个核心对象**上：

   ```
   0: 未分类, 1: 个人用户, 2: 企业用户     ← 这是「用户类型」，但页面上看不出来
   0: 未认证, 1: 已认证                  ← 这是「认证状态」
   0: 已停用, 1: 已启用                  ← 这是「启用状态」
   0: 不允许, 1: 允许                    ← 这是「是否允许」
   ```

   **「客户」对象 15 个属性里有 4 个是这样的裸枚举串。** 判读人看到这四条，
   既不知道字段叫什么，也不知道该不该算「属性识别成功」——
   **Q2 在这里会直接卡住或产生分歧。** 这不是「难懂」，是「无法判读」。

### 6.2 如果我是客户方业务人员，最觉得「技术人的东西」的词

按「最刺眼」排序：

| 排名 | 词 | 出现在 | 为什么刺眼 |
| --- | --- | --- | --- |
| 1 | **`IP 地址`** | 属性名 | 我第一次看到以为翻错了。而且「地址」和「IP」重复了一遍语义 |
| 2 | **`0: llm, 1: emb`** | 属性名 | 纯技术枚举，我完全不知道 llm/emb 是什么 |
| 3 | **`Provider绑定配置`** / **`Provider组绑定配置`** | 属性名 | 混排英文，中文翻译没有，像是没做完 |
| 4 | **`RSA 公钥 PEM`** | 属性名 | 我知道是公钥，但 `PEM` 是格式名，跟业务无关 |
| 5 | **`NULL` / `free` / `active` / `pending`** | 说明文字 | 看不懂的英文状态值 |
| 6 | **`操作前邀请方code`** | 属性名 | 混排 + 小写 code |
| 7 | **`资产类型：credit/recharge/free`** | 说明文字 | 三个英文枚举直接糊在说明里 |

**共同点：这些都不是「难」，是「跟我没关系」** ——
业务人员能理解「过期时间」「自动续费」「已付金额」，
但对 `0: llm, 1: emb` 这类**值域定义**根本无从判断，
而 REQ-005 又**刻意**规定这类值域不许翻译（理由是「翻了会破坏信息」）。

**这是 REQ-005 与 REQ-006 之间一个没被解决的产品张力**：
REQ-005 为「值域准确性」保留英文 ✅，REQ-006 为「判读人可读性」要求零技术串 ❌。
**两边都对，但没有人裁决过冲突时怎么办。** 建议单独决策：
要么给值域配一句中文说明（「模型用途：0=对话大模型，1=向量模型」），
要么在页面上把这类属性单独标一个「这是取值范围说明」。

### 6.3 另两个判读效率观察

- **43/90 个对象（48%）显示「目前还没找到它和别的东西的关联」**。
  判读人翻到一半的对象是死胡同。建议对这类对象也给出一点线索
  （哪怕「这个对象目前是独立的」），比空白好。
- **「客户」对象有 37 条关系，全是「多个」**。
  这个对象会成为判读的主战场，但 37 行同构问句视觉上很密。
  **建议按业务域二次分组**（计费类 / 权限类 / 消息类），
  客户已经口头确认了方向，所以分组不会引起歧义，只是可读性优化。

## 7. 结论

### VERDICT：**需修补**（不是「判读材料可用」，也不是「不可用」）

**为什么不是「可用」**：本次交付的产物就是 3 名外部评审人手里的唯一材料，
而它有 **3 类会系统性污染判读结论的缺陷**（见下阻断项）。
尤其第 3 条会让 Q2（属性识别率）**算出偏高的错误数字**，
把「我们清洗过严」误报成「系统抽取能力不足」，**误导下一轮需求方向**。

**为什么不是「不可用」**：核心机制是真的、变异自证是真的、S-2 纪律真的守住了、
页面真的能离线双击打开、关系问句真的说人话了。**地基是好的，坏的是表层。**
