## 五 · AC

### BA 预先裁定（不用 Dev 再猜，减少一轮往返）

| # | 裁定 | 依据 |
| --- | --- | --- |
| **R1** | `ontology diff` 归**建模轨**，**豁免发布闸** | `diff_snapshots` 吃的是 `Snapshot`（`diff.rs:81`），输出的是「key / field / parent / evidence」这类**建模结构本身**（`diff.rs:57-66`）。对建模结构过「客户可见性闸」等于把闸用错地方 |
| **R2** | `diff.rs:53` 的注释「给 CLI 与客户看」**必须改**为「给 CLI 与建模人员看」 | 与 R1 冲突的注释会误导下一个人「这条是客户出口」，从而把它接到客户管线上 |
| **R3** | `diff` 的**换行不转义**（`diff.rs:74` 直接 `clone` 字符串）**不在本需求修**，登记为已知限制 | 建模轨内部展示问题，不影响客户面；修它属于另一个需求的转义口径统一 |
| **R4** | 计数口径固定 **33**（CLI 22 + HTTP 4 + MCP 7），Dev 若要改口径必须**先提异议再改** | 见 §零 |

### AC-001 · 存在唯一的客户类出口管线，且出口只能声明「格式 + 轨道」

- 客户类渲染串**只能经由**一个必过闸的入口写出，而不是每个分支各写一次 `scan_modeling_terms`
- 出口层**不允许**再各自决定「要不要剔除 / 要不要清洗 / 要不要拦」
- ⛔ 不许把 `guard()` 的内部实现抄一份（纪律 H）；只许复用

### AC-002 · 13 个客户类出口全部接线（逐条可核对）

§一 表里的 13 条，每条都要在**管线调用点**上可查（`path:line`）。
验收方式：给一张「出口 → 管线调用点」映射表，**逐条贴代码行**。

### AC-003 · 漏接即红（**本需求的核心**）

- **必须**存在结构性判据：新增一个客户类出口而没接管线时，**测试立刻红**
- 允许的实现方式（至少一种，Dev 选并说明）：
  - 类型层：客户类渲染只能返回一个**只能由管线构造**的包装类型（构造器私有）
  - 或 源码层：枚举全部客户类写出点，断言每个都经过管线（**否定式断言**：「除管线外全仓无第二处 `scan_modeling_terms` 直调」）
- ⛔ **不许只写正向判据**：「这三个文件调了共享函数」这种断言**钉不住**「保留共享调用、另加一份本地判据」（QA 变异 M3 已实证 9 条全绿）
- **变异验证**（纪律 G）：把某个出口从管线摘掉，判据必须红，并贴三元组（变异后二进制 sha256 + patch 内容 + 逐条结果）

### AC-004 · 三个卡点逐个裁定（选定 + 理由 + 被放弃方案的代价）

| 卡点 | 必须回答 |
| --- | --- |
| ① 改名口径 | JSON 出口是否也做 `strip_id_token`？选「统一改名」还是「JSON 保持原名」？**被放弃的那一种会漏什么** |
| ② 闸粒度 | 统一到「整份」还是「逐节点」？选哪个，**另一个会漏什么**（整份 ⇒ 一个坏节点废整页；逐节点 ⇒ 跨节点上下文泄漏） |
| ③ stderr 报告 | 统一报告形状；另外 `cli.rs:1243-1247` **全量打印被剔除的原名**，与 `html_view.rs:486-489`「只报数量不报原名」口径矛盾 —— 选哪个 |

⚠ 三个卡点**任一个没裁定**，就等于静默改输出 ⇒ AC-005 直接不算通过。

## 七 · 修订（QA 生成用例后发现的 4 个 AC 缺陷，BA 已裁定）

> 来源：`test-cases/coverage-map.md` 附录 D。**QA 抓得对，这 4 条都是本 AC 自身的问题**，
> 按纪律 S（AC 自己也会是错的）在此修订，**不改历史结论，只追加裁定**。

### A1 · 计数闭合：34 ≠ 33，差的是 Z4

§一 13 + §二 4 + §三 8 + §四 9 = **34**，与口径 D 的 33 差 1 —— **差的是 Z4**（`INDEX_HTML` 模板）。

**裁定**：**Z4 不是出口**（它不「写出」，只是被渲染函数读取的静态素材），**不占出口位**。
⇒ 33 = 客户 13 + 建模 8 + 内部 9 + Z1 + Z2 + Z3。
⇒ §二 标题里的「4」应读作「4 个零闸位点」，其中**只有 3 个是出口**。

### A2 · AC-005 与 AC-006 冲突 → Z1 是**唯一允许的可见变化**

AC-006 要求 Z1 的 400 响应体**必须变**（不再回显项目名），而 AC-005 要求**零可见变化**。**两条并存时 AC-005 不可执行。**

**裁定**：
- **Z1 的响应体变化是 AC-006 的验收对象，不是 AC-005 的违反**。
- AC-005 的 golden 比对**必须显式排除 Z1**，并在交付物里给出 Z1 的「变化前 / 变化后」逐字登记。
- 除 Z1 外，任何其它出口的可见字节变化都算 AC-005 不通过。

### A3 · 既有测试必须**改写**，不许删除

`tests/test_property_filter.rs:341` 的 `all_three_outlets_call_the_one_shared_function` 断言三个出口文件里 `contains("property_filter::filter_view")`。收口后**必然转红**。

**裁定**：**改写，不许删**（删了就违反 AC-009 的「不许删除测试」）。
改写方向：把它换成同一套**否定式**判据（「出口文件里对该判据的直调点数为 0 / 全部经由管线」），并保留它原本钉住的「三处共用一个函数」这个意图。

### A4 · 与 REQ-103 的边界：两个否定式断言**各管一段**，不重叠

`src/domain/property_filter.rs:139` 写着 M3 加固「已划走 REQ-103」，与 AC-003 要求冲突。

**裁定**（责任边界）：
- **REQ-107 的 AC-003** 管：**客户类写出口不得直调判据**，必须经由管线。这是**出口侧**的不变量。
- **REQ-103** 管：`has_raw_identifier` 的**多份实现**问题（属性剔除判据本身被抄第二份）。这是**判据侧**的不变量。
- 两者**可以同时存在**，且判据形态相近（都是否定式计数），但**针对的文件集合与目标不同**。
⇒ Dev 做 REQ-107 时，**允许**在 `property_filter.rs:139` 加一句「出口侧的对应守卫见 REQ-107 AC-003」，**不许**把那段已有的自陈改写成「已封堵」。

### A5 · 两个基线 commit 不是矛盾，是两个口径

- **全量测试基线** `7f26fa2`（纪律 O 的 `62/846/0/1`）—— 是 **REQ-106 合并前**那次全量实测的锚点。
- **本需求代码基线** `b714f48`（REQ-106 合并后的 develop tip）。

**裁定**：交付物必须**分开写**：代码基线 `b714f48`、全量基线 `7f26fa2`（并声明本机不可复核）。**不许**把两者混写成一个数字。

### A6 · AC-003 的「类型层」用 `compile_fail` doctest

本仓**没有 `trybuild`**，新增依赖不在本需求范围。

**裁定**：类型层判据允许（且建议）用 `compile_fail` doctest + `cargo test --doc` 实现 —— 它只编 lib，**本机可跑**。Dev 若选这条，必须在交付物里贴 `cargo test --doc` 的实际输出。

### A7 · 派单陷阱（QA 已实测，Dev 必须遵守）

1. **新测试文件不要加** `//! @guard-manifest: REQ-081` 标记 —— 否则 `tests/test_guard_manifest_req081.rs:904` 立刻红（除非同步改那套基线，而那超出本需求范围）。
