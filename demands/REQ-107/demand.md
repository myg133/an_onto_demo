## 需求描述

### 问题不是「功能缺失」，是「出口没有单一收口」

同一份客户视图今天要从**多个出口**出去（CLI JSON、HTTP `/api/node`、MCP 工具结果、HTML 页面……），每个出口**各自决定怎么呈现**。后果已经发生过两次：

1. **REQ-104 事故**：HTML 出口早就做了属性级剔除（`exit 0`），JSON 与 `/api/node` 没做 ⇒ **同一份数据，两种结果**，3 个节点返 500。
2. **REQ-106 事故**：守门器 `guard()` **靠调用方自觉**在出口前调用 ⇒ 漏一个出口就漏一道闸；且 JSON 出口是「**先写出去、后判定**」，闸门对 stdout 形同虚设。

⇒ 真正的病根是：**「要不要剔除 / 要不要清洗 / 要不要拦」这件事，分散在每个出口里重新决定了一遍。**

### 目标（结构目标，不是功能目标）

把「渲染前的处理」与「发布前的闸」从各出口**收进一条管线**：

```
加载一次 → 统一前处理（剔除 + 清洗/改名）→ 统一发布闸（守门器）→ 按出口声明的格式写出
```

出口层从此只声明「我要哪种格式」（JSON / HTML / 文本 / MCP 结构），**不再自己决定要不要过闸**。

### 为什么现在做

- v2 要加推理层与远程 MCP，**出口数量只会增加**。每加一个出口就多一次「忘了接」的机会，而这类漏洞**测试抓不到**（漏接的那条出口根本没有测试会红）。
- 这是 v2 规划里唯一一个「**越晚做越贵**」的改动：出口越多，收口时要改的调用点越多，回归面越大。

## 范围

### 做

1. **枚举并分类全部出口**（外部客户 / 建模 / 内部），作为收口的输入清单 —— 已独立派 explore 完成，清单进入 `acceptance.md`。
2. **管线本体**：一个「加载后再统一处理」的入口，出口只声明格式。
3. **把现有出口接到管线上**，且**不漏任何一个**（漏接必须能被测试抓到，见 AC）。
4. **口径统一**：`filter_view`（剔除）与 `sanitize_display`（清洗 + 改名）目前口径不同，收口时必须**显式决定**保留哪一种、以及在哪些出口上生效，**并写清理由**。
5. **守门器粒度统一**：`guard()` 目前是「整份 JSON 全文扫」，而某些出口是「逐节点」，这个差异**零测试覆盖**且已在 `src/domain/property_filter.rs` 自陈登记为已知限制 ⇒ 本需求必须给出裁定（统一到哪一种、为什么、以及被放弃的那一种会漏什么）。

### 不做

- ⛔ **不改 `mcp::tools::guard()` 的内部实现**（纪律 H：不许新写一份守门器判据，只许复用与收口调用点）
- ⛔ **不动红线四文件**：`tests/drop_rate.rs`、`tests/test_fk_naming.rs`、`src/domain/view.rs`、`src/domain/review_view.rs`
- ⛔ **不改客户视图的内容口径**（本需求是结构收口；输出若发生**可见**变化，必须在交付物中逐条列出并给出理由）
- ⛔ **不新增业务功能**（不加新出口、不加新字段、不改 MCP 工具语义）
- ⛔ **不顺手修** REQ-105（`english_term_hit` 汉字前缀问题）等其它已登记缺陷

## 三个已知卡点（探查明确列出，**不可一步到位**）

| # | 卡点 | 为什么不能无脑合并 |
| --- | --- | --- |
| 1 | `filter_view`（剔除）与 `sanitize_display`（清洗+改名）**口径不同** | 直接收口会**静默改变 HTML 现有输出**。必须先裁定谁是「客户出口的正确形态」 |
| 2 | `guard` 的**整份 vs 逐节点粒度不同**，且该差异**零测试覆盖** | 统一到整份 ⇒ 可能过度拦截（一个坏节点废掉整页）；统一到逐节点 ⇒ 可能漏掉跨节点的上下文泄漏 |
| 3 | 各出口的 **stderr 报告内容各异** | REQ-106 已规定「诊断一律走 stderr」，但各出口报什么不一致；收口要定一个统一报告形状，否则「统一」只是换了写法 |

## 验收方向（AC 待 explore 输出后定稿）

本需求的历史教训（纪律 S）：**上一轮 REQ-107 的 AC 曾出现「判据写下前就不成立」「空转比对」「声称修好了其实没建防护」**。因此：

- ⛔ **AC 不许凭印象写**。必须先有 explore 的出口清单（`path:line`）才动笔。
- ✅ AC 的核心应该是「**漏接一个出口时，门禁必须立刻红**」，而不是「新管线看起来更整齐」。
- ✅ 每条 AC 必须能被一条命令或一个测试证伪。

## 交付物

1. **出口清单与收口映射表**：每个出口 `path:line` → 它在管线里的位置 → 它声明什么格式
2. **管线设计**：类型/函数签名 + 为什么这样切（尤其是「前处理」与「闸」为什么分开）
3. **三个卡点的裁定**：每个卡点给出「选哪一个 + 理由 + 被放弃方案的代价」
4. **漏接即红的证据**：新增出口（或删掉某个出口的接线）时，**哪些测试会红**，贴出实测
5. **输出变化清单**：若可见输出有任何变化，逐条列出（出口 / 变化前 / 变化后 / 理由）；若无变化，明说「零可见变化」并给出比对方式
6. **全量测试数字** + 口径 + 失败清单（基线不许下降）
7. `git diff --numstat` + 红线零触碰证据
8. **已知限制**：本需求**没有**做什么（如实列，例如某些内部出口不在本轮范围内）
9. **对本需求的异议（无则写「无」）** —— 特别是：若你认为「三个卡点里有哪一个不该在本需求解决」，说明理由，由需求方（BA）拍板
