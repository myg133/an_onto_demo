## 背景

本项目的核心赌注是「**人比 LLM 更会定义，LLM 更擅长发现**」——
让人凭空写出对象类型他写不出来；给他一份候选，他一眼能说「这不对，我们管它叫 XX」。

**这个赌注至今零验证。** 现有实现计划（3625 行）覆盖的全是确定性工程
（版本、diff、审核状态机、投影），而核心赌注在第 2 份计划里一行代码没写。

> **治理机制救不了客户不认的本体。**
> 如果 LLM 抽出来的东西客户判断不了，那么版本冻结、双轨审核、证据链、mcp-server
> —— 全部是在治理一个不存在的东西。

## 用户故事

作为**项目负责人**，我需要用一张真实客户库验证「LLM 抽出的候选本体客户认不认」，
以便**决定是否投入内核开发**。

## 功能要求

1. 读取一张**真实客户**的 PG / MySQL：schema + 每表 N 行脱敏样本
2. 按表分组调用抽取能力（接外部 A2A agent，或直接调模型 API 验证）
3. **代码验证每条证据**：声明的表 / 列是否真实存在
4. 跨表合成判断：`t_dev` / `t_device_info` / `dev_backup` 是不是同一个东西
5. 产出**两张判读表**

## 非功能要求

- **不碰生产库**：只读，禁止任何写操作
- **不建本体内核**：一次性脚本，跑完即弃
- **样本必须脱敏**：涉及客户数据出域的，按设计规格 §4.2 处理
- **限时 2 天**：超时就说明问题复杂度被低估，需重新评估

## 明确不做

- 不写本体内核代码
- 不做审核界面
- 不做采集器容器化
- 不追求工程可维护性

## 交付物

| # | 产物 | 判读标准 |
| --- | --- | --- |
| 1 | **幻觉率对照表**：LLM 提了什么 vs 代码验掉了什么 | 被验掉的比例 < 30% 可继续；> 50% 说明抽取质量不可用 |
| 2 | **跨表合成判断表**：`t_dev` / `t_device_info` / `dev_backup` 该合并还是分开 | 人工判读 LLM 的建议是否正确 |
| 3 | **候选本体一页纸**：类型 + 属性 + 证据 | **拿给客户看，他能否一眼判断对错** ← 这是核心判据 |

## 决策出口

| spike 结果 | 下一步 |
| --- | --- |
| 候选本体客户能一眼判读 | 启动内核重写（Rust），按设计规格 §0.2 |
| 客户判读不了，但证据链清晰 | 调整 prompt / 增加领域提示，再跑一轮；仍不行则重新评估 §2.3 前提 |
| 幻觉率过高（> 50%） | **停下**。重新评估「抽取结构」这个核心假设是否成立 |
| 跨表合成判断不可靠 | 该能力不外置，自研阶段 3（这会改变 §7.1 的边界，需回改规格） |
