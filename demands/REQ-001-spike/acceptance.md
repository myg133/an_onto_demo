# 验收标准：REQ-001 抽取可信度 spike

## AC-001 · 能读到真实 schema 与样本

- 前置条件：拿到一张真实客户库的只读连接
- 测试步骤：
  1. 导出全部表的 schema（表名、列名、类型、可空、主键、注释）
  2. 每表采样 N 行，**脱敏后**落盘
- 预期结果：schema 完整、样本可读、无 PII 残留
- 类型：功能

## AC-002 · 候选本体每条带机器可验证的证据

- 前置条件：完成一次抽取调用
- 测试步骤：对每条候选类型 / 属性，核对其声明的来源表 / 列是否真实存在
- 预期结果：产出**幻觉率对照表**（提了什么 / 验掉了什么）
- 类型：功能

## AC-003 · 幻觉率在可接受区间

- 前置条件：AC-002 完成
- 预期结果：被代码验掉的候选比例 **< 30%**
- 类型：功能
- **不通过的处理**：> 50% 则整个 REQ 判负，触发 `demand.md` 的「决策出口」

## AC-004 · 跨表合成判断可被人工判读

- 前置条件：抽取涉及多张语义相近的表
- 测试步骤：让 LLM 判断 `t_dev` / `t_device_info` / `dev_backup` 是「3 个类型 + 关系」还是「1 个类型」
- 预期结果：产出判断表，且**人工判读其结论是否正确**
- 类型：功能

## AC-005 · 候选本体一页纸可被客户一眼判读 ← **核心判据**

- 前置条件：AC-002 / AC-003 / AC-004 完成
- 测试步骤：把一页纸本体（类型 + 属性 + 证据）交给客户业务人员，问「这些是你们说的东西吗」
- 预期结果：客户**能明确指出哪里对、哪里不对**
- 类型：功能

> **AC-005 是这个 REQ 的全部意义。** 前四项都是过程指标，只有它回答了「核心赌注成不成立」。
> 若客户看一眼说「还行」但指不出具体哪里错，等同于不通过 —— 那说明抽取没有真正降低他的认知负担。

## AC-006 · 全程只读、不碰生产

- 前置条件：全程
- 测试步骤：检查数据库连接串是否为只读账号；检查脚本无写操作
- 预期结果：无任何写入
- 类型：安全

## AC-007 · 限时 2 天

- 前置条件：开工时刻
- 预期结果：2 个工作日内产出 AC-002 / AC-003 / AC-004 三张表
- **不通过的处理**：超时说明问题复杂度被严重低估，须记录并重新评估投入
