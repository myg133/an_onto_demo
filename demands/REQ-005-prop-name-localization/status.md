## 2. 根因：不是词表缺词，是「注释优先且排他」

**两处代码合谋**，缺一不可：

| 位置 | 修复前 | 问题 |
| --- | --- | --- |
| `src/extract/propose.rs:236` | `let name = comment.clone().unwrap_or_default();` | 任意非空注释直接当属性名，**无质量门槛** |
| `src/domain/view.rs:342` | `if p.name.trim().is_empty() { humanize_column(...)? } else { p.name.clone() }` | 词表**只在 name 为空串时**才被问 |

所以「注释优先」实际是「注释优先**且排他**」。词表里 `license → 授权`、
`COLUMN_LABELS` 里 `license_id → 所属授权` 都在，只是**永远没机会出手**。

**独立验证**：扫 `schema.json` 全部 681 条注释，「一个汉字都没有」的**恰好 8 条**，
与清单逐条吻合 —— 爆炸半径就是这 8 条，没有第 9 条。

## 3. 修法

### 3.1 注释质量门槛（`propose.rs::classify_comment`）

三档总闸：

| 档 | 判据 | 动作 |
| --- | --- | --- |
| `HumanReadable` | **有一个汉字** | 照用 |
| `EnumDomain` | 无汉字，但是**合法枚举值域形态** | **有意不翻**（类 B） |
| `LowQuality` | 无汉字、且不是值域 | `name` **和 `note` 一起**置空 → 回退词表 |

**判据只看「有没有汉字」，不看占比。** 这与本项目反复验证的「**词表是枚举、形态是判定**」同一纪律。

> 按占比设 0.5 门槛会**大面积误杀**合法注释 —— 实测占比：
> `状态 rech:成功 pending:支付中 free:取消` = 0.40、`用户类型 个人:person 公司:Corp` = 0.44、
> `商品状态:active-启用,inactive-停用` = 0.36。这些是中文人话，只是习惯把英文常量贴在中英文后面。
> 占比门槛会把它们赶去词表（多半认不出 → 丢属性），等于**制造**了新问题。变异 M4 专门钉死这点。

**「合法枚举值域」的判法也是形态不是词表**：按 `/ , ; |` 切成 **≥2 个裸值原子**
（无空白、只含标识符字符），先剥 `0:` 这类编码前缀。
`processing/charged/failed` ✓、`0: llm, 1: emb` ✓；`license key`（含空格、切不成 2 段）✗

**`note` 一起置空是 BA 追加的判断**（Dev 原始要求只提属性名）：
否则 `name` 修好了，同一段英文从 `note` 字段原样绕回客户视图。
有测试 `test_low_quality_comment_does_not_leak_through_note` 钉住。

### 3.2 词条补齐（`a9e197f`，BA 复核后追加）

Dev 的修复（`6eae1b1`）把零汉字属性名降到 2，但**类 A 5 处只成了 3 处**：
`session_id` / `customer_quota_policies` 因词表无对应词根 → 回退 `None` → **属性被丢弃**。

**其中 `session_id` 是词表真实缺词 → 补。** `session_id → 会话` 是语义映射，
**没有任何形态规则能推出来**。已补 `session`/`policy`/`policies` 三条（`a9e197f`）。

> ⚠️ **BA 的 briefing 有误并已纠正**：BA 写的「不要走加词条回头路」针对的是
> **形态能解决却用词表打补丁**（词表 `create_time` 配不上库里 `created_at`）。
> Dev 严格遵守，结果做出次优解。代价是客户视图少一项。**规则被套用过头了。**

**`customer_quota_policies` 本轮不补**：它是**复合词**（customer+quota+policies），
补 `policies` 单个词根救不了 —— `humanize_column` 只有「剥技术后缀后查词根」和「整词查」两条路，
都覆盖不到多词拼接。且它本身是内部 JSON 配置字段，对客户判读价值低。

## 5. 遗留问题

### 5.1 词表缺口是系统性的 —— 147 种词根 / 169 个列

扫真实库（91 表 / 1051 列）**无注释且词表翻不出**的：

| 类型 | 例子 | 性质 |
| --- | --- | --- |
| `*_at` 时间形态 | `expire_at` / `effective_at` / `locked_at` / `start_at` | **形态问题**，可规则化 |
| `*_count` 数量形态 | `retry_count` / `hit_count` | **形态问题** |
| `*_by` 形态 | `locked_by` / `cleared_by` | **形态问题** |
| **真缺词** | `payload` / `billing_cycle` / `timezone` / `content` / `batch` / `auto_renew` | 需加词条 |
| **复合词** | `customer_quota_policies` | 需复合词拆分能力 |

**根因是词表没有通用形态处理器。** REQ-002 时是照中文 demo fixture 手工编的，
真实库的英文词根没覆盖全。

> **建议下一轮做「形态/复合词处理器」而不是继续加词条** ——
> 147 个词条手工补是打补丁，`*_at`/`*_count`/`*_by` 三个形态处理器能一次覆盖大半。

### 5.2 守门器看不见属性名（**fail-open**）

`scan_modeling_terms` 的第四档只看 `meaning` 字段的值。
`license key`（`key` 因 `license` 在白名单被放行）和 `SessionId`
都能**通过全部四档守门、退出码 0**。

已写成**刻画测试** `test_runtime_guard_is_blind_to_english_property_names`，
注释里写明：*「若它变红说明守门器补上了这一层，请重新评估抽取层的降级策略是否还该保留」*。

> **含义：这次修复是「主动识别」（抽取层质量门槛），不是「被动拦截」（守门器）。**
> 抽取层再漏一个英文，守门器抓不到。
> 建议下一轮加一档「属性名完全没有汉字」—— **与抽取层门槛同口径**，
> 不能用「含 ASCII 就抓」（会误伤「API端点」这类中英混排）。

### 5.3 `props_dropped` 死字段（承自 REQ-003）

声明并序列化但**从未自增**，恒为 0。本需求里**有实际后果**：
2 个属性真的被丢弃（`customer_quota_policies`），统计却显示 `props_dropped: 0`。
**丢弃行为不可见。** 建议下轮修（改成真统计，或删字段）。

### 5.4 `_id` 后缀的 tail 是空

`license_id` 靠 `COLUMN_LABELS` 特例拿到「所属授权」，但其他未映射的 `*_id`
翻出来是**裸词**：`provider_id` → 「服务商」（不是「服务商编号」）。
要拿到「X编号」得改 `_id` 的 tail（影响所有未映射 `*_id`），本轮未做。

### ⚠️ 但我修正了自己之前的判断

BA 此前说「51 条全标 `N:1`（多对一），零外键下**大概率标反了**，客户视角应该是 `1:N`」。

**这个判断是错的。** 判据：外键在 `from` 表 ⇒ 「多条 `from` 记录 → 一条 `to` 记录」
⇒ `from` 是「多」的一侧 ⇒ **`N:1` 标注正确**。

真正的问题不是**基数标错**，而是**基数挂在哪一端没向客户说清**：
客户自然问法是「一个 X 有几个 Y」——「一个客户有几条 API 调用日志」，
答案的方向是 `1:N`，而视图里写的是「API 调用日志 **多对一** 客户」。

> **所以 Q5 问「A 对 B 是一个还是一个多个」可能问错了方向** ——
> 客户要答的其实是「**A** 有几个 **B**」，跟我方记录的 `N:1`（B 有几个 A）是**反的**。
>
> **建议改 Q5 的问法**：不抽象问「基数」，而是**具体问**「**一个 A，对应几个 B？**」，
> 并让评审人回答**从 A 出发**。这样答出来的结果才能和视图里的标注对齐。
> 判读手册需要相应改一处。
