# 验收标准：REQ-111 · 本地审核界面

> **前置**：REQ-110 已合并（页面可达性 + TTL 导出）
> **基线**：`develop`（REQ-110 合并后）

## 一 · AC

### AC-001 · 只绑回环，非回环拒启动

- `--bind 0.0.0.0:8788` ⇒ **exit≠0**，文案说明只允许回环
- `--bind 127.0.0.1:8788` ⇒ 正常
- 判据：两种绑定各跑一次

### AC-002 · 只服务**未冻结**提案

- 对已冻结版本启动 ⇒ **exit≠0**，文案点名「v2 已冻结」
- 判据：先用 `version freeze` 造一个冻结版本

### AC-003 · 写接口必须鉴权

| 请求 | 期望 |
| --- | --- |
| `GET /api/review` 无 token | 401 |
| `POST /api/decide` 无 token | 401 |
| 带正确 token | 200 |

### AC-004 · 决策走**同一个领域函数**

- `POST /api/decide {item:3, track:"biz", decision:"accept"}` 之后，`ontok review show` 里该条必须显示 `biz=accepted`
- 判据：**页面签一条 ⇒ CLI 读得到**；反向（CLI 签、页面读）也要一致
- ⛔ 不许 HTTP 层直写 SQL（代码审查项：写路径必须与 `review decide` 共用函数）

### AC-005 · 幂等覆盖

- 同一 `item+track` 连签两次（accept → reject）⇒ 终态是 reject，**不报错、不产生两条记录**
- 判据：连签后 `review show` 只反映最后一次

### AC-006 · 批量签有预览

- 批量入口必须**先显示将影响多少条**，确认后才执行
- 判据：构造 10 条未签，点批量 ⇒ 页面显示「将接受 10 条」；HTTP 层批量接口若存在，必须带 `items[]` 白名单，⛔ 不许「一键全库」

### AC-007 · 失败必须可见

- 对已冻结版本发决策 ⇒ 页面显示具体原因（不是「失败」两个字）
- 判据：构造冻结 + 提交，断言响应体含原因、HTTP 非 2xx

### AC-008 · 与 `serve` 完全隔离

- `serve`（只读）**一行未改**：`git diff` 里 `serve` 的路由与 middleware 无改动
- 判据：`POST` 到 `serve` 的端口仍返回 **405**

### AC-009 · 审计可区分来源

- 每条决策记录 `decided_at` 与 `via`（`cli` / `ui`）
- 判据：页面签一条后查库，`via = "ui"`；CLI 签的为 `"cli"`

### AC-010 · 不退化

| 项 | 约束 |
| --- | --- |
| ⛔ 禁改 | 四红线 + `tools.rs` + `guard()` + `property_filter.rs` G1–G4 |
| ⛔ 禁 | 删测试、`#[ignore]`、放宽断言、新增依赖 |
| 基线 | REQ-110 合并后的 lib/doc/套件数字，一条不许少 |

## 三 · Dev 交付后的裁定

### A-1 · `src/review_ui/` **不进** `OUTLET_FILES`（接受，但有条件）

Dev 指出的冲突：新增目录 `src/review_ui/` 没有进 REQ-107 的 `OUTLET_FILES`，所以 **T5**（每个 fn 必须登记）/ **T9**（`Json(`/`Html(` 必须是管线产物）**不扫它**。

Dev 的理由：**若纳入，T9 立刻红**——审核界面的 JSON 是「审核对象本身」，不能过客户发布闸。

**裁定：接受这个口径。** 但必须写清「为什么不是漏网」：

| 覆盖项 | 是否覆盖 `review_ui` |
| --- | --- |
| **T1**（`src/` 全目录写点枚举） | ✅ 覆盖 |
| **OUTLETS 登记** | ✅ 已登记 R1–R5（`Internal` 轨） |
| `outlet_sources` 对账 | ✅ 纳入 |
| **T5 / T9** | ❌ 不覆盖——**这是有意的**：T9 的语义是「客户出口必须是管线产物」，而审核界面**不是客户出口** |

**条件（QA 必须独立验证）**：

> `src/review_ui/` 里**不得出现任何 customer-track 输出调用**：
> `publish_customer` / `Product::CustomerTurtle` / `Product::CustomerJson` 等，调用数必须为 **0**。

⛔ 若为 0，「T9 不扫」就不构成漏网；若不为 0，说明它真在往客户轨输出，**必须纳入**。

⚠️ **登记为已知限制 G6**：**没有判据钉住这条「调用数为 0」**（只能靠 grep 复核）。下一轮应补一条否定式断言。

### A-2 · 批量没有原子性（接受）

页面批量 = 逐条 `POST /api/decide`（HTTP 层**没有**批量接口，所以「一键全库」在协议上表达不出来）。
代价：中途失败会停在半条并显示原因，**没有事务回滚**。

**裁定：接受。** 理由：审核决策本来就是**逐条语义**，「半途停下并说清停在哪」比「整批回滚」更符合审核场景——回滚会让已经看过并签过的条目状态退回，反而更难解释。

### A-3 · 耗时口径必须如实

Dev 报 **CLI 59.59s vs 页面路径 7.69s（7.75×）**，并注明「无 headless 浏览器，『页面』= 270 个 HTTP 请求的墙钟，不含渲染与人手点击」。

**裁定：口径成立，但交付说明里必须原样保留这半句**。⛔ 不许简化成「页面比 CLI 快 7.75 倍」——那会让人以为包含了人的操作时间。
