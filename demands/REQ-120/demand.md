| 项 | 值 |
| --- | --- |
| 需求编号 | REQ-120 |
| 优先级 | **P0**（替身实验证明：补上它，端到端答对从 1 条变 4 条） |

| 基线 | `develop`（REQ-119 合并后） |

## 问题（替身实测）

只读 TTL 的替身 Agent 写 5 条 SPARQL，结果 4 条方向对、**只有 1 条能交付客户**。它列的根因：

| # | 现象 | 后果 |
| --- | --- | --- |
| 1 | **5 个类 0 个 ObjectProperty**：`api_call_logs` / `package_products` / `service_config` / `llm_model` / `customer_account_binding` | 「按授权算用过哪些 API」走不通 |
| 2 | **FK 列是裸字符串**：`product_id` / `model_id` / `service_id` / `main_customer_id` / `sub_customer_id` | 无法 join，无法两跳 |
| 3 | 同一个 `license_id`，在 `deductions`/`usage_details` 是边，**唯独 `api_call_logs` 不是** | 不一致，Agent 会以为「这张表没有授权关联」 |

**根因**：抽取阶段的 `*_id` → 表名匹配**太严**：

```
product_id  → 找表 products  ✗（实际表叫 package_products）
model_id    → 找表 models    ✗（实际表叫 llm_model）
service_id  → 找表 services  ✗（实际表叫 service_apps）
```

## 目标

把「按列名严格匹配」升级成「**候选生成 + 证据打分 + 可评审**」：

```
每个 *_id 列
   ↓ 候选生成（宽松）
   表名包含 stem / 后缀匹配 / 单复数 / 注释提到「指向X表」
   ↓ 证据打分
   ① 名字相似度
   ② 列注释是否提到候选表
   ③ ★ 值域重叠（采样验证）：该列的样本值有多少落在候选表主键里
   ↓ 提案（ADR-005 形状）
   claim / evidence / confidence / reason / reviewed_by
   ↓ 人签
   进入本体 + TTL（带 ontok:joinVerified 与证据）
```

**为什么要「值域重叠」**：这是最强的证据。`api_call_logs.license_id` 的样本值若全在 `licenses.id` 里，那几乎肯定是 FK；若只有 10% 命中，那是同名不同义。

## 范围

### 做

1. **候选生成**：宽松匹配（子串/后缀/单复数/注释提示），产出候选集（通常 1–3 个）
2. **值域重叠采样**：复用 REQ-108 的只读采样设施，对 `列值 ∩ 候选表主键` 算命中率
3. **提案输出**：每条关系带 `claim/evidence/confidence/reason/decided_by/reviewed_by`
4. **落库与 TTL**：签过的关系进入本体；TTL 增加 `ontok:joinVerified "true|false"` 与 `ontok:joinEvidence`
5. **不臆造**：候选为空 / 命中率过低 ⇒ **不产出关系**（只进「未解析 FK 清单」）
6. **报告**：哪些 `*_id` 列仍未解析、为什么

### 不做

- ⛔ 不改 TTL 的结构（REQ-119 已完成）
- ⛔ 不改 R2RML（REQ-121）
- ⛔ 不引新依赖
- ⛔ 不做「跨库/跨 schema」推断

## 关键裁定

| # | 问题 | 裁定 |
| --- | --- | --- |
| R1 | 匹配策略 | **先宽松生成候选，再用值域重叠否决**。⛔ 不许只用名字相似度 |
| R2 | 命中率阈值 | ≥ 0.95 视为强证据（`confidence ≥ 0.9`）；0.5–0.95 中等（需人签）；< 0.5 **不产出** |
| R3 | 无 PK 的候选表 | 跳过（无法验证重叠），进「未解析清单」 |
| R4 | 一对一 vs 多对一 | 由**值唯一性**判：该列值在样本里唯一 ⇒ 1:1，否则 N:1 |
| R5 | 提案不权威 | 未签的关系**不进快照**（ADR-005 P2）；但要在报告里可见 |
| R6 | 性能 | 采样每列 ≤ 5 行、每候选一次查询；全库 96 表应在数十秒内 |

## 已知风险

| # | 风险 | 缓解 |
| --- | --- | --- |
| 1 | 值域重叠误判（同名同格式但语义不同，如两个 `customer_id` 指向不同系统） | 命中率阈值 + 人签 + 证据里带样本值 |
| 2 | 稀疏列（大部分 NULL）导致重叠率虚高或虚低 | 采样时跳过 NULL，样本数不足 ⇒ 标 `insufficient_sample` |
| 3 | 关联表（复合主键）无法验证 | 跳过并列出 |
| 4 | 候选爆炸（90+ 表两两比） | 候选生成限定名字相关 + 采样只做一次 |

## 交付物

1. 候选生成 + 值域重叠采样 + 提案输出
2. 真实库实测：**补出多少条关系**、其中多少是高置信、多少被值域否决
3. 5 个孤儿类（`api_call_logs` 等）**逐个交代**：补上了 / 未解析 / 为什么
4. 未解析 FK 清单
5. TTL 里的 `ontok:joinVerified` 与证据样例
6. **复跑替身实验**：Q3 / Q4 / Q5 是否从「写不出」变「写得出」
