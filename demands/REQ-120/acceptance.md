# 验收标准：REQ-120 · 关系推断改进（FK 边补全）

> **一句话**：每一条补出来的关系，都要有**数据证据**（值域重叠），而不是“名字像”。

## 一 · AC

### AC-001 · 提案形状（ADR-005）

- 每条候选关系输出为提案：`claim` / `evidence[]` / `confidence` / `reason` / `decided_by` / `reviewed_by`
- `reviewed_by` 初始 `null`
- `evidence` 至少含：匹配方式（后缀/包含/单复数/注释）+ **值域重叠的实测数字**（命中数/样本数）+ 样本值示例
- 判据：抽查 5 条，evidence 能让人独立判断真假

### AC-002 · 值域重叠是**硬证据**

| 命中率 | 处理 |
| --- | --- |
| ≥ 0.95 | `confidence ≥ 0.9`，标 `strong` |
| 0.5 – 0.95 | 中等，标 `medium`，必须人签 |
| < 0.5 | **不产出关系**，进「被否决」清单 |
| 样本不足（< 3 行有效值） | 不产出，标 `insufficient_sample` |

- 判据：构造一个「名字像但值域不重叠」的假 FK ⇒ **必须被否决**
- 判据：「被否决」清单里有条目（真实库应该会有）

### AC-003 · 5 个孤儿类逐个交代

| 类 | 要求 |
| --- | --- |
| `api_call_logs` | 补上 / 未解析 + 原因 |
| `package_products` | 同上 |
| `service_config` | 同上 |
| `llm_model` | 同上 |
| `customer_account_binding` | 同上 |

- 判据：每个类在真实库上给出**明确结论**，⛔ 不许模糊带过
- 特别验：`api_call_logs.license_id` → `licenses`（**同一个列名在 `deductions`/`usage_details` 已经是边**，这里不该例外）

### AC-004 · 1:1 vs N:1 按**值唯一性**判

- 采样该列的值，若在样本里**唯一**（等于行数）⇒ 1:1（`owl:InverseFunctionalProperty` + `FunctionalProperty` 双标）
- 否则 N:1
- 判据：REQ-119 QA 指出的 6 条（`balances.customer_id` 等 unique 列）应变成 **1:1**；其余保持 N:1
- 判据：反向属性同步（1:1 的反向也是 1:1）

### AC-005 · 未解析清单

- 报告必须列出**所有**未补出关系的 `*_id` 列 + 原因分类：
  - 无候选（名字不匹配任何表）
  - 命中率过低被否决
  - 候选表无主键（无法验证）
  - 样本不足
- 判据：清单里每行有列名 + 原因；⛔ 不许「静默跳过」

### AC-006 · 提案不权威（ADR-005 P2）

- 未签的提案**不进快照**
- 判据：不喂 `--relations`（或等价的签字产物）时，本体/TTL 里不出现新增边

### AC-007 · TTL 带证据

- 签过的边在 TTL 里带 `ontok:joinVerified "true"` + `ontok:joinEvidence "…"`
- 未验证的老边（名字推断）标 `ontok:joinVerified "false"` 或省略但**可区分**
- 判据：抽查两条，一条 verified 一条不 verified

### AC-008 · 不臆造

- 候选为空 / 候选表无 PK / 命中率不足 ⇒ **不产出**
- 判据：构造三例各一次

### AC-009 · 确定性与性能

- 同输入两次运行 ⇒ 提案文件逐字节相同
- 96 表全库运行在可接受时间内（目标 < 3 分钟）
- 判据：两次 sha256 + 计时

### AC-010 · 不退化 / 零依赖

| --- | --- |
| ⛔ 禁改 | 四红线 + `tools.rs` + `guard()` + `property_filter.rs` G1–G4 + `/api` 鉴权与路由 |
| ⛔ 禁 | 删测试、`#[ignore]`、放宽断言、新增依赖 |

### AC-011 · **复跑替身实验**（本需求的最终判据）

用补全后的 TTL 重跑 REQ-119 的 5 题实验（只读 TTL、只写 SPARQL、不执行）：

| 题 | REQ-119 时 | 本需求期望 |
| --- | --- | --- |
| Q1 扣费明细 | ✅ 可交付 | 保持 |
| Q2 余额 | ❌ | 不要求（是业务口径问题，非关系问题） |
| Q3 额度（说出产品名） | ⚠️ 说不出 | **应可说出**（`product_id` → `package_products`） |
| Q4 用过的 API | ⚠️ 只有绕路 | **应可直查**（`api_call_logs` 有边） |
| Q5 套餐下订阅 | ⚠️ 可写但跨租户 | 关系可写；跨租户口径另行裁定 |

- 判据：**Q3 + Q4 从「写不出/绕路」变「能直接写」**；Q1 不退化
- ⛔ 达不到就如实报告，不许说「基本达到」

### A-1 · E-1：join 目标应包含**唯一列**（不只是主键）

Dev 报 `llm_model` 未解析，理由是「`model_id` 是业务键（`kimi-k2.5`），5 个候选 0 命中」。

**BA 判断：不是候选错，是 target 选错。**

> `api_call_logs.model_id = 'kimi-k2.5'` 要 join 的是 **`llm_model.model_id`（唯一列/业务键）**，不是 `llm_model.id`。

⇒ 候选目标改为 `primary_key` ∪ `unique_columns`（96 表里 95 张有唯一索引信息）。

### A-2 · E-2：新增次级证据 `inherit`

`api_call_logs` 源库 0 行 ⇒ 值域重叠无从验证。但 `usage_details.license_id` 已验证 4/4。

⇒ 允许**同名同义列继承**，但必须满足全部条件：同名列、候选唯一、confidence 0.60–0.75、evidence 写明继承来源、**必须人签**。

**三态必须分清**：

| 值 | 含义 |
| --- | --- |
| `true` | 值域重叠实测通过 |
| `inherit` | 同名同义列继承（有验证来源，本表未实测） |
| `false` | 仅名字推断 |

⛔ 不许把 `inherit` 标成 `true`——**那等于把「别人验过」冒充「这张表验过」**。

### A-4 · 一条值得记的观察

**Q4 的失败根因是数据（源库 0 行），不是判据。** 这印证了一个原则：

> **验证不了的，就不要假装验证过。** 但也不能因此丢掉结构上存在的边——**用`inherit` 明确标注「没实测」比偷偷标 `true` 诚实得多。**
