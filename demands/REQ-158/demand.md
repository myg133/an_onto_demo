# REQ-158 · 修 fail-open：客户视图 TTL 的英文语义能过闸

- 状态：**已就绪**（hotfix 级）
- 提出：2026-10-27
- 来源：REQ-156 期间实测发现（Dev 用探针定位到行号）
- 类型：**安全/正确性** —— 客户能拿到未翻译的内部标识符

---

## 一 · 一句话

有一条"**漏翻即拒绝发布**"的守卫，但它**只认 JSON 形状**，对 **TTL 形状是盲的** ⇒ 13 个英文动词（14 行）**经闸放行**，进了客户视图。

---

## 二 · 证据链（Dev 实测，含行号）

| 环节 | 位置 |
| --- | --- |
| TTL 渲染 | `src/query/ttl.rs:202` |
| 发布闸 | `src/console/ops.rs:493-499` → `src/domain/pipeline.rs:997-1003` `gate_text(spec, doc.body())` → `pipeline.rs:1080-1088` `scan_modeling_terms` |
| 第四档判据 | `src/domain/view.rs:1073-1078` → `meaning_values`（`view.rs:1007-1009`）**只找 JSON 键 `"meaning"`** |

**探针实测**：

```
scan_modeling_terms(r#"rdfs:comment "语义：applies_to（多对多）"@zh ;"#)      ⇒ []          ← 漏
scan_modeling_terms(r#"{"meaning":"applies_to"}"#)                            ⇒ ["未翻译…"]  ← 抓到
```

⇒ **守卫在，但看不见 TTL 形状。这是 fail-open。**

---

## 三 · 要做

| # | 做什么 | 判据 |
| --- | --- | --- |
| ① | 把 `untranslated_semantic_hit` 的取数口径**扩到 TTL/HTML 形状**：识别 `语义：<token>` 里的 `<token>` 含 ASCII 字母 | 上面的探针 TTL 串 ⇒ **必须返回命中** |
| ② | JSON 形状判据**保持原样**（⛔ 不许因为改造而放过 `"meaning"` 那条） | 原探针仍命中 |
| ③ | 加回归守卫：**两种形状各一条正例 + 一条反例**（中文不误报） | 4 条断言 |
| ④ | 造一份含英文语义的客户视图 ⇒ **发布被拒**（点名那个值） | 端到端一条 |

## 五 · 为什么单独立单而不是塞进 REQ-156/157

| 理由 | 说明 |
| --- | --- |
| **性质不同** | 156 是"透出"，157 是"治理"，本条是**防线本身有洞** |
| **可独立验证** | 两条探针串就能红绿，不依赖任何数据改动 |
| **优先级最高** | 它是 fail-open（发错数据给客户），比"标签好不好看"严重 |
