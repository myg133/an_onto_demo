# 需求：REQ-137 · 本体模式下 token 不该被强制要求租户

## 基本信息

| 项 | 值 |
| --- | --- |
| 需求编号 | REQ-137 |
| 优先级 | **P1**（审计诚实性） |
| 状态 | 进行中 |
| 基线 | `develop` `d433108` |
| 触发 | 实际部署 Ops360 时撞到（REQ-136 漏掉的） |

## 问题（部署时实测）

```
✗ token 表不合法：missing field `tenant`
```

**根因**：`query` 的 token 结构把 `tenant` 当必填。而 **`--ontology-only` 模式根本没有租户概念**（没有业务库、SPARQL 恒 503）。

**现在的临时办法是填一个假租户**：

```json
{ "label": "partner-ops360（本体模式：无租户）",
  "token": "PARTNER-…",
  "tenant": "00000000-0000-0000-0000-000000000000" }
```

**后果**：审计日志里会出现 `tenant=00000000-…`——**看起来像一个真实租户，实际无意义**。

> 这是「假数据冒充事实」，和这套系统一直在防的"看起来对"是同一类问题。

## 要做

`tenant` 改为**按模式必填**：

| 模式 | token 里的 `tenant` | 行为 |
| --- | --- | --- |
| **普通模式**（有源库） | 必填 | 不变（缺 ⇒ 拒绝启动，现有行为） |
| **本体模式**（`--ontology-only`） | **必须不填** | 填了 ⇒ **拒绝启动**并说明原因 |

### 为什么"填了就拒绝"，而不是"忽略"

忽略会留下更坏的东西：**一个声明了数据范围、但范围不存在的 token**。
拒绝会逼人在 token 里写实话。

### 报错文案（要能照做）

```
✗ token 表 "…" 第 1 个 token 带了 tenant，但这是本体服务模式（--ontology-only）。
  本体模式**没有业务库、没有租户概念**，SPARQL 恒 503 —— 这里的 tenant 不表示任何数据范围。
  ⛔ 不要填假租户（例如全 0 UUID）：它会让审计日志里出现一个"看起来真实"的租户。
  请从 token 里删掉 tenant 字段。
```

## 不做

- ⛔ 不改普通模式的任何行为
- ⛔ 不改 token 的其他字段（`label` / `max_rows` / `max_concurrency`）
- ⛔ 不引依赖

## 关键裁定

| # | 裁定 |
| --- | --- |
| R1 | 普通模式：`tenant` **仍必填**（零行为变化） |
| R2 | 本体模式：`tenant` **必须缺省**；填了 ⇒ 拒绝启动（不是忽略） |
| R3 | 本体模式的审计行：`tenant=-`（明确"没有租户"，不留假值） |
| R4 | 报错文案必须说明「为什么不能填假租户」 |

## 风险

| # | 风险 | 缓解 |
| --- | --- | --- |
| 1 | 改结构后普通模式回归 | 用现有 anspire 快照对拍（84/70/8、293,814 B、5 行） |
| 2 | 部署侧现有 secret 带假租户 | 交付里给出「改 secret + 重启」的命令，并实测改完能起 |
| 3 | 有人为省事又填假租户 | R2 的拒绝 + R4 的文案 |

## 交付物

1. 模式感知的校验 + 文案
2. 普通模式回归证据
3. **部署侧实测**：把集群 secret 改成无租户 ⇒ Pod 起来 + 审计行 `tenant=-`
4. 已知限制
