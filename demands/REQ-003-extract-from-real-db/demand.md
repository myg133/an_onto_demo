## 1. 背景：为什么是现在

REQ-002（本体内核 MVP）在 2026-10-02 合入 `develop`（`723cc87`），两轮审核闭环。
内核已具备完整的只读治理闭环：**提案 → 双轨审核 → 冻结 → diff → 客户视图**。

但它**不含抽取**。REQ-002 范围规划明确写了「抽取与跨表合成属 REQ-002 之后的第 2 份计划」。

项目自诞生起就押在一个赌注上：**「LLM 能否从真实客户库抽出客户认得的本体」**。
README 原话是「下一步不是写代码，是跑 2 天 spike」—— 而这个 spike（REQ-001）
技术侧 6/7 通过，唯一卡住的 AC-005「客户判读」需要真实业务场景才能做。

**现在条件齐了**：内核有了，真实源库有了（2026-10-02 拿到 `<业务库名>`，91 张表）。
本需求把这两者接起来。

## 4. 验收标准

> 判定器扩展为 `BA/verify-req003.sh`，与 REQ-002 的 `verify.sh` 并列。
> **沿用 REQ-002 的教训**：判定器本身要有自测（`BA/verify_selftest.sh`，首轮审核 G-1 提出，本需求必须补上）。

### AC-101 · 只读保证（**安全红线，最高优先级**）

- 勘查器**只能**发 `SELECT`，且连接串必须带 `default_transaction_read_only=on`
- **不得**有任何 `INSERT`/`UPDATE`/`DELETE`/`DDL`/`TRUNCATE` 字面量出现在勘查路径
- 测试：注入一个会写库的函数 → 必须编译不过或被 grep 抓住
- **口径留痕**：产出 JSON 里必须记录勘查时刻的 `transaction_read_only` 实际值

### AC-102 · 勘查器产出完整 schema 元数据

- 91 张表全部出现，无遗漏
- 每表含：表名、列名、类型、**注释**、是否主键、是否可空
- 含 `column_count` / `commented_count` 统计（用于评估抽取质量）
- 判定：`jq` 断言表数 == 91 且每表列数 > 0

### AC-103 · 抽取器产出合法提案

- 产出必须是 REQ-002 的提案 JSON，能被 `ontok propose import` 接受
- 实体 `key` 用英文蛇形（与源库一致），`display_name` **必须中文**（否则触发 `usable_as_human_name` 全丢弃，见 §5）
- 关系两端必须都在实体集合内（否则 AC-007 拦截）
- 属性名必须 `humanize_column` 能翻（否则进不了客户视图）
- 判定：导入后 `ontok review show` 能列出全部条目

### AC-104 · 客户视图投影覆盖率达标

REQ-002 修复轮的评估显示**真实数据上只有 18% 覆盖**（200/1068 列）。
本需求要求：

| 指标 | 基线（REQ-002） | 目标 |
| --- | --- | --- |
| 属性投影覆盖率 | 18% | **≥ 60%** |
| 属性投影来源 | 仅硬编码词表 | **列注释优先**，词表兜底 |
| 实体存活率 | 场景 A 下 0% | 抽取产出必为 100%（display_name 全中文） |

- 判定：拿真实源库的 1068 列跑新投影，统计覆盖率，`< 60%` 判 `✗`

### AC-105 · 守门词不再误杀真实业务名

- `scan_modeling_terms` 改**词元精确匹配**，替代子串匹配
- 必须仍能抓住 S-3 回归点（`CARDINALITY` / `Key` 大小写绕过）
- 必须**不再**误杀 `License Key` / `API Key` / `keywords` 这类真实业务名
- 判定：正反两组用例各过一半才算数

### AC-106 · E2E 端到端（真实源库 → 冻结版本）

完整链路，一条命令可复现：

```
勘查真实源库 → 抽取本体 → 导入提案 → 双轨审核 → apply → 冻结 → 客户视图 → diff
```

- 判据：v2 冻结成功；客户视图**零建模术语**（复用 REQ-002 的运行时守门）
- 客户视图里对象数 > 0、**平均属性数 ≥ 3**（REQ-002 真实数据上只有 2.2）
- 冻结后再基于 v2 导入 → 必须报「base 已冻结」并非 0 退出

### AC-107 · LLM 抽取的可复现性

- 抽取必须记录 `extracted_by`（agent 标识 + **具体版本**），复用 REQ-002 的 AC-011/AC-014 契约
- 同一 schema 连续抽两次，产物差异必须能被 diff 解释（不是随机噪声）
- **不得**让 LLM 凭空造源库里不存在的实体（可机械核对：提案实体数 ≤ 源库表数）

## 5. 已知风险与前置结论

### 5.1 零外键是最大风险

91 主键、**0 外键**。关系只能靠命名约定（`*_id`）和语义推断。
且 `*_id` 不总是关系（可能是 JSON 字段、可能是日志 actor）。

**这是 REQ-001 spike 要回答的核心未知，本需求是它的实现。**
对应 AC-007「关系依赖两端」在真实数据上**无法机械验证**，只能信抽取器判断。

### 5.2 投影必须改，否则抽取白做

REQ-002 的评估已证明：抽取就算成功，客户视图里平均也只有 2.2 个属性、
15% 的对象一个属性都没有。**AC-013（客户 3 人判读）几乎必然失败。**
所以 AC-104（投影改进）不是可选项，是本需求能否验证成功的前提。

### 5.3 LLM 只看 schema 元数据

用户已明确授权边界：**发 schema 元数据（表名/列名/类型/注释/约束），不发任何数据行。**
本体结构本来就是从 schema 推的，这个边界对抽取影响有限。
但要注意：**零外键 + 无样本数据 → 关系推断准确率会明显受限**，AC-107 的「差异可解释」是兜底。
