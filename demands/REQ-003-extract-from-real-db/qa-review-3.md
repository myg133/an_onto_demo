### 1.3 结论：安全红线真的守住了吗

**守住了 —— 但要分两层说清。**

- **真实失守（N7）必然被抓住**：任何让勘查器**实际不再强制只读**的变异，都会在 `read_only_pool_really_reads_back_on` 上暴露（服务端读回 `off`）。这道行为层测试连 `#[cfg(test)]` 里的干扰都躲不过，因为它是真连库、真读回。**这与 R1 被两层抓住是同一回事：两层判据各管各的、都得留 —— 自述 2 的论证成立。**
- **接线层的盲区是真的**：N3 / N6 两种手法能让**接线层**判据全绿。根因是 `read_only_pool_fn()` 用「起点→终点」切文本区间，而不是解析函数边界；区间内的辅助函数、字符串字面量都会被算作「函数体」。**判据自曝的弱点（保留字符串字面量）在此变成了攻击面。**
- **严重性：定为「必须同批修」而非阻断。** 理由：① 生产代码此刻是**对的**（守卫确实以 `?` 强制，N7 实测证明行为层能兜住）；② 绕过需要「刻意插一个诱饵函数/字符串」——不是自然演进；③ 属于**防回归能力的缺口，不是现存缺陷**。但它与首轮 S1 / 复审 S1' 是同一个病的第三次同型复发（**判据有鉴别力但判不出「守卫是否真的在强制」**），且修法很便宜。

**低成本修法（叠加，不替换）**：把 `read_only_pool_fn()` 的「区间切分」换成**花括号配平**扫描 —— 从 `pub(crate) async fn read_only_pool` 之后开始数 `{`/`}`，到配平为止。约 8 行。这样区间内插函数不再算「函数体」，而 N3 的字符串字面量仍需额外处理（把 `squashed()` 之前的原始代码里的字符串字面量**替换成等长空格**再切分，SET 证据仍可用 `c.contains("SET default_transaction_read_only = on")` 单独保留 —— 现有 `after_connect_...` 判据不依赖 `squashed()`，所以不会误伤）。**这一点我未在真实代码上实现验证（我不改被审对象）。**

### 2.3 畸形 JSON / 中英混排 —— 🔴 挖到真缺陷

**「一个汉字都没有，却含 ASCII」这条形态，对「中英混排」完全失效。**

| 语义值 | 守门器结果 | 应有结果 |
| --- | --- | --- |
| `拥有 belongs_to` | 🟢 **PASS（漏）** | 🔴 应拦 |
| `belongs_to 拥有` | 🟢 **PASS（漏）** | 🔴 应拦 |
| `归属于(1:N)` | 🔴 HIT | ✅ 靠第三档兜住 |
| `一对多` / `多对一` / `属於` / `拥有-属于` | 🟢 PASS | ✅ 正确 |

**这不是理论缺口 —— 它可达：**

- `domain/apply.rs:252`：`semantic: obj.get("semantic").and_then(|v| v.as_str()).unwrap_or("has").to_string()` —— **导入路径接受任意字符串**。
- 即：一份 `semantic` 为 `拥有 belongs_to` 的提案（手写 JSON、或 LLM 抽取产出、或将来 `_ => s.to_string()` 兜底遇到带修饰的语义）→ apply → 冻结 → 客户视图 → **`cli.rs:518-523` 的守门器放行、`exit 2` 不触发** → 内部记号 `belongs_to` 原样发给客户。
- 客户视图红线「零术语」被绕过，且**失败方向是发错数据给客户**（不是拒发）—— 这是本项目里少见的 **fail-open 方向**，比前三轮抓到的任何判据盲区都更接近红线本体。
