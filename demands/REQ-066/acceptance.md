## 问题一：AC-006「消息点名」守不住它要守的东西（**F7 未根治**）

REQ-063 的 AC-006 要求「断言消息里点名 `>= 0` 这条恒真路径」。
Dev 照做了，并把消息提成常量、加了一条测试断言「消息被点名」（MG1 删掉点名 ⇒ 32/1 杀）。

**但 QA 实测把 AC-006 自己点名的那个入口真的放宽了**：

| 改动 | 结果 |
| --- | --- |
| 四条 `assert_eq!(count, 1)` 全改 `assert!(count >= 0)` | **33 / 0 全绿** |
| 只改其中一条 | 同样 **全绿** |

⇒ **洞没堵上。** 消息点名只守住了「消息文本」，**管不住比较符真被放宽** ——
而真正会让人栽跟头的恰恰是后者。

Dev 主动披露了这个边界（这点做得好），QA 也判它**不构成假安心**
（因为 AC-006 字面只要求「消息点名」，类型自标「文档正确性」）。
**但 F7 不能记为「已根治」。**

### AC-001 · ⭐ 拿掉「可放宽」这个轴，而不是盯着它

现在的判据形状是 `assert_eq!(count, 1)` —— **它有方向**：
`>= 0` / `>= 1` / `!= 1` 都是「放宽」，而且都是**合法的一行改动**。

- 预期结果：判据形状改成**没有放宽轴**的形式
- 类型：测试有效性

**推荐方向（Dev 可提出更好的）**：
把「出现次数 == 1」改写成「**匹配到的集合恰好等于某个期望集合**」——
集合相等**不存在放宽方向**（放宽它必须改期望值，而那在 diff 里一眼可见）。

⚠️ **判别力自证（这是本条的灵魂）**：

| 变异 | 预期 |
| --- | --- |
| M1 把四条判据改成 `assert!(count >= 0)` | **必须变红** |
| M2 只改其中一条为 `assert!(count >= 0)` | **必须变红** |
| M3 把「期望集合」改大（例如加上第三个允许串） | **必须变红** |

⚠️ **M2 是本条与 REQ-062 那次的关键区别**：
上一轮 QA 说过「只改一条同样全绿」—— **本条要保证「只改一条」就足以被抓**。
若你的新形状仍然「四条全改才抓得住、单改漏过」，**那是假修**。

⚠️ **AC-006 已有的消息点名测试不许删** —— 它守的是另一件事（消息腐烂），留着无害。

## 问题二：真实样本路径硬编码、无覆盖口（F1 可移植性）

`REAL_BASELINE` / `REAL_LIVE`（`ontok-gate-preflight.rs:1815/:1817`）是
**硬编码绝对路径**，指向仓库根 `.review-workspace/` 下**不入库**的客户源库 schema。

QA 实测的事实（BA 已核对）：
- 缺样本时 `cargo test --bin ontok-gate-preflight` **红 1 条**
  （不是 Dev 报告的 2 条 —— `real_pair_has_no_soft_skip_left` 是 `include_str!` 纯文本判据，与样本无关）
- **更关键**：缺样本时 `drop_rate` 与 `test_fk_naming`（本条**零改动**的红线）
  **本来就在红** ⇒ **失败面是 2 → 3，不是 0 → 1**。
  「与既有 fail-closed 口径一致」**成立**。
- 硬编码路径在 `50a4a24` 就有、**非 REQ-063 引入**，
  但**失效模式从「静默绿灯」变成了「恒红」** ⇒ 无从补救。

### AC-002 · 加环境变量覆盖口

- 预期结果：`REAL_BASELINE` / `REAL_LIVE` 支持环境变量覆盖，
  **缺省值保持不变**（⇒ 本机零影响）
- 类型：可用性
- ⚠️ **照本仓既有约定做**：参考 `tests/drop_rate.rs:68` 的 `ONTOK_SCHEMA_JSON`
  —— **不要自创一套命名风格**
- ⚠️ **必须记在 `status.md` 或模块文档里**：真实样本是哪两个文件、怎么准备它们。
  依据本项目纪律「运行前提要写下来，否则下一个人会对着一个无从补救的红灯发呆」

### AC-003 · 不得把「有覆盖口」写成「有默认值」

- 预期结果：环境变量**未设**时行为与今天**逐字节一致**
- ⚠️ 变异：把缺省路径改成一个不存在的目录 ⇒ 缺省路径下的行为必须与今天不同，
  而**设了环境变量时不受影响** —— 用以证明覆盖口真的生效，不是摆设
