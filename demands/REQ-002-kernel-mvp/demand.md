## 背景

REQ-001 用真实库（`<业务库名>`，97 张表）验证了抽取链路：

| 阶段 | 结论 |
| --- | --- |
| 阶段 1 分组抽取 | ✅ 可外置 |
| 阶段 2 证据验证 | ✅ **不可外包**（13 条 `column_not_found` 是它拦下的） |
| 阶段 3d 跨组合并 | ✅ 可外置（4 组全判对，含 `t043`/`t044` 语义相反的识别） |
| 阶段 3e 跨对象关系 | ✅ 可外置（69 对象规模下 22/22 连接列全部验过） |

**结论**：抽取侧可外置，**本 MVP 承接「阶段 2 那一侧」** —— 它接收的提案必须已带证据，且证据已由抽取侧验证过。

技术栈已定为 Rust（采集器单静态二进制，硬要求见规格 §4.2）。旧的 Python 内核计划（3625 行）语言不匹配，本需求按 MVP 范围重做。

## 用户故事

作为 **FDE**，我需要一套可执行的本体内核机制（版本 / 提案 / 双轨审核 / 冻结 / diff），
以便把抽取侧产出的提案**安全地**转成客户签字的本体版本。

## 范围

**做**：项目与版本容器 · 本体 schema（含 ActionType/Function 占位）· 快照契约（含 `extracted_by`）·
提案制 · 双轨审核状态机 · 客户视图投影 · 提案应用与冻结 · 快照 diff · 层级纯函数 · CLI 端到端

**暂缓 10 项**（**不是永久不做**，各项补回时机见范围规划 §3）：Store trait 抽象 · 内存实现 ·
建模视图投影 · 复杂 diff · `disjoint_with` 逻辑 · HTTP API / MCP server · 数据库迁移 ·
权限 / 多租户运行时 · 抽取与跨组合成 · 写回执行

## 非功能要求

- **分层纪律**：`src/domain/` 内出现 `sqlx` / `PgStore` / `db::` 即为违规，用一条命令守住
- **单静态二进制**：为采集器复用预留（规格 §4.2）
- **快照往返无损**：`save` → `load` → 断言相等，这是最强的一道防线
- **无依赖构建**：不使用 `sqlx::query!` 编译期宏（避免 `.sqlx` 离线数据维护）
- **切片 1 无写回**：**不存在任何可执行写回路径**，有测试守住
