## 2. 裁定：B1 算不算修完？

### 2.1 源码守卫：**两头都不成立** —— 这是本轮最重要的结论

修复方对第一道防线（`passed` 表达式）没有用运行时测试，改用 `include_str!` 源码守卫。
复审**自设计了两个变异专门打这个守卫**，结果一正一反：

| 变异 | 做法 | 结果 | 含义 |
| --- | --- | --- | --- |
| **V6** | 删掉 `blocked` 守卫，但**把字面量留在注释里** | 🟢 **GREEN 存活** | **守卫可被欺骗** —— 源码里"看得见关键词"就算通过，实际的守卫子句可以不在 |
| **V7** | 把 `passed` 做**等价重构**（逻辑完全不变，字面量消失） | 🔴 **RED** | **守卫误报** —— 语义没变的正确改法被判失败 |

**裁定：源码守卫在本项目不成立。** 它同时有两个致命缺陷：

1. **可绕过（V6）**：把守卫逻辑改掉、但让文件里残留一个含关键词的注释或字符串，测试照样绿。
   这正是首轮 B1 被判"零覆盖"的同一种病 —— **"看起来在守"**。
2. **误报（V7）**：合法的等价重构会让 CI 红。开发为绕过它而加注释/常量的倾向，恰好会喂给 V6 那个漏洞。

> **这形成一个闭环陷阱**：守卫会误报 → 开发者为让它绿而留下关键词字符串 → 守卫因此可被绕过。
> 「补了测试」和「测试有判别力」在这里再次分道扬镳 —— **这次是修复本身带来的新分岔。**

**后果：V6 存活意味着第一道防线在修复后仍然是「名义覆盖」。**

### 3.2 自述 7 后半：「对当前代码无误报」🔴 **为假 —— 引入了三类假失败**

复审 agent 未跑完这部分，BA 补做（从 `verify.sh` 原文抽取判据管道，不重打，避免抄错）：

构造 4 行探针，**只有第 1 行是真实 I/O**：

| 探针 | 期望 | 实际 |
| --- | --- | --- |
| `std::fs::read_to_string(...)` | 🔴 抓到 | ✅ 抓到 |
| `let x = 1; /* 注释里写 sqlx::query */` | 🟢 不该误报 | 🔴 **误报** |
| `pub fn trailing() -> u8 { 2 } // 见 sqlx::query 的用法` | 🟢 不该误报 | 🔴 **误报** |
| `const S: &str = "字符串字面量里的 db::"` | 🟢 不该误报 | 🔴 **误报** |

**根因**：`verify.sh` 的过滤器 `grep -vE '^\S+:[0-9]+:\s*(//|/\*|\*)'` 只排除**行首**注释。
行内 `/* */`、**行尾 `//`**、以及**字符串字面量**全部落在判据内。

> 首轮审核曾把这条标为「存疑·未实测」—— 现在**实测确认了，且比预想更广**：
> 不止行尾注释，**字符串字面量也误报**。

**当前无实际影响**（现有 `src/domain/` 没有这类行），但这是明确的**埋雷**：
任何人在 domain 层写一句带 `sqlx` 的行尾注释、或一个含 `db::` 的字符串常量，判定器立刻红。
判定器是"红线判据"，它误报的代价是**开发者学会忽略红线输出**。

## 4. S6 偶发失败：根因已定

**根因：`Connection reset by peer`，发生在建立连接时，不是逻辑 bug。**

机制：每个测试各自建一个 `max_connections(5)` 的连接池，**测试并行执行**；
而测试库端点在**非标准端口 30432**（是一个代理），**超额连接被重置**。

这解释了为什么首轮审核和修复轮 Dev **两次**都只看到"偶发失败、重跑又好了"。
首轮审核 11 次未复现、Dev 3 次未复现，是因为**没有开着完整输出跑**，抓不到那条连接错误。

**整改建议（按性价比）**：
1. 降低 `max_connections`（5 → 2），总连接数立刻降一半 —— 最小改动
2. 加连接重试（`sqlx::pool` 的 `max_connections` + `acquire_timeout` 调优）
3. CI 用独立实例/独立 schema，不共用代理端点
4. 根治：DB 测试串行化（`--test-threads=1`），代价是测试变慢

**建议写进需求文档**：S6 的定性应记为「环境导致的假阴性信号」，
即 **"133 全绿" 作为验收信号在当前环境下不可靠** —— 它同时取决于测试库代理的连接容量。
