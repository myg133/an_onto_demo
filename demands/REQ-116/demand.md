# 需求：REQ-116 · 文档摄取与断言抽取（第一步：从非结构化文档抽本体候选）

## 基本信息

| 项 | 值 |
| --- | --- |
| 需求编号 | REQ-116 |
| 优先级 | **P0**（补的是当前本体的**结构性缺陷**：关系只有归属） |
| 状态 | 进行中 |
| 基线 | `develop` `a85383a` |
| 触发 | 用户：「关系除了归属没有其他关系了？我想通过非结构化文档抽取本体，再用 schema 矫正并关联」 |

## 为什么需要它（先看数据）

当前 82 条关系：

```
semantic:     belongs_to 79 · references 3
cardinality:  N:1 82（全部）
```

**这不是抽取质量差，是 schema 里只有这个**：

| 原因 | 后果 |
| --- | --- |
| 源库 0 个外键 | 没有一条关系是 DB 声明的 |
| 只能靠 `*_id` 命名约定推断 | 「`orders.customer_id` → `customers`」天然就是**归属** |
| DDL 里没有动词 | 「客户**下单**」「平台**扣费**」「用户**订阅**套餐」——**关系语义在语言里，不在表结构里** |
| 单列外键 | 基数必然 N:1；多对多藏在关联表里，又被推成两条归属 |
| 26 个对象度 = 0 | 没有 `*_id` 的对象在图上就是孤岛 |

⇒ **schema-first 能恢复「存在」与「归属」，恢复不了「含义」。**

## 本需求的范围（**只做第一步**）

```
① 文档 ──摄取+抽取──▶ 断言（概念 / 关系+动词 / 证据片段）   ← 本需求
② 断言 ──对齐────────▶ 文档概念 ↔ 表/字段（人签）            ← REQ-117
③ 融合 ──矫正────────▶ 与 schema 关系合并、冲突显式            ← REQ-117
```

⛔ 本需求**不碰数据库、不改本体、不出图**。产出是一份**带证据的断言文件**，供下一轮回合。

## 范围

### 做

1. **`ontok doc ingest --input <dir|file> --out <assertions.jsonl>`**
   - 接受 `.md` / `.txt`（UTF-8）；⛔ 其它格式**显式报错**并提示先转文本（PDF/Word 由外部转换，转换后记 hash）
   - 目录递归；每个文件记 `sha256`
2. **确定性分块**：按标题/段落切，块 id = `sha256(file)[:12]:<起始字节>-<结束字节>`；⛔ 不用模型分块
3. **断言抽取**（模型）：
   - `concept`：`{name, aliases?, description?, evidence}`
   - `relation`：`{subject, predicate（动词，如「下单」「扣费」「订阅」）, object, cardinality?, evidence}`
   - **`evidence` 必填**：`{file, chunk_id, quote, span:[start,end]}`
4. **证据校验（fail-closed）**：`quote` 必须能在**该块原文**里逐字找到（归一化 CRLF 后）；找不到 ⇒ **该条断言丢弃并计数**，⛔ 不许「修正 quote 凑上」
5. **指纹缓存**：`sha256(chunk_text + prompt_sha + model + agent_version)` ⇒ 命中不调模型（REQ-109 口径）
6. **预算闸**：`--budget-tokens`，超了**停**并报告「已用/上限/停在第几块」
7. **产出**：JSONL（每条一行，按 `file, chunk 起点, 序号` 稳定排序）+ `stats.json`（文件数/块数/断言数/被丢弃数/缓存命中/token）
8. **注册为内部出口**：登记进 REQ-107 的 `OUTLETS`（内部轨，**不过客户发布闸**——它不是客户可见内容）

### 不做

- ⛔ 不写库、不改本体、不出图（REQ-117）
- ⛔ 不做 PDF/Word 解析（外部转）
- ⛔ 不做对齐（文档概念 ↔ 表名）
- ⛔ 不做「自动合并同一概念的不同叫法」（留到对齐轮）
- ⛔ 不引新依赖（HTTP 用既有 ureq；JSONL 手写）

## 关键裁定

| # | 问题 | 裁定 |
| --- | --- | --- |
| R1 | 证据是**硬要求** | 无 quote 或 quote 对不上 ⇒ 丢弃并计数。**没有证据的断言是幻觉的温床** |
| R2 | 分块必须确定性 | 同文件、同参数两次分块 ⇒ 块 id 与内容逐字相同 |
| R3 | 抽取也要求确定性 | 靠缓存：第二次运行 **0 token**、输出逐字节相同 |
| R4 | 事实与意见分开 | 文档里的「未来规划」「建议」「示例」不许当断言；模型须标 `modality: fact/spec/future/example`，⛔ `future`/`example` 不进后续对齐 |
| R5 | 不猜 | 文档没写关系就不产出关系。⛔ 不许用 schema 知识「补全」文档断言——那会在第二步污染对齐 |
| R6 | 中文友好 | 分块按标题层级 + 段落，不按字符数硬切（避免把一句话切断） |

## 风险

| # | 风险 | 缓解 |
| --- | --- | --- |
| 1 | 模型编造原文 | R1 逐字校验 + 计数曝光 |
| 2 | 同一概念多种叫法导致断言爆炸 | 本需求**接受**重复（对齐轮再做实体消解），但 stats 里报「去重后概念数」 |
| 3 | 文档很长、成本高 | 预算闸 + 缓存 + 可选 `--limit-chunks` |
| 4 | 断言的粒度不合适（太细/太粗） | 先跑真实文档看分布，再调提示词；**不预先优化** |

## 交付物

1. `ontok doc ingest` 命令 + JSONL/JSON 产出
2. 证据校验（有牙：构造伪造 quote ⇒ 必须被丢弃）
3. 确定性双证（分块两次一致；抽取两次 0 token 且输出相同）
4. 真实文档实测（用户提供路径后跑；先用手头可得的文本做冒烟）
5. 已知限制（格式、语言、粒度）
