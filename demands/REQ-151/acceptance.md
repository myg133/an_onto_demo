## 二 · 裁定（Dev 交付后）

### R-A · REQ-136 的 AC 被**有意收窄**：加勘误，不改原文

Dev 复核发现 REQ-136 的 `AC-004/008` 原文是「POST /api/sparql ⇒ 503」，**没有限定类**——比我假设的更宽。

**裁定**：在 REQ-136 里加**勘误段**（已加），原文保留。
**为什么**：验收文档是历史记录，"收窄"必须留下痕迹；直接改原文等于抹掉当时的事实。

**Dev 的处理正确**：它指出冲突、没动别人的 AC、让我来定。

### R-B · 已知限制：本体模式下 `get.filter.ids` 无法从 id 字面量推出（**接受**）

| 模式 | `@pending.get.filter` |
| --- | --- |
| 普通模式 | 有 R2RML 映射 ⇒ 能从 `?c :cvm_instance__id <id>` 认出主键 ⇒ `{"ids":[...]}` |
| **本体模式** | 无 R2RML ⇒ **拿不到主键** ⇒ `filter: {}` |

**裁定：接受，但必须写进已知限制并说清后果。**

后果要说白：
> Agent 拿到 `filter: {}` 等于"**取全量**"——对账单一类接口代价很大。
> 它应当**先按其 id 属性查询拿 id**，再带 id 去取；而"哪个属性是主键"本体里**目前没有声明**。

**补齐路径**（记债，不阻塞）：本体里需要 **property 级主键声明**，pending 才能自动填 `ids`。

### R-C · `max_rows=0` + 纯 api 查询从 503 变 400：**接受**

参数闸在模式闸之前，语义上更合理（"你这个参数就是错的，跟你部署什么模式无关"）。
**要求**：写进 `--help` 或已知限制。
