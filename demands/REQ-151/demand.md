# 需求：REQ-151 · 本体模式下，**api 源**的查询应返回取数指引（而不是 503）

## 基本信息

| 项 | 值 |
| --- | --- |
| 需求编号 | REQ-151 |
| 优先级 | **P0**（决定"对外只给本体 + 指引"这个形态能不能成立） |
| 状态 | 进行中 |
| 基线 | `develop` `9dfb8e7` |
| 触发 | UAT 装了 AM（14 类 `sourceKind: api`）后，**SPARQL 仍恒 503** ⇒ AM 装等于没装 |

## 问题（实测）

UAT 部署是 `--ontology-only` + `--access-mapping`。查询 api 类：

```
POST /api/sparql  {"query":"SELECT ?c WHERE { ?c a :cvm_instance }"}
⇒ 503 {"code":"NO_DATA_SOURCE","message":"本部署只提供本体，未接业务库"}
```

**代码顺序**（`src/query/mod.rs::run_sparql`）：

```
⓪ 本体模式？ ⇒ 直接 503          ← 卡在这
① 租户核对
② max_rows
③ 并发
④ source_check ⇒ 这里才判「api 类 ⇒ @pending」
```

**⓪ 在 ④ 之前，所以 `@pending` 永远走不到。**

## 为什么这是**过度拦截**

REQ-136 加 ⓪ 步的理由是「本体模式不接库 ⇒ **不许任何请求碰源库连接**」。
**这个理由只对 `db` 类成立**：

| 查谁 | 该不该 503 |
| --- | --- |
| `db` 类（库源） | ✅ 该——我确实没有库 |
| **`api` 类** | ⛔ **不该**——我本来就不需要库，我要说的是"你去调这个接口" |

⇒ 现在的行为等于：客户问「云硬盘有哪些」，我们答「**我们没有仓库**」，
而正确答案是「**仓库不归我管，你去这个地址取**」。

## 要做

**把 ⓪ 步挪到"源判定"之后**，只对**需要库**的查询保留 503。

| 场景（本体模式 + 有 mapping） | 期望 |
| --- | --- |
| 只涉及 **api 类**（jsonld） | **200** + `@graph: []` + `@pending` + `meta.complete:false` + `get{...}`（与普通模式同形状） |
| 只涉及 **api 类**（rows） | **400 `NOT_DB_SOURCE`** + hint（⛔ 不是 503、⛔ 不是空表） |
| 只涉及 **库类** | **503 `NO_DATA_SOURCE`**（不变） |
| **混合**（库类 + api 类） | **503 `NO_DATA_SOURCE`**（因为它需要库） |
| `sample` | **503**（不变，取样必须真连库） |
| 没有 mapping | **503**（不变） |

## 不可破的结构事实

> **本体模式下，任何代码路径都不得拿到源库连接。**

`svc.source` 是 `Option`，现在靠"⓪ 步早返回"保证。**挪动判定顺序后必须重新保证这条**：
- `source` 为 `None` 时，后续任何 `expect`/`unwrap` 不可达（保持结构保证，不靠约定）
- 加一条**测试**：本体模式下走 api 类查询，断言"零连接尝试"（可用"源库 URL 指向不存在的地址也不受影响"证明）

## 关键裁定

| # | 裁定 |
| --- | --- |
| R1 | **普通模式行为逐字节不变**（含 400/503 的码与文案） |
| R2 | 本体模式下 **db 类仍 503**（这是 REQ-136 的原始意图，不动） |
| R3 | 本体模式下 **`sample` 仍 503** |
| R4 | **审计 `code` = 客户端实际收到的码**（沿用 REQ-145 R-B） |
| R5 | 响应里的 `@pending` 形状与普通模式**完全一致**（同一渲染路径，⛔ 不许为这个模式另写一份） |
| R6 | ⛔ 不许出现厂商名；⛔ 不改 `access` 契约格式（那是 REQ-150 的事） |

## 风险

| # | 风险 | 缓解 |
| --- | --- | --- |
| 1 | 挪顺序后"绝不碰源库"被破坏 | 结构性保证 + 一条"零连接尝试"的测试（R2 之外的硬要求） |
| 2 | 与 REQ-136 的验收冲突 | REQ-136 的 AC 只约束 **db 类**；本条不违反（要复核 REQ-136 的 AC 文案） |
