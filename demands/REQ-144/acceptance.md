## 四 · 阶段 1 裁定（2026-10-25）

### R-A · 签名对拍：**接受**，且中间量全部对齐

官方文档《签名方法 v3》唯一带密钥示例（`cvm` / `1551113065`）：`Authorization` 与
`Signature=10b1a37a…6ab6c4f` **逐字节相同**，且 `Date` / `HashedRequestPayload` / `CanonicalRequest` /
`StringToSign` / 三把派生密钥**逐项相等**。

**为什么这条判据够硬**：它证明的不是"输出像"，是**每个中间环节都对**——签名错时真调用只回一个看不懂的 401。

**⚠️ 第二组向量的来源已如实标注**：文档只公布一组（SecretKey 打码），第二组用**文档同一份 Python 实现**复算，
测试注释写明"⛔ 不要说成文档公布的期望值"。**这个处理正确。**

### R-B · 零新增依赖：**接受**，但记两条代价

1. 手写密码学原语**必须**靠标准向量证明（FIPS 180-2、RFC 4231 §4.2/4.3/4.6 已做）
2. 将来换算法时，这段是自维护代码，**不如现成库**——那时应重新评估"零依赖"是否值得

## 六 · 真调用结果（2026-10-25 · 用只读子账号实测）

```json
{ "@id": "…/cvm_instance/ins-70n4ge4i", "@type": "ontok:cvm_instance",
  "ontok:cvm_instance__name": "test03",
  "ontok:cvm_instance__status": "RUNNING",
  "ontok:cvm_instance__zone": "ap-guangzhou-5" }
```

⇒ 手写 TC3 签名 + HTTP 传输 + 迭代器 + 字段路径**全部经真实接口验证**（不再是"逻辑上应该对"）。

### R-L · ⛔ R-E 的风险**被真调用证实**（这是本轮最重要的发现）

带过滤时：

```
✗ API_ERROR · 服务端返回码 `UnknownParameter`：The parameter `Zone` is not recognized.（HTTP 200）
这是业务错误，不是签名问题：按这个码改请求…
```

**结论**：
- 腾讯云 `DescribeInstances` **不接受**顶层 `Zone` 参数
- 必须用 `Filters[].Name = zone`（`Filters` 是数组，元素 `{Name, Values}`）
- ⇒ 现有 access mapping 的 `from_filter: { "zone": "Zone" }` **是错的**

**这是"签名对 ≠ 接口通"的教科书案例**：
签名与传输都完美，**但参数位置错**，真调用直接失败。
如果没做真调用，这个东西会带着"已验证"的标签上线，然后在客户现场 100% 失败。

**⇒ R-E 那条裁定（"真调用第一件事就是验它"）是对的，而且它验出了失败。**

### R-M · 错误分类**经受住了真实错误**

`UnknownParameter` 被归到 `API_ERROR`，并给出"这是业务错误、⛔ 重试无效"的可行动提示
——**不是**一律 `request failed`，也没有误判成可重试。这一条在真实错误上验证通过。

### R-N · 阻塞项：mapping 需要**数组对象参数**的表达能力

现有 `from_filter` 只能表达"过滤键 → 顶层标量参数"。
腾讯云多数查询接口用 `Filters.N.Name` / `Filters.N.Values.N`，**这是结构性缺口**，不是 cvm 一个特例。

**必须扩展**（否则所有带过滤的 API 映射都写不出来）：

```json
"request": {
  "required": ["Region"],
  "from_filter": {
    "zone": { "array": "Filters", "item": { "Name": { "const": "zone" },
                                            "Values": { "from": "value" } } },
    "ids":  { "scalar": "InstanceIds" }
  }
}
```

⇒ 判据：**用真账号跑通"按 zone 过滤"并返回正确子集**（不是返回 0 条、也不是静默忽略）。

## 七 · 裁定（用户 2026-10-25）：**不做特例适配，改通用请求模板**

### R-P · 两个原因，两个责任方

真调用暴露的"参数抽错"，背后**不是一个问题**：

| 原因 | 归属 | 说明 |
| --- | --- | --- |
| **A · 抽取端没拿到"接口入参规格"** | **抽取/语料** | 我们给抽取的语料是「数据结构」页——**只有响应字段，没有请求参数**。写映射的人只能猜"按 zone 过滤就传 `Zone`" |
| **B · 映射格式表达力不够** | **产品** | `from_filter` 只能写"过滤键 → 顶层标量"，表达不了嵌套/数组请求体 |

**关键结论（要写进流程）**：

> **本体（类/字段）该读「数据结构」页；映射（怎么调接口）必须读「接口定义」页。**
> 我们只采了一种语料，做了两件事 —— 这是流程设计缺口，不是某个人写错。

### R-Q · F4 改写：**不是"支持 Filters"，是"通用请求模板"**

用户原话：「**开发不要针对特例适配，我们做的是产品，不针对特例**」。

⇒ ⛔ 不许出现 `if vendor == tencent` 之类的特例分支。
✅ 只认一个机制：**任意 JSON 模板 + 占位符绑定**。

```json
"request": {
  "template": {
    "Region": "{region}",
    "Filters": [ { "Name": "zone", "Values": ["{zone}"] } ]
  },
  "bindings": {
    "region": { "source": "default" },
    "zone":   { "source": "filter" }
  },
  "paging": { "offset": "Offset", "limit": "Limit" }
}
```

| 要素 | 说明 |
| --- | --- |
| `template` | **请求体长什么样就写什么样**（任意嵌套 / 数组） |
| `{…}` | 占位符 |
| `bindings` | 每个占位符从哪来：`default`（源默认值）/ `filter`（调用方过滤条件）/ `paging` |
| `paging` | 分页参数位置（`Offset`/`Limit` 等），⛔ 不硬编码 |

**通用性判据**：**不下发任何厂商名**也能表达下列三种请求体：

1. 顶层标量：`{"Region":"x","InstanceIds":[...]}`
2. 数组对象：`{"Filters":[{"Name":"zone","Values":["y"]}]}`
3. 深层嵌套：`{"Condition":{"Rules":[{"MetricName":"m","Value":"v"}]}}`

**如果真出现了第 4 种非 JSON 形态（如 XML body / 表单编码）⇒ 报"不支持"并点名，⛔ 不许偷偷适配。**

### R-R · 语料缺口要单独立项

映射抽取没有"接口定义"语料 ⇒ 现在是人在猜。
⇒ 需补采：每个产品的**接口页入参表**（参数名 / 必选 / 类型 / 位置：body vs query）。

**这条不属于本需求**（本需求只负责"格式能表达"），要单独登记。

### R-S · 对用户的承诺（流程）

真调用必须**先于**任何"映射已可用"的声明。
本次如果没做真调用，产物会带"已验证"标签上线，**在客户现场 100% 失败**。
