# 需求：REQ-153 · 覆盖盲区盘点（把"该建哪些类"变成可执行的检查）

> 让 §一·五「盘点盲区」从**手工比对**变成一条命令。

## 基本信息

| 项 | 值 |
| --- | --- |
| 需求编号 | REQ-153 |
| 优先级 | **P1**（不挡接入，但决定本体能不能"建对范围"） |
| 状态 | 已就绪（未开工） |
| 基线 | `v0.1.8`；依赖 **REQ-152 阶段 1**（`ontok-builder` 存在） |
| 触发 | 真实巡检：**轻量应用服务器占当月支出 14.96%，本体没有这个类** ⇒ 这部分钱在系统里隐形 |

## 一 · 问题

本体是**从文档抽的**，而**该建哪些类应该由"钱和资源"决定**。

实测缺口（同一套 30 类本体）：

| 产品 | 当月消费 | 本体里有类吗 | 后果 |
| --- | --- | --- | --- |
| 轻量应用服务器 | 382.33 元（**14.96%**） | ❌ | **隐形支出** |
| VPN 网关 / 云联网 / NAT / EIP / COS | 都有消费 | ❌ | 同上 |
| `cvm_image` / `eip` / `route_table` … 等 16 个类 | —— | ✅ 有类 | 但**无取数契约** ⇒ 查了 503，像"没这东西" |

**两种缺口，都得能自动盘出来。**

## 二 · 要做

新增子命令（构建面，REQ-152 之后就是 `ontok-builder`）：

```bash
ontok-builder coverage \
  --project cloud-resource --version 3 \
  --billing bill-summary.json \      # 云厂商"按产品汇总"的响应（原样）
  --mapping am-tencent.json \        # 已签取数契约（可多份）
  --dict product-class.json \        # ⭐ 声明：产品名 → 类 key（或 null）
  --format md \                      # md | json
  --out gap-report.md
```

### 三个输入的含义

| 输入 | 来源 | 作用 |
| --- | --- | --- |
| `--billing` | `…BillSummaryByProduct` 一类接口的**原始响应** | 哪些产品真在花钱 + 金额 |
| `--mapping` | `am-*.json`（可多份） | 哪些类**有**取数契约 |
| `--dict` | **人写的声明**（见下） | 产品名 ↔ 类 key |

### 输出四块

```json
{
  "missing_classes": [            // 有消费、没有类 ⇒ 隐形支出（按金额降序）
    { "product": "轻量应用服务器", "cost": 382.33, "share": 0.1496,
      "suggested_class": "lighthouse_instance", "decision": "pending" }
  ],
  "classes_without_contract": [   // 有类、没有契约 ⇒ 查不了
    { "class": "eip", "note": "catalog 有，am 无" }
  ],
  "contract_without_class": [],   // 契约指向不存在的类 ⇒ P0
  "unmapped_products": [          // ⭐ 字典里没声明的产品（⛔ 不许静默丢）
    { "product": "某种新产品", "cost": 12.0, "share": 0.0047 }
  ]
}
```

### ⛔ 核心裁定：产品名 ↔ 类 **只认字典，不许猜**

```json
{ "version": "1.0.0",
  "map": {
    "云服务器":            "cvm_instance",
    "轻量应用服务器":       "lighthouse_instance",
    "云硬盘":              "cbs_disk",
    "NAT 网关":            null,                 // ⭐ null = 明确决定"不建"
    "对象存储":            "cos_bucket"
  } }
```

| 情况 | 行为 |
| --- | --- |
| 字典里有映射 | 正常对账 |
| 字典里是 `null` | **明确不建** ⇒ **不进** `missing_classes`（但可在报告里单列"已决定不建"） |
| **字典里没有** | 进 `unmapped_products[]` + **警告**，⛔ **不许猜、不许忽略** |

**为什么**：和 ADR-006 一致——**机制/声明/决策**三层分开。工具只做机制，字典是声明，"归不归并"是决策。

### 退出码

| 情况 | 退出码 |
| --- | --- |
| 全部覆盖 | 0 |
| 有 `contract_without_class`（P0） | **非 0** |
| 有 `missing_classes` 且**最高占比 ≥ 2%** | **非 0**（可 `--fail-threshold` 调，默认 2%） |
| 只有 `unmapped_products` | 0 + 警告（需要人补字典，不是"覆盖不够"） |

## 三 · 不做

| ⛔ | 理由 |
| --- | --- |
| 自己去调云 API 拿账单 | REQ-152 之后构建面**不该带网络执行**；由 FDE 用厂商 SDK 取，喂 JSON 进来 |
| 自动把"轻量应用服务器"归到 `cvm_instance` | 这是业务决策，⛔ 不许算法猜 |
| 自动补类 / 自动写映射 | 只出报告，建不建人定 |
| 改本体 | 只读 |

## 四 · 关键裁定

| # | 裁定 |
| --- | --- |
| R1 | **只读**：不写元数据库、不调网络、不改本体 |
| R2 | 字典没声明的产品 → `unmapped_products` + 警告，⛔ 不静默丢弃 |
| R3 | `null` 是**合法决策**（明确不建），不是"没配" |
| R4 | 金额占比排序用**账单原始数字**，⛔ 不做汇率/口径换算 |
| R5 | 报告要人可读（md）+ 机可读（json）两种 |
| R6 | 账单 JSON 的结构**因厂商而异** ⇒ 用 `--billing-shape` 或小适配段声明取值路径（⛔ 不许在产品里写厂商分支，参考 REQ-152 的禁止项） |

## 五 · 风险

| # | 风险 | 缓解 |
| --- | --- | --- |
| 1 | 账单结构因厂商/版本而异 | R6：取值路径由参数/声明给，不写死 |
| 2 | 字典长期不更新 ⇒ 一直有 `unmapped_products` | 报告里单列，并作为 FDE 每轮必看的清单 |
| 3 | 类名与产品名对不上导致误判 | 字典人签 + 报告列出"已决定不建"的，便于复核 |
| 4 | 依赖 REQ-152 阶段 1 | 若 152 未合，先在 `ontok` 里加同名子命令，迁移时跟着走 |
