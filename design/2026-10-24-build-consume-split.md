## 一 · 一句话

> 把产品切成**三段**：客户网络里跑「构建」，中间交一份「带哈希的构建包」，我方只负责「人签 + 冻结 + 消费」。
> 连接层可选地坐在构建面底下，把所有外部源归一化成「逻辑表」。

## 四 · 三个可交付物

| 交付物 | 形态 | 装在哪 | 谁维护 | 依赖权力 |
| --- | --- | --- | --- | --- |
| **`ontok-build`** | CLI + stdio MCP server + skill | 客户网络 | 我们发版，客户升级 | 只读源 + 可选 LLM |
| **连接层** | 独立进程 + 适配器插件 | 客户网络 | 同上 | **持有凭据**（最强） |
| **bundle** | 文件包 + manifest | 跨边界传输 | 契约由我们定义 | —— |
| **`ontok-control`** | 控制面服务（console + 接收） | 我方 | 我们 | **写元数据库** |
| **`ontok-runtime`** | 数据面服务（query/portal） | 我方 | 我们 | **只读元数据库** |

**五个东西，四套权限**。这就是拆分的全部意义。

## 五 · 契约：bundle 里有什么

### 5.1 最小包（阶段 0）

```
bundle/
├── manifest.json          # 版本 + 每个文件的 sha256 + 总数
├── schema.json            # 逻辑表与列（来自连接层 describe）
├── proposal.json          # 实体/属性/关系提案（含证据）
└── capability.json        # 每个逻辑表的 pushdown 等级与上限
```

### 5.2 完整包（加溯源）

```
├── assertions.jsonl       # 文档断言（每条带逐字 quote）
├── names.json / exclusions.json / concept-groups.json
└── docs/                  # 原始文档（可选；上传即授权溯源）
```

### 5.3 manifest 是核心

```json
{
  "bundle_version": "1",
  "project": "ops360",
  "built_at": "2026-10-24T12:00:00Z",
  "builder": { "tool": "ontok-build 0.2.0", "operator": "alice" },
  "source": { "kind": "connector", "sources": ["prod-db", "oss-docs"] },
  "files": [
    { "path": "schema.json",     "sha256": "…", "bytes": 12345 },
    { "path": "proposal.json",   "sha256": "…", "bytes": 67890 },
    { "path": "capability.json", "sha256": "…", "bytes": 1234 }
  ],
  "evidence": { "measured_by": "client", "server_verified": false }
}
```

`evidence.measured_by` 是**新增的诚实声明**（见 §七）。

## 六 · 这次拆分顺手能清掉的一个历史包袱

现在有**两套签字机制**：

| 机制 | 写什么 | 谁看 |
| --- | --- | --- |
| `review decide`（双轨） | 元数据库里的评审状态 | 服务端流程 |
| `doc sign` | 提案文件里的 `reviewed_by` 字段 | apply 时判"未签" |

REQ-129/130 那两轮我们花了不少力气让两者共存，本质是**因为它俩生在不同时代**。

**拆到"签只在服务端"之后，`doc sign` 就该消失**：

```
构建面产出 doc 断言 → 合并进 proposal → 上传
控制面 import → review decide（对所有条目，含 doc 来源）→ apply
```

⇒ 一套签字、一个事实来源。**这是拆分带来的净收益**，不是新功能。

## 七 · 证据等级必须改语义（不可回避）

拆完之后，服务端**看不到源库**，所以：

| 现状 | 拆后 |
| --- | --- |
| `joinVerified: true` = 我们实测值域重叠 5/5 | = **客户端声明**它测了 5/5 |
| 我们能复算 | 我们**不能复算**，只能比对两次构建的 digest |

**建议**：

| 方案 | 含义 | 我倾向 |
| --- | --- | --- |
| a | 保留 `true`，加 `measured_by: client` | ⚠️ Agent 会忽略附加字段 |
| **b** | 新增一档 `declared`；`true` 只给服务端实测 | ✅ **换个词，Agent 才会读** |
| c | 不动等级，TTL 头部声明"证据由客户端提供" | ⚠️ 藏在文件头，容易被跳过 |

**背书方案 b**：四档变五档

```
verified    服务端实测（本部署有源库时才有）
declared    客户端声明实测（当前主路径）
inherit     同名列传递
unverified  无证据（文档语义/命名推断）
false       明确不成立
```

**并且**：同一项目两次构建的 `sample_digest` 不一致 ⇒ 服务端**报警**（数据变了，需要重审）。

## 八 · 边界：明确不做的

| # | 不做 | 理由 |
| --- | --- | --- |
| 1 | **跨源 join**（v1） | 需要联邦执行器 + 跨源权限模型，scope 爆炸 |
| 2 | 服务端跑 LLM | 拆构建的初衷就是"数据不出客户网络" |
| 3 | 第三方插件市场（v1） | 带凭据的插件 = 后门，先只做官方 |
| 4 | 文档进本体 | 文档是**证据**，不是数据；混进去谁都说不清 |
| 5 | 连接层强制必装 | 保留"给我一个目录"的最低接入路径 |
| 6 | 数据面写库 | 数据面用只读 DB 账号，靠**账号**而非代码 |

## 九 · 权限矩阵（拆分的真正落点）

| 组件 | 源库 | LLM | 元数据库 | 对象存储 |
| --- | --- | --- | --- | --- |
| `ontok-build` | 只读（或经连接层） | ✅ | ❌ | ❌ |
| 连接层 | **只读 + 凭据** | ❌ | ❌ | 读 |
| `ontok-control` | ❌ | ❌ | **读写** | 读（取 bundle） |
| `ontok-runtime` | 只读（普通模式查数据） | ❌ | **只读** | ❌ |

**数据面拿只读 DB 账号**——这比"镜像里没有写库子命令"更硬，因为它不依赖谁能 exec。

## 十 · 迁移路径（每步可回退）

| 阶段 | 做什么 | 可回退点 |
| --- | --- | --- |
| **M1** | 定 bundle 契约 + manifest；控制面加"接收 bundle" | 旧路径（本地构建+直连）仍可用 |
| **M2** | 拆镜像：`ontok-runtime` / `ontok-control` 两套 + DB 账号分离 | 合并回单镜像 |
| **M3** | `ontok-build` 打成客户端交付物（CLI + MCP + skill） | 服务端仍能自己构建 |
| **M4** | 证据等级引入 `declared` + digest 报警 | 等级可回退（加字段不改语义） |
| **M5** | 连接层（先对象存储一个适配器 + 契约） | 连接层可选，直连路径保留 |
| **M6** | 第二个适配器（DB 或 API），证伪契约 | 同 M5 |
| **M7** | 插件签名 + 开放策略 | 保持官方插件 |

**顺序的理由**：先定契约（M1），再动部署（M2/M3），最后加能力（M5+）。
**反过来做**（先拆镜像、后定契约）会把问题藏进镜像里。

## 十一 · 需要拍板的三件事

| # | 问题 | 选项 |
| --- | --- | --- |
| 1 | 控制面与数据面**是否分镜像** | 分（权限靠账号）/ 不分（靠 RBAC） |
| 2 | `doc sign` 是否**并入** `review decide` | 并入（一套签字）/ 保留（两套） |
| 3 | 证据等级用 **b 方案（新增 declared）** | 同意 / 用附加字段 |

## 十二 · 这张图的自检

| 问题 | 回答 |
| --- | --- |
| 客户不装任何东西能用吗？ | ✅ 能：给它一个目录 + 一个只读账号，跑 `ontok-build` |
| 源库必须出网吗？ | ❌ 不需要（连接层或直连都在客户侧） |
| 服务端能写库吗？ | 控制面能（内部）；**数据面不能**（只读账号） |
| R2RML 能通吃非关系源吗？ | 🟡 能描述，但**查询能力分级**必须显式声明 |
| 拆完谁最容易出错？ | **能力声明与证据等级**——两个都是"说了什么"而不是"做了什么" |
