# 需求偏差任务列表 · 设计 vs 实现

> 2026-10-05 · BA Agent 梳理 · 依据 `BA/docs/design/ontology-platform-spec.md`（1449 行，唯一事实源）
>
> **背景**：REQ-002 ~ REQ-009 的开发**偏离了设计**。三轮独立审核全部通过（167 测试全绿），
> 但**没有一轮质疑「这是不是该由 agent 做」** —— 因为审的是代码，对的是代码。
> 本清单把偏差摊开，**逐条处置**。

---

## 0. 偏差的性质：不是漏做，是**做了另一个东西**

| | 设计要的 | 我做的 |
| --- | --- | --- |
| 抽取 | **LLM 在数据里识别模式**（§7.1 阶段 1，A2A 调外部 agent） | **规则引擎 + 我手写的知识库** |
| 产物 | 候选 + 证据，**待验证** | 「翻译后的表结构」，直接当成品 |
| 命名 | agent 做**映射**（模式识别，强项） | **我做命名**（§7.1 明确标注为 agent 最弱项、会幻觉） |
| 范围 | **决策清单限定**（§2.6） | 数据源扫全 91 张表 |

**两者输出形状很像**（都是「实体+属性+关系」），所以一路跑下来测试全绿、审核全过。
**但它从一开始就不是设计要的那个东西。**

**方法论错误**：在错误的抽象层打补丁。三轮审核挖出 20+ 个问题，我一轮轮修，
**全是在规则层精修**。形而上学的问题不会被形而下的修复解决。

### RN 实施中暴露的架构约束（补记于 2026-10-08）

以下三条不是需求，是 **§7.1 没写出来但必须遵守**的约束，均由 verifier 实证：

1. **能力声明必须是静态的。** 闸门在抽取**之前**执行，而「这份答案能否重建」是抽取**之后**才知道的
   —— 让能力标签跟着答案翻转，会造出一个经生产入口不可达的分支，并把闸门从「防呆」变成「逼你签字」。
2. **`extracted_by` 的可信度由写入通道担保，不由内容担保。** import 通道按 ADR-001 原样取 JSON 里的值，
   零校验零留痕 ⇒ 提案的自我声明默认不被担保。详见 [ADR-003](../../decisions/ADR-003-提案溯源可信度由谁担保.md)。
3. **`concept import` 已有 fail-closed 内容指纹校验，`propose import` 是全系统唯一漏网。**
   ⇒ 补齐它属于「内部一致性」，不是「新增安全机制」。

## 6. 与切片顺序的关系

设计 §9.1 切片 1 = **只读闭环**。按 §9.5，验收 8 条，我目前**满足 3 条**：

| §9.5 验收项 | 状态 |
| --- | --- |
| 真实客户数据源 | ✅ `<业务库名>` |
| **已有决策清单且范围可追溯** | ❌ |
| FDE 一个工作日产出第一版提案 | ⚠️ 产出了，但方式与设计不符 |
| 每条提案携带证据 | 🟡 部分 |
| 建模轨 FDE 完整执行 + 业务轨代签留痕 | ❌ 无 FDE 视图、无代签机制 |
| **MCP 能回答 ≥5 个客户级业务问题** | ❌ |
| 覆盖率达阈值 | 待校准 |
| 不要求客户独立完成建模轨、不要求写回 | ✅ |

**缺口集中在 RE / RN / RM 三批。** 本清单把这三批作为重梳主线。
