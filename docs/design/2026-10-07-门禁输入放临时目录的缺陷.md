# 发现：回归门禁的输入放在临时目录里，随时会失效

> 2026-10-07 · REQ-011 期间暴露 · **输入文件已找回并恢复**，但缺陷本身未修，待用户裁定

## 现象

两条 **fail-closed 回归门禁**的输入是 `.review-workspace/fix-props/schema.json`：

| 测试 | 默认路径定义处 |
| --- | --- |
| `tests/drop_rate.rs:29` | `const DEFAULT_SCHEMA: &str = "../.review-workspace/fix-props/schema.json";` |
| `tests/test_fk_naming.rs:311` | 同一路径硬编码 |

两条测试的纪律是明确的——读不到输入就判失败，不能安静跳过：

```
这个测试是丢弃率的**回归门禁**，读不到输入时它必须失败 —— 静默跳过等于没有门禁。
```

## 根因

`.review-workspace/` 按 `agent-workspace` 规范的定义就是**临时工作区**：所有 QA / Dev 的变异备份、独立 target 目录、脚本与日志都放这里，每轮验收后由 BA 清理。

而这两条门禁的**唯一数据输入**也在同一目录，且：

- 该目录被仓库根 `.gitignore` 的 `/*` 规则忽略；
- `schema.json` **从未进入过 git 历史**；
- `tests/drop_rate.rs` 的注释自己就写着「文件被 gitignore，需自行准备」。

**后果：任何一次正常的临时文件清理，都会让这两条门禁失效。**

这不是假设 —— 2026-10-07 BA 清理 `.review-workspace/` 时就发生了。门禁随即因输入缺失变红，排查后确认与被测代码无关。

## 历史证据

`.review-workspace/audit-re10-baseline.log`（10-05 那轮审核留下的）显示：

```
Running tests/drop_rate.rs
test real_schema_drop_rate_report ... FAILED
```

即 **REQ-010 验收当时的基线就已经是红的** —— 说明在那之前已经发生过至少一次同类误删。这不是孤立事件。

## 为什么不能简单重建

仓库里确实有一份旧的 schema.json（`BA/demands/REQ-001-spike/spike/out-ful/schema.json`，09-30，已入库），但**不能拿来顶替**：

1. **格式过时** —— 缺 `TableMeta.column_count` / `commented_count`，当前代码反序列化直接失败；
2. **数据实质不同** —— 补齐字段后 `test_fk_naming` 卡在：
   ```
   37 条 customer_id 里有 33 条应当统一成「所属客户」
     left: 27    right: 33
   ```
   原因是旧副本里多出 `客户标识` 这类注释，而该测试判据二**明确禁止**出现这个显示名。

所以重建出来的是假数据。BA 已把尝试产物撤掉，让门禁恢复「输入缺失就大声失败」的诚实状态。

## ✅ 输入文件已找回（2026-10-07 23:55）

**不需要源库凭证。** 全盘搜索找到仓库里另一份**同源的真实勘查产物**：

```
code/out/e2e-schema.json    91 表 / 1051 列 / 219,688 B
```

| 特征 | 值 |

| `commented_column_count` | 681 / 1051 = 64.8%，与 `introspect.rs:44` 注释「约 64%」吻合 |

**指纹逐格命中** —— `tests/test_fk_naming.rs:1-20` 的文档表写死了 37 条 `customer_id` 的注释分布：

| 注释 | 文档记载 | e2e 实测 |

| `客户标识` | 10 | 10 ✅ |

已复制回默认路径 `.review-workspace/fix-props/schema.json`，**实跑确认两条门禁全绿**：

```

tests/test_fk_naming.rs  → 6 passed; 0 failed
```

丢弃率 8.0% 与 `drop_rate.rs:33-45` 文档记载的 8.4%（REQ-006 落地值）、10-05 实测的 7.8%（REQ-008 后）处于同一区间，判据 10% 未被触碰。

## ⚠️ 但缺陷本身没有修

恢复的文件仍然躺在 `.review-workspace/` —— 也就是**同一个按定义临时的目录**。下一次清理还会再丢一次。

而替代源 `code/out/e2e-schema.json` 同样被 `code/.gitignore:5` 的 `out/` 规则忽略，**也没有入库**。

两份都不可复现。这正是下面「待定问题」第 1 条要解决的。

## 待定问题

1. **schema.json 放哪？** 候选：
   - `code/tests/fixtures/schema.json` —— 与测试同仓，入库，门禁长期有效
   - `BA/docs/` 下 —— 但那是 demand 分支，测试从 `code` 分支读不到，跨 worktree 取用不便
   - 保持现状 + 重建脚本 —— 治标，每次清理后仍要手工重跑
2. **1MB 入库可接受吗？** 它是**脱敏元数据、零业务数据行**（源库只读保证的产物），但体积不小，且可能随源库变化而需刷新。
3. **若入库，如何保证它不过期？** 源库 schema 变了，门禁就会拿旧数据判绿 —— 这是**新的假绿风险**，需要一个「schema 变了就要求刷新夹具」的机制。
4. **门禁阈值是否需要重定基线？** `drop_rate.rs` 的 10% 上限与 80 表 / 900 属性下限是按「91 表 / 964 属性」定的。schema 刷新后是否仍合适，需要复核。

## 影响面

- 只影响 `drop_rate.rs` 与 `test_fk_naming.rs` 两条测试；
- **不影响**其余测试，也不影响产品代码；
- 但这两条恰恰是 REQ-006（形态处理器）与 REQ-008（外键命名）的**回归哨兵** —— 它们失效期间，这两块改动没有守卫。
