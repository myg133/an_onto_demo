## 2. 提案原文复述（负责人 2026-10-16 口述）

> **本节的准确性由负责人裁定。BA 对每一条的理解都写在括号里，请逐条判「对 / 不对」。**

### 2.1 终端区分

| 视图 | 形态 | 用途 | BA 括号理解 |
| --- | --- | --- | --- |
| **user view** | HTTP server + graph view | **只展示已构建好的本体的图关系**，不做操作入口 | （检查口，不是自助操作台） |
| **agent view** | skill / cli / mcp | **最终用户的运行时入口** | （最终用户通过 agent MCP 使用平台，不在构建时用） |

### 2.2 本体设计（只做三样）

1. **实体**（类型层）
2. **关联关系**
3. **rule**

> **明确不做的**：对象实例（实体实例）的存储

### 2.3 抽取与关联

1. **先通过非结构化数据**（各种文档、聊天对话等）：
   - 对**名词**聚类 → 抽出第一版实体
   - 对**动词**抽取 → action、function 等行动
   - 同时抽 rule、关系
2. **再通过结构化数据**（DB schema、API）对本体模型进行**验证与关联**：
   - DB 关联本体相关部分
   - API 接口关联 action、function 等行动
   - 这类数据放到**实体的 metadata** 中
   - join 等关联放到**边**里面

> ⚠️ **BA 注意到的术语冲突**：v1 规格里「元数据」= **使用痕迹**，且明确「不进本体」
> （`SPEC:400`、`SPEC:782`）。提案里的「实体 metadata」指外键/绑定/来源。
> **同名不同义，v2 必须改名**（建议「绑定」或「落地信息」）。

### 2.4 整体逻辑（三步）

1. 非结构化文档 → 抽本体、关系、规则
2. DB schema → **验证本体**，同时构建 SQL 和 API 到 metadata，关联到本体
   （可能涉及多种数据库：**一个本体可关联到 OA 系统、ERP 系统等**）
3. **执行过程 · 推理层**：通过实体等 metadata，计算出需要执行的
   - **SQL 查询（检索类）**
   - **API 调用（行动类）**
   
   **在推理层直接去执行。**

### 2.5 身份与权限（2026-10-16 追加澄清）

- 最终用户**通过 agent MCP** 使用平台，不是构建时
- **本体平台自己做 SSO**，并**打通与其他系统的权限**
- 用户 agent 接入后，才**代表一个真实对象**
- **写操作（API）按当前操作人员的权限调用**
- **审核逻辑不变**
- **写逻辑永不走 DB**（只走 API）

> **BA 括号理解**：平台持有自己的服务凭据 + 一张权限映射，而不是转发用户 token。
> 「用户在系统之中」= 权限建模进本体视野，不另起一套外挂 RBAC。

## 4. BA 的理解修正（**需负责人逐条确认或否决**）

> 本节是 BA 对提案的**推断**，不是负责人的原话。若理解有误，§5 的代价分析会跟着失真。

### M1 · 「先非结构化、后结构化」= **权威性顺序**，不是执行顺序

- **负责人说的是**：非结构化**定义**实体，结构化**验证与绑定**
- **BA 读成**：两个抽取器**并列生产**，产出进同一个提案通道；差别在**谁有否决权**
- **代码依据**：`src/agent/orchestrate.rs` 已是「分组 → 逐组抽取 → 阶段 2 验证 → 组装提案」，
  且 `agent/` 下已有两个同构 `ExtractionAgent` 实现 ⇒ **加 unstructured 是同构扩展，不是新管线**
- **收益**：这样 §4.3.1 的双轨审核、快照、冻结**一个字都不用动**

⚠️ 若负责人本意是**物理上先跑完非结构化再跑结构化**，成本会显著上升。请明确。

### M2 · 「用户是本体对象」需拆成三层，否则会撞上冻结语义

| | 内容 | 生命周期 | 进快照？ |
| --- | --- | --- | --- |
| ① | 「客户」这个**类型存在** | 跟版本走 | **是**（抽取 + 双轨审核得出） |
| ② | 「此刻是张三」**身份绑定**到某实例 | 每请求变 | **否** |
| ③ | 「张三能调 ERP 的哪个 API」**读写绑定** | 每请求变 | **否** |

**理由**：若权限写进本体，改一次组织架构就要走「提案 → 审核 → 冻结」——
不可接受。v1 规格 §4.6「切片 1 必须为 ActionType 占位」正是这条教训。

**需要补的新构件（唯一一个）**：**外部身份 → 本体 object key 的解析**。
SSO 登进来的 subject 怎么落到「客户」类型的某个实例上，现在完全没有。
⚠️ 这正是 `SPEC:2.3` 说的那类问题：「数据能告诉你"有什么"，不能告诉你"这算什么"」。

### M3 · 「按操作人员权限调 API」消掉了规格最大的那条反对

`SPEC:668` 反对自动写绑定的核心理由：

> 「给设备加了个状态字段」会**静默地**使某个 Action 从写 2 个系统变成写 3 个。**多写 = 误操作客户生产数据。**

但若调用用的是**操作人员自己的权限**：

| | 平台直连 DB 写 | 平台代操作人员调 API |
| --- | --- | --- |
| 平台持有的权限 | 一份平台自己的万能写权限 | **没有**，每次调用都是某个人的权限 |
| 加个字段的后果 | 静默获得新系统的写能力 | **得有人真的有那个权限**，否则调用失败 |
| 权限边界谁执行 | 平台要自己实现一遍 | **业务系统自己执行，平台不重复造** |

⇒ 平台从**特权写者**变成**委托执行者**。建议在 v2 里明确写成理由。

### M4 · 写绑定的形状要**作废重做**，不是扩展

现有 `WriteBinding` 是 DB 直写形状：`system / table / field / key_expr / conflict_field`。

走 API 需要：`endpoint / method / param_mapping / auth_context / **idempotency_key**`

⚠️ **`conflict_field` 乐观锁没有对应物** —— DB 条件更新能原子判冲突，API 不行。
**幂等性从「次要问题」升级为「必须设计」。**

### M5 · 「不做对象实例」其实现状已经符合

`object_types` / `link_types` 本来就只存类型与关系，**不存实例**（§3.4 G11）。
提案在这条上是**往前一步**（实例改为按需物化），不是改结构。

## 5. BA 不同意 / 要付的代价的地方

> 本节是**异议**，不是结论。负责人可全盘否决。

### X1 · 规则必须进提案通道，否则就是铁律禁止的东西本身

提案把 rule 列为一等公民。规则是**唯一由机器产生、又直接决定执行路径**的东西。

`SPEC:484` 铁律：「**没有任何未被人审核过的自动化结论，允许出现在查询上下文里。**」

规则不经审核就驱动 SQL/API = 铁律禁止的东西本身。
而 `SPEC:907` 对规则层的态度是「**之后再定结构**」⇒ **这个结构现在还没有。**

⚠️ 本提案真正的风险不在架构，在**规则本身没地方放、也没人审**。

### X2 · 实例按需物化会打破封闭世界契约

v1 的核心卖点（`SPEC:1.1` / `SPEC:6.5`）：

> 「这台设备没有工单」| 本平台答「**确定没有**」 | OWL 只能答「未知」

「确定没有」要求**实例完整**。按需物化的实例**不完整** —— 没查到可能是真没有，也可能是这次没解析到。

⚠️ `SPEC:109` E 表把这条列为**能力边界且当卖点卖**。现在这个卖点在松动。

⇒ 需要显式区分：**哪些类型保证完整、哪些不保证**。这个区分必须进模型。

### X3 · 按 metadata 生成 SQL = 全新安全面

现状：3 处 `format!` 拼 SQL，表名列名**全硬编码**。
改成按 metadata 生成 ⇒ **引入规则/LLM 产出的 SQL 进数据库执行** = SQL 注入面。

必须配套：参数化 + 表列白名单 + 生成结果的静态检查。**v1 规格完全没有这一块**，因为它不生成 SQL。

### X4 · 级联深度与成本不可控

一次业务问题可能触发：查客户 → 查该客户订阅 → 查每条订阅的扣费 → ……
**串行依赖**，每步等上一步的 key。91 个类型各有绑定，一次问答的真实成本可能不是「一次查询」而是「一串查询」。

⚠️ 必须在设计阶段算清，否则线上炸。

### X5 · 可复现性

`demo3` 第 2 版冻结于 10-12，里面的实例数据永远停在那一刻 —— 这是快照的价值。
按需物化没有这个问题，但**用户 3 月问「当时这个数是多少」，现在重查可能变了**。

⇒ **中间路线**：类型层轻（提案要的）+ 物化结果带时间戳缓存。
平时按需查；已签字的结论、被引用过的实例物化留存。查询优先读缓存，过期回源。
