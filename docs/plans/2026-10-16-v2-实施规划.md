## 一 · 这个规划的核心判断

v2 有 **8 项待拍板决策（D1–D8）**，其中 **D2（规则所有权与审核）是硬门槛**。
按「被决策阻塞」一刀切地排队，会得出「什么都干不了」的结论 —— **这是错的。**

逐阶段核对依赖后的实际情况：

| 阶段 | 依赖决策 | 能否立刻开工 | 说明 |
| --- | --- | --- | --- |
| **1 · user view** | 仅 D4 影响节点显示 | **✅ 能** | D4 可延后，默认「不标完整性」，事后补是纯增量 |
| **4 · 动词维度** | 无 | **✅ 能** | 纯扩类型系统 + 审核面，与推理层无耦合 |
| **2 · 读绑定** | D3 | **🟡 大部分能** | `ReadSpec` 枚举同时容纳 SQL 与 API；D3 只决定默认走哪条 |
| **3 · API 写绑定** | D1 才能测权限 | **🟡 能** | 先做无权限版本，D1 落地后补测 |
| **5 · 非结构化 agent** | 依赖阶段 4 的 kind | **🟡 排在 4 后** | 同构扩展，非新管线 |
| **6 · 推理层** | **D2 硬依赖** + D4 D5 D7 | **⛔ 阻塞** | D2 不定 ⇒ 规则就是「未签字的自动化结论」 |

**⇒ 六个阶段里四个可以立刻开工，只有一个被真正阻塞。**
**关键路径不是编码，是「D2 什么时候拍板」。**

## 四 · 逐阶段详述

### 阶段 1 · user view（REQ-093 → REQ-094）· P0 · 无依赖

**目标**：把「双轨审核里客户过目」这一条从「看一个文本文件」变成「看得懂的图」。

| | |
| --- | --- |
| **为什么排第一** | 复用最多（`CustomerView` + 守门器 + `html_view.rs` + `object_types/link_types` 全部原样复用）、**不动抽取内核、不碰安全网**，且它是后面每个阶段唯一的检验手段 |
| **交付物** | `server/http.rs` + `server/sso_middleware.rs`（最小版）· `domain/graph.rs` 纯函数 · `/api/graph` 返回节点与边 · graph view 前端 |
| **验收要点** | ① 图内容与 `ontok ontology overview` **逐条对得上**（节点数、边数、属性数）② 建模术语守门器**在 HTTP 路径上同样生效**（不能因为换了出口就绕过）③ **只读**：任何变更动词一律拒绝，且有测试钉住 ④ 身份门（未登录拿不到数据） |
| **红线** | `domain/` 零 I/O 仍是硬验收；`src/domain/view.rs` 不得改（它是 `CustomerView` 的真身） |
| **风险** | ① **把本体库经 HTTP 暴露而系统零身份** ⇒ 必须带身份门，这不是「先上线再补」的 ② 前端图布局性能（91 节点 / 79 边客户端力导向够用，超千级需另议） |
| **可延后** | 完整性标记（D4）—— 先不标，REQ-098 之后再补，是纯增量 |

---

### 阶段 4 · 动词维度（REQ-098）· P0 · 无依赖

**目标**：让「动词 → action / function」在类型系统里真的存在。

| | |
| --- | --- |
| **为什么排这么前** | 阶段 5 与阶段 6 的**共同前置**。先做它，后面两个阶段才能接上 |
| **交付物** | `ItemKind` 加 `AddActionType` / `AddFunction` 两个变体 · 提案校验放行 · 双轨审核 UI 能处理这两类 · `CustomerView` 投影 · MCP tools · 快照写入 |
| **验收要点** | ① **六个联动点逐个有测试**（少一处的症状是「能存不能看」或「能看不能 apply」）② `action_types` / `functions` 两表的**写入路径真的被跑到**（QA 必须构造样本证明从提案到落库全通，不能只看 DDL 在）③ 双轨审核能对这两类**独立表态** ④ `tests/test_no_write_path.rs:62-63` 那两条 `is_empty()` 断言**如何处置要有明确结论**（分档放开，不是一次删掉） |
| **红线** | `src/domain/view.rs` / `src/domain/review_view.rs`（建模术语黑名单所在地）**禁改** |
| **风险** | **本项目已吃过同款亏**：`action_types` 的 DDL 在、领域类型在、就是没人往里写 ⇒ 「DDL 占位 ≠ 功能可用」，QA 必须验数据真的落了库 |

---

### 阶段 0 · 身份与规则机制（REQ-099 → REQ-100）· 决策 + 少量编码

> **这是整个 v2 唯一真正的门槛。**

| | |
| --- | --- |
| **REQ-099（D1）** | SSO subject → 本体 object key 的解析。落点 `server/sso_middleware.rs` + `db/identity_store.rs` |
| **REQ-100（D2）** | **规则由谁写、谁审、变了怎么办**。落点 `domain/rules.rs` + `db/rules_store.rs` |
| **为什么阻塞** | 规则是**唯一由机器产生、又直接决定执行路径**的东西。不经审核就驱动 SQL/API = v1 铁律 `SPEC:484`「没有任何未被人审核过的自动化结论允许出现在查询上下文里」禁止的东西本身 |
| **验收要点** | ① 规则**必须**有与本体同等的审批状态流转（草稿/待审/生效/作废）② 规则变更必须留痕 ③ **未生效规则不得被推理层读到**（有测试钉住）④ 身份解析有明确的失败路径（解析不出 object key 时**拒绝执行**，不猜） |
| **不做** | 这一阶段**不写推理层**，只把「规则怎么被管起来」和「身份怎么落到本体对象上」定死 |

---

### 阶段 2 · 读绑定（REQ-095）· P1

| | |
| --- | --- |
| **交付物** | `domain/binding.rs`（纯函数）· `ReadSpec` 枚举（同时容纳 SQL 与 API）· `object_types` 加 `source[]` · `db/binding_store.rs` · 补 v1 规格 `SPEC:645` 的悬空引用 |
| **验收要点** | ① 每个绑定**显式标注走哪条路**（SQL / API），不许有「默认路径」这种看不见的东西 ② 绑定的表/列/API 路径**能在真实源库上跑通**（不是构造样本）③ 覆盖率可数：哪些类型**没有**读绑定，要能被列出来 |
| **依赖** | D3（读路径）**只影响默认走哪条**；枚举两种都容纳，所以不阻塞开工 |
| **风险** | 现有源库**外键 0 条**，关联能力全靠列名后缀约定 —— 绑定质量直接受限于此，验收时要如实报覆盖率 |

### 阶段 3 · API 写绑定（REQ-096 → REQ-097）· P1

| | |
| --- | --- |
| **交付物** | `domain/authorization.rs`（权限判定纯函数）· API 绑定（`endpoint/method/param_mapping`）· `db/identity_store.rs` · `runtime/exec_api.rs` |
| **关键变更** | **作废** `WriteBinding` 的 DB 直写形状（`system/table/field/key_expr/conflict_field`） |
| **验收要点** | ① **写路径只走 API，有测试证明不存在任何写 DB 的分支** ② 权限判定是纯函数、可单测：越权必然拒绝 ③ `Idempotency-Key` 重复提交**只生效一次**（有测试） ④ 每次执行留审计：`operator + 端点 + 动作 + 结果` |
| **风险** | ① `conflict_field` 乐观锁退役后**没有对等物**，幂等必须自己扛 ② 拆 `test_no_write_path.rs` 时**必须分档**：每放一档补一条新断言 |
| **依赖** | D1 未定前可先做**无权限版本**，身份落地后补测 |

### 阶段 5 · 非结构化抽取（REQ-101）· P2 · 依赖 REQ-098

| | |
| --- | --- |
| **交付物** | `agent/unstructured.rs` —— **第三个** `ExtractionAgent` 实现 |
| **为什么不是新管线** | `orchestrate.rs` 已是「分组 → 逐组抽取 → 阶段 2 验证 → 组装」骨架，`rule_based` / `acp` / `llm` 已是同构实现 ⇒ 加一个是**扩展** |
| **验收要点** | ① 声明 `CAPABILITY_PRODUCES_PROPOSAL`（否则编排入口直接拒绝，这是 fail-closed 设计）② 抽取失败**不得静默跳过**，失败组必须进 `failed_groups` ③ **与 DB 抽取并列**，不替换 ④ 合并验证：非结构化提的实体在 schema 里找不到对应物时**被否决** |
| **风险** | 文档/聊天里的实体名与 DB 表名对不上 ⇒ 合并验证的召回率会成为真瓶颈，验收要报实测数字 |

### 阶段 6 · 推理层（REQ-102）· P2 · **被 REQ-100 阻塞**

| | |
| --- | --- |
| **交付物** | `domain/rules.rs` `domain/sqlgen.rs` `domain/integrity.rs` · `runtime/reasoner.rs` `runtime/exec_sql.rs` `runtime/authz.rs` |
| **切分理由** | ①②③ 在 `domain`（纯函数，可单测、可用构造样本做变异自证）；只有 ④ 执行在 `runtime`（可 mock） |
| **验收要点** | ① **规则求值 / SQL 生成 / 权限判定**三层各有构造样本自证（不连库）② 生成 SQL **表列白名单强制**，白名单外标识符直接拒绝、不做转义兜底 ③ **只读先行**：本阶段不含任何写执行 ④ 级联深度与单次问答成本**有实测数字** ⑤ 未生效规则不可达 |
| **依赖** | **D2（REQ-100）不落地，本阶段不得开工** —— 否则等于在实现 v1 铁律明令禁止的东西 |
| **未决** | D4（完整性表达）· D5（缓存与可复现）· D7（SQL 安全边界深度） |

## 六 · 贯穿全程的纪律（继承自 `dispatch/rules.md`）

每个 REQ 的 briefing **必须携带**下列条目原文（纪律 M：规则只在 briefing 里出现才对子 agent 生效）：

| 纪律 | 内容要点 |
| --- | --- |
| **A–K** | 禁 `ls-files -c` 误用 / 禁 `\b` 统计中文 / 变异回滚必 `touch` / `.review-workspace/` 入 gitignore / 零命中先怀疑扫描器 / 「不存在」是异常值 / **变异必须三元组（sha256+patch+条数）** / 忠实重复实现抓不住，登记为限制 / 每次命令自带 `cd` / 禁 `2>/dev/null` / skip-worktree 对照须用 `git show HEAD:` |
| **L** | 报「环境不具备」前先查变量**来源**（`.env` 在仓库根，worktree 里找不到是正常的） |
| **M** | briefing 必须携带纪律原文 |
| **N** | **建 worktree 后第一件事**：重放 skip-worktree 位 |
| **O** | **基线必须绑 commit**：全量数字写成 `passed/failed/ignored @ <hash>` |
| **P** | 证据输出里的无关噪声要单独立项清掉 |
| **红线** | `tests/drop_rate.rs` / `tests/test_fk_naming.rs` / `src/domain/view.rs` / `src/domain/review_view.rs` 禁改；无测试删除、无 `#[ignore]`、无断言放宽 |

## 七 · 本规划明确不做的事

| 不做 | 理由 |
| --- | --- |
| 不推翻现有 `object_types` / `link_types` 结构 | 现状已符合「不存实例」，不需要重做 |
| 不重写 `domain/view.rs` / `html_view.rs` / `overview.rs` | 原样复用，`domain/graph.rs` 只是它们的第二个投影 |
| 不动现有 5 个 MCP 工具的语义 | 只**增加**工具；已有的是对外契约 |
| 不在阶段 6 之前做任何写执行 | 写必须先有审核机制（REQ-100） |
| 不给 `db/` 的新 store 抽 trait | 沿用 `db/mod.rs` 已定的「只有一个实现时抽 trait 是过早抽象」 |
| 不在这一轮重跑 §8.2 决策清单 | REQ-032 是 v1 的验收前置，与 v2 方向无冲突 |
