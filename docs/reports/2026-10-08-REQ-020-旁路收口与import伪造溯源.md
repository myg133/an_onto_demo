## 一、缺口 1 · `pub` 旁路收口

Dev 的三个入口处置：

| 入口 | 处置 | 验证 |
| --- | --- | --- |
| `propose::extract_with_context` | `pub` → **`pub(crate)`**（`propose.rs:280`） | ✅ QA 用编译错误证明 |
| `RuleBasedAgent::propose` | `pub` → **`#[cfg(test)] pub(crate)`**（`rule_based.rs:122-123`） | ✅ `E0599` 证明 |
| `propose::extract` | **仍 `pub`**（`propose.rs:215`） | 红线调用，无法收窄 |

### QA 的编译错误原文

```
error[E0603]: function `extract_with_context` is private
   --> tests/qa_probe_visibility_tmp.rs:2:30
280 | / pub(crate) fn extract_with_context(

error[E0599]: no method named `propose` found for struct `RuleBasedAgent` in the current scope
  --> tests/qa_probe_visibility_tmp.rs:20:19 |   agent.propose(&SchemaReport{}, "p");
```

> `E0599` 是关键证据：集成测试链接的是**不带 `cfg(test)`** 的 lib，
> 所以 `propose` 连测试构建下都不存在 —— **不是文档措辞，是编译期事实**。

### 「红线无法收窄」的理由成立

```
tests/drop_rate.rs:26 import + :95        extract(&report,&names,"dropprobe",…)
tests/test_fk_naming.rs:42 import + :108  extract(&schema,&names,"fk_fix","test","test")
```
两文件在 `tests/` = crate 外独立编译。它们传的是 `"test"` / `"dropprobe"` / `"fk_probe"`,
**任何能放行它们的闸门等于放行任意字符串**。

### 迁移后判据强度未变弱（QA 程序化 diff）

| 测试 | 结果 |
| --- | --- |
| `test_rule_based_agent_output_is_byte_identical_to_legacy_extract` | 唯一差异是 `agent.propose(...)` 的 **rustfmt 换行**；5 条断言全保留 |
| `test_extraction_stats_fields_are_untouched` | **逐行完全一致** |
| fixture（`NAMES_JSON` / `schema()` / `col()` / `table()`） | 逐行一致 |

QA 专门回答了「搬进 `mod tests` 是否获得原本没有的能力导致判据变松」：
**不成立** —— 断言调的 `extract` 是 `pub`（任何构建可见），**不是**任何 cfg(test) 专属符号；
迁移是**被迫的**（`E0599` 已证明 crate 外调不到）。

**净增量非减量**：新增 2 条判据，且**故意不断言 `extract` 是 pub**，避免把临时状态钉死。

## 四、QA-B 架构评估 → 升级为 ADR-003

Dev 报的「`propose import` 可伪造溯源」经 QA-B **独立实测复现并从库里取证**：

```
proposals.extracted_by          = {"agent":"totally-not-a-real-agent", …, "failed_groups":["payments","risk"]}
ontology_versions v2.extracted_by = 同上      ← apply.rs:260-263 直写，一路传染
```

**QA-B 修正了 Dev 对性质的描述**（两处偏差会误导排优先级）：
1. **不是「绕过」闸门，是压根在闸门之外的第四条路** —— REQ-019/020 都没漏检
2. **不是安全漏洞** —— 触发者本就有写库与 `accept-all`，不构成权限提升

**QA-B 找到 Dev 与 QA-A 都没提到的最硬论据**：

```bash
$ ontok concept import --file concept_fake.json
✗ 改内容必须改版本：当前内容指纹 51b8689d… 与版本 9.9.9 记录的不一致
exit=1                                    ← 挡住了

$ ontok propose import --file fake_real_items.json
exit=0  静默入库                          ← 唯一漏网
```

⇒ 定位为「**补齐 `concept import` 已有的纪律**」，不是「新增安全机制」。
论证基础是**内部一致性**，ADR 评审更容易过。

**另发现 Dev 的 PoC 本身是错的**：`"items":[]` 会被 `proposal.rs:114-116` 的
`NothingApplicable` 挡下，跑不通。换成真实 item 才复现成功。

## 五、BA 的两处裁定

### 裁定 1 · B-1（`propose::extract` 仍 pub）：**不改红线**

QA-A 把这条列为需 BA 拍板。理由：

- 关掉它**并不关闭假溯源** —— import 那条门才是主路。少一扇门不是关门。
- 动红线会把它和 REQ-018 纠缠：那两条测试读 `.review-workspace/fix-props/schema.json`，
  迁进 crate 后相对路径基准会变，而那个文件**根本不在仓库里**。
- 归属上是继承性缺口（REQ-003 起就 `pub`），不是本 REQ 引入。

⇒ **放行，记为已知限制。**

### 裁定 2 · ADR-001 不动，另立 ADR-003

ADR-001 全文 74 行**没有回答**「谁来保证不是编的」，但它的逻辑自洽：
它规定的是**取值口径**，「提案自己知道」这个前提它并未声称要担保。
**改 ADR-001 反而越界。** ADR-003 补的正是它没写的那一格。
