本体论平台设计规格

本体是运营层，不是分析层。抽取把发现成本从「几周」压到「几分钟」，但不承担决策责任——骨架是抽出来的，物种是定义的。

A

核心赌注

五条，全部设计决策的依据。每一张都写明了「押不起怎么办」——这是这份规格最不像 PPT 的地方。

§2.3 人比 LLM 更会「定义」，LLM 更擅长「发现」 让人凭空写出对象类型他写不出来；给一份候选，他一眼能说「这不对，我们管它叫 XX」。 押不起：真实客户连候选都判断不了 ⇒ §2.3 前提不成立，这是第一个要验证的假设
§8.3 双轨审核撑得住「客户审不了建模、FDE 审不了业务」这个夹缝 客户看主键会随便点通过；FDE 替客户判断业务等于没审。 押不起：审核退化成盲审 → 证据链失效 → 整条链崩
§8.4 收敛靠「快照 + 增量 diff + 冻结」，不是靠模型更聪明 每轮重新生成必然振荡。 押不起：无退路 —— 这是唯一一条没有兜底的赌注
§9.3 客户签字的判据是「能回答我的业务问题」，不是「有写回」 问答价值先于写回价值。 红线：切片 2 不得再顺延
§2.5 本体难以跨项目复用，所以不做行业模板 只有一个样本时做抽象，抽出来必然是那家客户的怪癖。 押不起：做了 5 个同行业项目后再回头归纳
§2.3

抽取结构，人定义语义

这是本平台与 Palantir 的分野，也是全文唯一一处用画面讲清楚的地方。

LLM 能做的 · 抽取
从地层挖出骨头、拼出骨架
把发现成本从「几周」压到「几分钟」。
人必须做的 · 定义
这是什么物种、要不要进展厅、叫什么名
需要馆长签字。抽取不承担决策责任。

具体例子：t_dev t_device_info dev_backup 三张表，字段重叠但不完全相同。若它们是设备生命周期的三个阶段，应建 3 个类型 + Link；若只是历史遗留的冗余拆分，应合并成 1 个类型。 这两种判断所依据的数据长得一模一样——决定它的是业务语义，不是数据形态。

§4

系统架构

客户环境与 SaaS 之间只传「实体 + 关系 + 证据」，原始数据留在客户域内。

客户环境（内网）
数据库结构化
m365 / 文件非结构化
IM 数据对话式
日志 / 报表使用痕迹
采集器 Collector轻量容器 · 本地抽取
实体 + 关系 + 证据（出站 TLS） · · · 使用痕迹（只喂抽取引擎，不产实体）
本体论平台（SaaS）
connector接入层 · 三类通道
元数据采集通道接入层
数据面 pipeline高频 · 自动 · 幂等
控制面 pipeline低频 · 需审核
抽取引擎产出只能是提案
ontology-store存储抽象层
agent-registry只服务建侧
mcp-server对外唯一出口
只读消费 —— 外部 agent 不经过 agent-registry
外部 agentClaude Desktop / Cursor / 自研

两个容易混的点：ontology-store 是存储抽象，GraphDB 只是实现之一，上层无感； agent-registry 与读本体的 agent 名字里都有 agent，但一个是造本体的、一个是读本体的，后者只经 mcp-server 进来。

§4.3

数据面与控制面必须分车道

进入 pipeline 的东西性质不同。混在一条流水线里的后果：无法区分「哪些变化需要人看」，以及本体结构一变是否触发历史数据重算变得不可控。

数据面
本体实例同步 · 高频 · 自动 · 幂等
connector 抽取→ 语义映射→ 本体实例写入
触发自动（定时 / 增量）
幂等是，可重放
需要人否
控制面
本体结构变更 · 低频 · 人工签字
KH Agent 抽取提案→ 双轨审核→ 版本快照 / 冻结
触发人工审核通过
幂等否，有语义后果
需要人是

本体变更后的历史数据重抽取，必须在图上显式表达（控制面 → 数据面的虚线），作为可观测、可审批的动作，不能靠流水线自然流动。

B

有意偏离（对外讲解时不必回避）

每一条都写明了代价与缓释——「有意」不等于「没有代价」。

偏离了什么我们的选择理由 · 代价 · 缓释
Palantir 的「动作先行」 POC 不含写回，推迟到切片 2 客户首轮签字判据是问答可用；写回需先解决权限与审计 §9.3
代价：交付物有沦为昂贵仪表盘的风险——报告警告的失败模式 #4，未消除、只是推迟
缓释：一页纸本体文档 + 决策清单驱动的问答演示（≥5 个业务问题）+ 呈现写回路线
OWL / SPARQL / SHACL 语义网栈 全部不进运行时 ① OWA 与封闭世界契约正面冲突 §6.5；② 团队仅一人、POC 目标一周；③ Palantir 自身也不用
缓释：内部用 LPG（Palantir 同源），出口处转标准；对照表已备
应用层推理 只读已冻结事实，推理结论一律进提案通道 未签字的结论没有责任人；推理直接进查询会拆掉「可测性」
缓释：规则引擎在生产阶段补，结论同样走审核
「涌现」→「抽取」 统一用「抽取」 「涌现」暗示模型自主发现真相，与「Agent 是提议者」矛盾 §3
缓释：术语变更已记档，勿改回
抽取能力自建 通过 A2A 协议调用外部抽取 agent ① 市场已归纳过这方法，不必等我们做满 5 个项目；② 主动让出编排，换取「验证与决定」牢牢在手
代价：引入版本漂移、静默失败、成本不可控、数据出域四类新风险
缓释：四项强制义务 —— 版本冻结 / 失败可见 / 成本闸门 / 出域逐案确认
D

必须守住的红线

这些不是建议，是违反即设计失效的约束。共同主题：现在不做，将来要推翻重来。

切片 1 必须为 ActionType / Function 占位 §4.6
违反后果：切片 2 引入时必须改快照契约、diff 引擎、apply、双轨视图——推翻重来
切片 1 必须为 parent / disjoint_with 占位 §4.6
违反后果：层级变更还要改 diff 语义——不是普通修改，是「重挂子树」
Agent 不得直接写生产本体 §2.2 §4.3.1
违反后果：平台自我否定——整个可信度地基塌掉
所有自动化结论只进提案通道 §4.3.1
违反后果：未经签字的语义进入查询 → 「可测性」崩塌
阶段 2 证据验证不可外包 §7.1
违反后果：若连「依据是否属实」都由 agent 自判，「Agent 是提议者」就空转了
切片 2 写回时身份不确定 → 必须拒绝 §5.4
违反后果：改错客户生产数据。这是事故，不是体验问题
一轮抽取内锁定 agent 版本 §8.4
违反后果：中途换版 = 换了输入，收敛判定作废
抽取失败不参与收敛判定 §7.1 §8.4
违反后果：静默失败会把「什么都没抽」误判成「已收敛」
§9

切片路线

按「多快能证明价值」排序，而非按功能完整性。

  1. 切片 1 · 只读闭环目标：一周内可演示，且真能用
    仅支持一种数据源（PG / MySQL）→ LLM 内省表结构 + 真实行样本 → 候选本体 → 双轨审核 → 落库 → mcp-server 暴露查询工具 → Claude Desktop 接上即可提问。
  2. 切片 2 · Action 写回与审计运营层的分水岭
    客户续约的理由。实现成本远低于实体对齐，所以排在切片 4 前面。
    红线：不得再顺延。若无法启动，必须回到规格重新评估是否收缩本体范围，而不是把 Action 永久推迟 §9.3
  3. 切片 3 · 对话式建模领域文档 + 使用痕迹
    补上「抽取质量」的缺失输入：缺领域文档时必猜错（风险 R4）。
  4. 切片 4 · m365 / IM 非结构化接入故意放最后
    实体对齐是无底洞——把文档里的「张三」对到数据库里的员工记录，能让人陷进去数月。
    切片 1 已能证明价值，不必陪它一起沉 §9.1
E

明确的能力边界

别让人误以为我们能做。这一节的存在本身就是一种诚实。

本体不推理
disjoint_with 只是审核提示 + 写入校验 + 导出，不是推理公理。不会从「A 与 B 互斥」推出「C 只能是 A 或 B」 §4.6
应用层不给「大概」
命中或明确失败，二值。「这台设备没有工单」我们答「确定没有」，OWL 只能答「未知」 §6.5
不改非结构化内容
IM / 文档不可被写回，只能作触发方与证据 §5.7
不保证跨系统事务
不追求「永不不一致」，追求「不一致一定能被发现并列出」 §5.5
标准导出有损
OWL 覆盖 3/4 根柱子的前两个 + 全部治理物；缺口集中在「动作」——语义网里没有这个位置 §6.5
数据治理不做
血缘 / 质量规则 / 元数据目录是另一个产品 §11
F

16 条风险，分两档

分档的依据不是概率，是最坏结果。

前 12 条
最坏结果是交付不达标。
收敛性审核疲劳采集器落地阻力 抽取质量过度抽取演示导向偏移 实体对齐阻塞动作缺失→仪表盘化
后 4 条 · 严重程度更高
最坏结果是改坏客户生产数据或无法解释 diff。全部由写回与外置带来。
外部 agent 版本漂移外部 agent 静默失败 成本不可控数据出域超预期

完整 16 条及缓解措施见 §12.2。

G

当前最大的未知

“
LLM 能否从真实客户库抽出客户认得的候选本体——
至今零验证。

全部计划覆盖的都是确定性工程（版本、diff、状态机、投影），而项目的核心赌注写在另一份计划里，一行代码没写。

治理机制救不了客户不认的本体。

建议先做 2 天 spike（一个脚本 + 一个 prompt + 一张真实库的 schema 与样本行 → 人工肉眼判断），再决定内核建多厚。见实现计划开头的顺序提示。
