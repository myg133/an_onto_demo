## 一、Dev 的并发结论被推翻（QA-A）

Dev 声称：`CREATE TABLE IF NOT EXISTS` 在 PG 里不是并发安全的，加 `pg_advisory_xact_lock` 后
「去锁 7/8 失败、带锁 8/8 通过」。

QA-A 跑了三档，每档 5 轮 × 8 并发 = 40 次：

| 档位 | 场景 | 带锁 | 去锁 |
| --- | --- | --- | --- |
| ① | 只建 registry 两表，空 schema | **40/40** | **40/40** |
| ② | **完整 `migrate()` 全量 DDL**，空 schema | **5/40** | **5/40** |
| ③ | 升级场景：9 张老表已存在 | **40/40** | **40/40** |

**每档带锁与去锁完全相同 —— 这把锁没有产生任何可测量的效果。**

原因：`migrate()` 里锁只包住第 3 个 batch（registry），`SCHEMA`（9 表）与 `SCHEMA_PATCH`
（2 条 ALTER）在锁**之外**先跑。Dev 的两个数字都复现不出来：8/8 只出现在①③档（那里去锁也 8/8），
7/8 失败只出现在②档（那里带锁也 5/40）。

> ⚠️ **代码本身无害、无回归。** 问题在结论表述与文档，不在行为。

## 六、QA-B 的 F1–F4（已转 REQ-014）

### 🔴 F1（最重）阶段 1 与阶段 3/4 **已经**存在实打实分歧，不是未来风险

设计要求一表一组。实测：

```
全作用域: t_dev.t_customer_id → 「所属客户」  ← 关系推导
一表一组: t_dev.t_customer_id → 「客户标识」  ← 注释回落
```

同一列、同一 schema、同一实现，**两个作用域两个名字**。根因链：`extract_group` 用
`group.to_schema_report()`（`group.rs:146` `tables: self.schema.clone()` = 组内表）→
`extract()` 据此建 `known_tables` → `infer_link` 要求 `known.contains(cand)`（`propose.rs:847`）
→ 组外 FK 目标不在 `known_tables` 里 → 关系推不出来 → 属性名回落。

**且零测试发现**：QA-B 把 `to_schema_report` 收窄到首表（= 设计的真实分组）后，
**22/22 全绿逃逸**。

Dev 自述的「阶段 1 与阶段 3/4 今天无分歧」**是错的**；「没有任何东西把它们钉在一起」是对的，
但比自述更严重 —— **已经漂了，且无人看守**。

### 🟡 F2 抽象层名义可插拔、管线未接通

六个关键件全部**零生产调用点**：`ExtractionGroup` 构造 / `derive_group_id` / `drive_group` /
`verify_mappings` / `failed_groups()` / `dyn ExtractionAgent`。

生产入口 `src/bin/ontok-propose.rs:123` 构造**具体类型** `RuleBasedAgent` 并调用
**不在 trait 里**的固有方法 `propose()`。缺 factory（`fn build_agent(&AgentRegistration) -> Box<dyn ExtractionAgent>`）与编排入口。

### 🟡 F3 设计点③「可演示」而非「生效」

`verify_mappings` 实现了但**未接入任何生产路径**，不存在「agent 声明 → 代码核对」的闭环。

### 🟡 F4「key 稳定」是注释而非机制

无代码或测试钉住 `ExistingType.key` 不可变；`verify_mappings` 反而允许 key 打错（只报错不丢弃）。

### ✅ 阶段 2 未外泄（正面结论）

agent 侧 grep `confidence|self_check|verified|is_valid|self_report` **零命中**；
`RuleBasedAgent::extract_group` 不调用 `verify_mappings`；trait 无 verify/validate 方法；
`GroupExtraction` 无 Link。规格「外置『怎么想』，不外置『想得对不对』」守住了。

## 十、过程透明（BA 自责）

**BA 把两个 verifier 派进了同一个 worktree。** 两个会话同时对 `src/db/agent_registry.rs` 与
`src/agent/group.rs` 做变异测试，QA-A 的基线指纹 `group.rs = 67223789…` 实为对方 MUT4b 的中间态，
靠与对方的 `RESTORED_SHA` 交叉比对才发现。**差点让「并发安全的对照数字」取自被污染的源码。**

已写入 `BA/dispatch/rules.md`：**1 worktree = 1 写入者**；拆 agent 必须各给独立 worktree，
否则串行派。另加一条：子 agent **禁用冷编译**（此前两个 verifier 会话先后死在冷编译上，
一次吐 2393 个构建产物文件、638M 后会话消失，输出全丢）。

QA-A 同时如实交代：它第一次全量跑出现的 `ConnectionReset` **是自己的探针**造成的
（一次开 16 连接 × 多轮 × 多池），已隔离不计入。
