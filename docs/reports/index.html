01这一版的核心取舍

如果只有五分钟，把下面这五条记住 —— 它们决定了整套系统在赌什么、以及赌不起什么。

赌注WHAT WE BET ON

人比 LLM 更会「定义」，LLM 更擅长「发现」。
让人凭空写出对象类型他写不出来；给他一份候选，他一眼能说「这不对，我们管它叫 XX」。 抽取把发现成本从几周压到几分钟，但不承担决策责任。

有意偏离DELIBERATE DEVIATION

POC 不含写回，推迟到切片 2。客户首轮签字的判据是「能回答我的业务问题」。 代价是交付物有沦为昂贵仪表盘的风险 —— 这个风险没有消除，只是推迟。

不做WHAT WE REFUSE

不用 OWL / 推理栈，不做行业模板，不跨系统编排。 开放世界假设与我们的封闭世界承诺正面冲突；只有一个样本时做的抽象必然是那家客户的怪癖。

红线NON-NEGOTIABLE

Agent 不得直接写生产本体；所有自动化结论只进提案通道；写回时身份不确定即拒绝。 违反即设计失效 —— 客户签字的意义会消失，可测性会崩塌，最坏会改坏客户生产数据。

最大未知THE OPEN RISK

LLM 能否从真实客户库抽出客户认得的候选本体 —— 至今零验证。 全部计划覆盖的都是确定性工程，而核心赌注还没写一行代码。 治理机制救不了客户不认的本体。

02选哪一张

功能面架构 FUNCTIONAL PLANE 老板 / 产品 / FDE

回答：FDE 拿这套平台怎么完成一次交付？
七个业务功能域 + 一条从建项目到客户签字的完整旅程。主视觉是「FDE 在做的事」，不是「平台有的东西」—— 全文不含任何技术选型词。给老板和客户看，用这一份。

9 节 · 含 POC 与生产对照 · 含已明示的有意偏离
能力面架构 CAPABILITY PLANE 老板 / 客户 / FDE

回答：平台对外能做什么？
建、审、用、动四件事，加一条纵切「溯」。是功能面的抽象视图——它把「建」当成一个动作， 功能面拆成四步，因为 FDE 干这四件事时用的是四套界面、见的是四批人。

9 节 · 含本体核心底座（对象 / 关系 / 动作 / 函数）
组件面架构 COMPONENT PLANE 工程师 / 交付

回答：系统由哪些模块组成？
采集器、connector、pipeline、ontology-store、mcp-server 的职责与边界。 客户数据在内网、平台在公网，这条硬约束决定了整套架构的形状。 开发看这一份。

04维护规则

三条硬规则

1 · 事实变更只改设计规格，随后同步受影响的 HTML 汇报。

2 · 汇报里出现设计规格没有的判断，视为缺陷，以设计规格为准。

3 · 实现计划与设计规格冲突时，改计划，不改规格。

文档格式约定

设计用 md —— docs/design/ontology-platform-spec.md，可 diff、可 grep、适合工程协作。

汇报严格用 HTML —— 本目录下全部为自包含单文件，零外部依赖（含字体、样式、图），可离线双击打开，也可直接作为汇报材料投屏或分发。

052026-09-28 本次修订

三份文档此前各自演化，已出现互相矛盾之处。本轮把事实收敛到单一来源，并修掉三处硬矛盾、补三个缺口。

处置内容
修 · 使用痕迹口径 此前「读使用痕迹」被列为 connector 能力标签，又在别处声明「使用痕迹不是 connector」—— 自相矛盾。现统一：能力标签只有四个，使用痕迹是与 connector 平行的第二条输入通道。
修 · POC 审核门槛 此前一处要求「客户独立完成业务轨审核」，另两处写「单轨代签」—— 与会议「不得设置过高人员能力要求」直接冲突。现统一为：建模轨 FDE 全责，业务轨客户侧可代签但须过目、代签须留痕，客户签字仍是冻结的必要条件之一。
修 · 明示有意偏离 参考方法论主张「动作先行」，本项目 POC 不含写回。现已把理由、代价、缓释与红线写进文档——这是有意识的决策，对外讲解不必回避。
补 · 决策清单入口 新增 ⓪ 决策清单 作为范围闸门：先定「本轮服务哪条决策」，再决定抽什么。防止过度抽取，也让收敛有业务边界而非数据量边界。
补 · 本体核心模型 四根柱子（对象 / 关系 / 动作 / 函数）+ 三件治理物（版本 / 提案 / 证据）首次进入设计规格，并明确 ActionType 与 Function 在切片 1 必须占位，否则切片 2 会推翻切片 1。
补 · 实体对齐降级 多源对同一实体定义不一致时怎么办：收窄到单库 + 显式声明未解边界 + 转生产阶段立项，禁止临时硬合并。
定 · 抽取能力外置 产出候选的生成能力通过 A2A 协议调用外部抽取 agent——抽取的「方法」是市场已归纳过的东西，不必等我们做满 5 个项目。但证据验证与治理留在我们手里：外置「怎么想」，不外置「想得对不对」。配套三项义务：agent 版本冻结进快照 / 失败必须可见 / 成本闸门。
补 · 写回设计 写回对象是「某系统里某行的某个字段」，不是「本体」。三条硬规则：写比读严（身份不确定即拒绝）、哪些系统被写必须显式声明、不一致不消除只让它可被列出。
补 · 类的结构 本体类不是扁平的：parent 表达「是一种」的层级，disjoint_with 表达类型互斥。同时补上术语别名 aliases[]——客户叫法与数据库字段名的翻译表。
一处术语变更

2026-09-24 初版曾用「涌现」描述抽取过程，后统一改为「抽取」。

理由：「涌现」暗示模型自主发现了真相，与「Agent 是提议者不是决定者」矛盾；「抽取」只承诺捞出候选物，与提案制自洽。勿改回。

本次修订的落点

所有事实只写一遍，在 设计规格里；本目录下的三张图是它的投影。

读法：老板与客户 → 功能面 · 平台能做什么 → 能力面 · 模块与边界 → 组件面。三者冲突时以设计规格为准。
