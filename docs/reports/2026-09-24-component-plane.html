02三条关键点

图上信息量最大的是三条线，不是那些框。

关键点 01 存储是可替换的 ontology-store 是存储抽象，GraphDB 只是其实现之一。存储可替换，上层无感。
关键点 02 原始数据不出域 采集器与平台之间只传实体 + 关系 + 证据，原始数据留在客户域内。
关键点 03 元数据不进本体 元数据通道（使用痕迹）不进本体，只喂抽取引擎，作为抽取时的上下文。

为什么必须这样切§4.2

SaaS 在公网，客户数据在内网。connector 无法直连客户数据源 —— 这是 SaaS 形态的硬约束，不是可选项。

于是职责一分为二：

  • 采集器（客户侧）：连接数据源、执行连通性测试、驱动抽取、本地标准化为「实体 + 关系 + 证据」
  • 平台（SaaS 侧）：接收标准化结果、语义映射、抽取、本体管理、审核、MCP 暴露

原始数据不出客户环境，这条是合规刚需（尤其 IM 内容），也是对客户沟通时的核心话术。

一个组件吃两种形态

私有化部署 = 把 SaaS 整体搬进客户环境，采集器在两种形态下都复用（私有化时退化成本地直连，或保留作为隔离层）。FDE 不必维护两套交付流程。

03数据面 / 控制面

进入 pipeline 的东西性质不同，必须分车道。这是整份架构里最容易做错的一处。

数据面 connector 抽取 → 语义映射 → 本体实例写入
∥
控制面 抽取提案 → 双轨审核 → 版本快照 / 冻结
数据面控制面
频率高频低频
触发自动（定时 / 增量）人工审核通过
幂等是，可重放否，有语义后果
是否需要人否是

为什么不合并：混在一条流水线里会出现两个后果 —— 无法区分「哪些变化需要人看」；本体结构一变，是否触发历史数据重算变得不可控。

因此：冻结的版本不可覆盖，后续抽取只能在其上追加 diff。而本体变更后的历史数据重抽取，必须在图上显式表达（图里的虚线回路），作为可观测、可审批的动作，不能靠流水线自然流动。

04存储抽象

ontology-store 是一个抽象接口，底下可以换实现 —— 这也是能力面图上它「不出现在主视觉里」的原因。

ontology-store（抽象接口）
  • GraphDB 实现 —— Neo4j 等。深链查询与超大规模图
  • RDBMS 实现 —— PostgreSQL：JSONB + 邻接表 + pgvector
  • 内存 实现 —— 测试用
选型说明

企业本体的实际查询深度通常 ≤ 3 跳，PostgreSQL 完全够用；GraphDB 的价值在 10 跳以上的深链查询和超大规模图。

切片 1 建议直接用 PostgreSQL 实现 —— 客户环境里大概率本来就有 PG，少一个中间件就少一个交付障碍。对 FDE 而言，部署阻力是最大的敌人。

读法

组件面上几乎所有模块，在能力面上都退到了能力内部；唯一被提升到主视觉中心的，是本体核心模型。

这不是删掉模块，而是换一个提问方式：工程师问「怎么搭」，老板和客户问「能做什么」。两张图都要有，缺一张就有一方看不懂。

agent-registry 归「建」，不归「用」

agent-registry 承载 FDE 反复调整抽取方法的闭环：注册抽取 agent（自研的与外部的）、锁定版本、记录每轮迭代。它服务的是建侧。

经 mcp-server 消费本体的外部 agent（logic agent）走的是另一条路，不经过 agent-registry。两者名字里都有 agent，但一个是造本体的，一个是读本体的。

版本锁定是它的硬职责：一轮抽取用了哪个 agent 的哪个版本，必须与本体版本一起冻结进快照。否则 agent 悄悄升级后，你分不清 diff 变化是「本体演进」还是「agent 换人」。

06图上要注意的两点

agent-registry 在图上没有出边，是刻意的

它只有一个入边（ontology-store → agent-registry），右边 mcp-server 那条才通到外部 agent。这正是两者的分工：agent-registry 是 KH Agent 的抽象层，只服务建侧；外部 agent 只经 mcp-server 消费本体。

图上不画 agent-registry → 外部 agent 那一笔，是有意为之，不是漏画。

主图与 specs §4.1 的一致之处

分层、模块命名、连线语义（含 META 不产实体、ONT -.-> GDB 表示实现之一、agent-registry 只入不出）均逐条对应 specs §4.1，没有增删模块。
