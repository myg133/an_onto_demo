## 二、QA-B：落库路径数据完整性

### 🔴 BL-1　`write_snapshot_in` 静默丢两栏（确认）

`src/db/apply.rs:146` DELETE 5 张表，函数体只有 3 个 INSERT（`object_types:155` / `link_types:177` / `concept_groups:197`）。`action_types` 与 `functions` 删了不写。

运行时实证（裸 SQL 计数，不走读取层）：

```
base  v1 = [object 2, link 1, action 2, functions 2, concept 1]
apply v2 = [object 2, link 1, action 0, functions 0, concept 1]
```

**同一函数、同一事务内 3 栏写回、2 栏蒸发，无任何错误或警告。** 对照组成立（`save_snapshot` 路径写入后 v1 两栏均为 2 行），证明表与列本身没问题。

### 🔴 对 Dev 两处说法的纠正

| Dev 原话 | 纠正 |
| --- | --- |
| 「切片 1 没有提案能造出这两栏，等切片 2 才暴露」 | **前半对后半错**。`src/domain/apply.rs:70` 是 `let mut out = input.base.clone()` —— 领域层**整体继承 base**，这两栏不是「无法产生」而是「继承了、然后在落库层被丢弃」。丢失机制**今天已 100% 成立**，只是今天没有数据可丢（base 恒空） |
| 「补 `ORDER BY ordinal` 修读侧乱序」 | **会直接报错**。`action_types` 表**根本没有 `ordinal` 列**（`src/db/pg.rs:94-106`），实测 `error: column "ordinal" does not exist`。照 Dev 方案实施会让 `get_snapshot` 全面崩溃 |

### 顺序确实不稳（单连接实测，排除连接池串扰）

```
默认计划  Index Only Scan using action_types_version_id_key_key → ["act_0000", "act_0001", ...]  ← key 序
SET enable_indexscan=off → Seq Scan                          → ["act_0299", "act_0298", ...]  ← 插入序
RESET 后又回到 key 序
```

返回顺序既不是写入顺序，也不由代码决定，**完全由优化器选择决定**。其余四栏读 SQL 均有 `ORDER BY`，`action_types` 是唯一例外。

后果：逐字节往返比对假红 + 顺序漂移传导到 `view.rs` / `html_view.rs` / `diff.rs`。

### 分层契约断裂的直接证据

`src/domain/apply.rs:158` 有 `out.action_types.retain(|a| a.target != key);` —— 领域层**专门实现了**「删实体时清掉指向它的动作类型」。这个精心算出的结果在落库层**根本没有机会生效**。

### 🟡 `transition.json` 无运行时路径（Dev 属实，但说法要纠正）

全仓 grep 决定性：`include_str!` 唯一命中是 `tests/test_concept_transition.rs:21`，`src/` 下无任何代码读它。

准确表述：**没有任何自动生效路径；必须人工把文件路径显式传给 `ontok concept import --file <path>`**，再走 `review decide` 双轨 → `proposal apply`。

缓解：`cli.rs:288` 的 `decl.verify()?` 是 fail-closed（改了内容不升版本会被拒）。风险是改声明 → 测试全绿 → 但抽取产出毫无变化，维护者会误以为已生效。→ 转 REQ-011 条件 C-2。
