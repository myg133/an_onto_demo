本体平台 · 交付视角

功能面架构Functional Plane — FDE 拿这套平台怎么完成一次交付

这个平台只做一件事：把客户系统里的数据与 know-how，变成 Agent 能理解的业务语义。

读者 · 老板 / 产品 / FDE 语言 · 产品语言，不含技术选型 上一层 · 能力面 下一层 · 组件面 事实源 · docs/design/ontology-platform-spec.md 2026-09-28
本文的由来

2026-09-24 对齐会议：「过于偏向底层技术实现，与本体核心逻辑关联度不足，需进一步向上抽象调整」。

能力面把主视觉从模块换成了能力；本文再上一层，把主视觉从能力换成交付。

01一句话

这句话里有两个词是全部价值的来源：

  • 速度 —— FDE 第一次进客户现场，多久能拿出第一版可讨论的本体？
  • 可信度 —— 每一条语义，有没有证据、有没有人签字？

功能面上的七个功能域，全部围绕这两个词展开。任何一个功能域，如果既不加快速度、也不提高可信度，就不该出现在这张图上。

此外还有一道 ⓪ 决策清单 范围闸门 —— 它不是第八个功能域，而是 ④ 的输入约束：先定「本轮服务哪条决策」，再决定抽什么。

02为什么还要再上一层

能力面已经讲了「平台能做什么」，为什么不够？因为它回答的是平台自己的问题，没回答交付这件事的问题。

问题谁在问哪一层回答
系统由哪些模块组成工程师组件面
平台对外能做什么老板、客户能力面
为什么需要这个平台老板、客户、销售功能面
FDE 拿它怎么完成一次交付FDE、交付负责人功能面
客户凭什么签字、凭什么续约客户功能面

关键的差别是视角的方向：

  • 能力面是共时的 —— 站在平台外面往里看，此刻平台有哪些牌。
  • 功能面是历时的 —— 站在交付里面往外看，一个项目从头到尾走一遍，每一步谁在干活、产出什么、什么时候停。
一句话区别

能力面像一张名片（我们有什么）；功能面像一张作战地图（这一仗怎么打）。

03总图：本体在中间

这张图的画法是从客户价值往下倒推，而不是从模块往上堆 —— 倒推才能保证每一层都有存在的理由。

读这张图，三句话：

  1. 客户买的不是平台，是一个能回答他问题的 Agent。 平台本身不产生价值，它只是这条价值链的中段。
  2. Agent 需要的是语义，不是数据表。 把表给 Agent，它给出的是查询幻觉；把本体给 Agent，它才能回答业务问题。中间这一层才是平台存在的理由。
  3. 本体不是人手画的，是 FDE 用平台从客户系统里抽出来的。 底部那一层（进场组 / 成体组 / 出品组）就是本文要讲的全部内容。

3.1　本体核心逻辑 —— 为什么「本体」必须在正中间

会议指出上一版架构「与本体核心逻辑关联度不足」。这里把它讲透。本体之所以不是「高级版的数据字典」，靠的是三条：

  • 对象是从数据里认出来的，不是搬过来的 把表搬进平台，它还是表。只有「这几张表说的其实是同一种设备」这个判断被做出来，意义才出现。抽取不是一个搬运动作，是一个认知动作。
  • 企业的真相在关系里，不在单表里 设备、工单、合同各自躺在各自的系统里，业务价值全在它们之间的连线上 —— 「这台设备的故障史」「这批工单关联的合同」。关系必须是一等公民，能单独带基数、带语义、带证据。
  • 本体最终要驱动行动，不能只是被读 一个只能回答问题的本体是知识图谱；一个能驱动业务系统发生真实变更（派单、审批、冻结）的本体，才是运营层。这是客户续约的理由。
本层的一条硬约束

功能面上的七个功能域，只有三个（④⑤⑥）直接作用于本体，其余四个全部是在为这三个供货或消化产物；⓪ 决策清单是 ④ 的范围闸门。本体始终在画面中央。

04七个功能域

分三组：进场（把客户的世界装进平台）· 成体（本体从这里长出来）· 出品（本体被用上）。

进场组 —— 把客户的世界装进平台

⓪ 决策清单Scope Gate POC 起就要

先定「本轮服务哪条决策」，再决定抽什么。这是抽取范围的唯一闸门。

谁用
FDE（主产出）；客户业务专家（确认）
解决什么
系统里数据很多，但客户真正要改善的决策只有几条。不先定边界，抽取就会摊薄成「把库扫一遍」 —— 类型数量不可控，客户审不动，最后变成一个昂贵的仪表盘
输入
与客户首轮沟通：这个业务里最贵、最频繁、最常出错的决策是什么？谁在什么场景下做？
产出
一份决策清单 —— 业务决策 / 决策人 / 当前基线 / 所需信息 / 遵循的规则 / 决策后谁执行。清单里没提到的数据源字段，本轮不抽
取舍
这是范围闸门，不是第八个功能域。它是 ④ 的输入约束，成本几乎为零，但它是防止过度抽取最有效的一道闸门
为什么要倒推

一条系统的原子单位不是数据记录，而是决策。因此建模的起点不是「这个库里有什么」，而是「你希望操作员下个季度做出什么不同的决策？」——再从这条决策倒推，需要哪些对象、关系、动作。

决策清单最后三行（所需信息 / 遵循的规则 / 决策后谁执行）恰好对应本体的对象、函数、动作三根柱子：一份决策清单，顺手就把本体该长什么样点齐了。

① 项目管理Project POC 起就要

SaaS 上同时跑着好几个客户的项目，谁也别看见谁。

谁用
FDE（主）；客户 IT（被邀请）
输入
客户信息、部署形态选择（SaaS / 私有化）
产出
一个项目空间 —— 该客户的本体、KH Agent 配置、数据连接、全部迭代记录都归属它
取舍
项目之间强隔离（安全刚需）；项目内部不做细粒度权限（使用者就是 FDE 自己，省掉）
② 系统接入Connect POC 起就要

让平台「看得见」客户的数据。

谁用
FDE（主操作）；客户 IT（提供凭据 / 放行）
输入
数据源凭据、connector 选装清单
产出
一份数据地图 —— 有哪些表 / 字段 / 文档 / 会话，样本长什么样
取舍
connector 按能力标签选装（读结构 / 读行 / 读文本 / 读对话，共四个），不建继承树 —— 因为 m365 这种东西既有文档又有日历，单继承归不了类。
「读使用痕迹」不是 connector 能力标签 —— 它是与 connector 平行的第二条输入通道：connector 抽的是本体要描述的对象（进本体），使用痕迹描述这些对象在业务里怎么被用（不进本体，只作抽取上下文）。切片 3 接入。
原始数据不出客户环境 —— 合规刚需（尤其 IM 内容），也是对客户沟通时的核心话术。
③ 知识装载Load POC 起就要

数据里没有的东西 —— 业务规则、行业暗语、约定俗成、历史包袱。

谁用
FDE（主）；客户业务专家（供给 know-how）
输入
客户访谈、领域文档、术语表、历史工单
产出
一个装好的 KH Agent（connector 选装 + 领域提示 + 约束）
取舍
KH Agent 是被迭代的对象，不是一次性的配置。这是整套方法论的核心 —— FDE 调的是 Agent，不是本体；因为 Agent 里装的是「怎么从一堆表里认出设备 / 工单」这套方法，方法是跨项目可复用的，而本体不是。

成体组 —— 本体从这里长出来（核心）

为什么这一组要单独成段

这三个功能域是唯一直接作用于本体的部分。前面三个在给这里备料，后面一个在消化这里的产物。整个平台的价值，收敛在这三个功能域上。

④ 语义抽取Extract 核心

从表和文档里认出业务对象 —— 而不是等客户坐下来定义。

谁用
FDE（触发）；抽取 agent（执行，可为外部）
输入
上一版本体快照 + 人工反馈 + connector 拉到的数据
产出
本体提案 —— 候选的对象与关系清单，每条带经代码验证过的证据
取舍
一、产出的是提案，不是直接改本体。Agent 是提议者，不是决定者。
二、基于上一版做增量，不重新生成。每轮都重生成，模型的随机性会让结果来回漂移，永远收敛不了。
三、一次抽取会话内，connector 集合与 agent 版本都固定。中途换输入或换 agent，此前的收敛判定作废。
抽取能力外置，但验证权不在外

产出候选的生成能力通过 A2A 协议外置给外部抽取 agent —— 抽取的方法是市场已归纳过的东西，不必等我们做满 5 个项目。

但证据验证留在我们手里：agent 说「设备.序列号 ← t_dev.sn」，由我们的代码去查 t_dev 是否真的有 sn 列。外置「怎么想」，不外置「想得对不对」。

对 FDE 的实际影响：能接现成的行业抽取能力，但每轮抽取用的 agent 及其版本会被记录进快照 —— 出问题时能查到是哪一版 agent 抽的。

⑤ 双轨审核Review POC 可单轨代签

客户看不懂主键和基数，FDE 看不出业务对错 —— 一轨审不了。

让客户审建模质量，他只会随便点「通过」；让 FDE 替客户判断业务含义，等于没审。

谁用
客户业务专家（业务轨）+ FDE（建模轨）
输入
本体提案
产出
逐条结论（通过 / 打回 / 需修改）
取舍
同一版本体，两个视图：客户看的是「这些是你们说的设备吗？名字对吗？」；FDE 看的是「这个主键对吗？这对关系的基数对吗？」。客户视图里不得出现任何建模术语。
⑥ 收敛冻结Freeze 交付判据

不说停，这个循环就是无底洞。FDE 会永远觉得「再调一版会更好」。

谁用
FDE（判断）；客户（签字）
输入
多轮迭代记录 + 覆盖率与稳定性指标
产出
冻结的本体版本 + 客户签字
取舍
三个终止信号，任一满足即可收：
一、覆盖率 —— 数据源里有多少被打进本体，未映射率降到阈值以下
二、稳定性 —— 连续两轮的版本差异小于阈值
三、验收 —— 客户签字
认知对齐（对客户也要这么讲）

不存在「正确的本体」，只有「够用的本体」。目标是让 Agent 能可靠回答客户的业务问题，不是完美刻画客户的业务。这条认知不摆正，项目会在「再改改」里无限期拖延。

出品组 —— 本体被用上

⑦ 本体服务Serve 交付即兑现

本体被用上，交付才算完成。前面六个功能域都是在为这里供货。

谁用
外部 Agent（Claude Desktop / Cursor / 自研）、业务系统
输入
冻结的本体版本
产出
Agent 可用的语义上下文 —— 客户真正买单的东西；（切片 2）业务系统的真实变更
取舍
只读冻结版本，不读未审提案 —— 未审的东西不能给 Agent 用。不写 agent runtime、不写 SDK、不绑任何模型厂商，接入面与后端实现完全解耦。

纵切与后验

纵切 · 溯源Trace 横跨全部

溯源不是第八个功能域 —— 不是一步操作，而是每个操作都必须写下的属性。

每个对象 / 关系 / 动作都挂四个字段：谁提的 · 依据哪条数据 · 谁批的 · 何时。

没有这条纵切，双轨审核会退化成盲审，客户签字也会签得心里没底。

后验 · 沉淀Compound 不在交付周期内

一个项目交付完成后，其本体（含版本历史与证据链）一键导出为结构化文件，成本几乎为零。

但要说清楚：这是做了 N 个项目之后回过头来做的事，不是交付流程的一环。

  • 可以复用的是建模逻辑（KH Agent 里那套方法、connector 库）
  • 不好复用的是模型本身（每个客户的本体是客户特有的）
  • 行业的建模抽象，只能在一个行业做了多个项目之后再归纳 —— 这是后验的，现在做就是拍脑袋

功能面上给它留一个出口即可，不做更多。

05一个 FDE 项目的完整旅程

把七个功能域按时间排开，就是 FDE 实际干活的样子。

5.1　迭代闭环长什么样

POC 阶段里，③④⑤ 会循环好几轮。这个环跑几轮、什么时候停，是项目成败的关键。

  1. FDE 与客户第一轮沟通，理解业务这是唯一的非平台环节，也是后面所有事情的起点。
  2. FDE 组装第一版 KH Agent选 connector、写领域提示、加约束。产出一个可跑的 Agent，不是一个配置项。
  3. KH Agent 跑抽取，产出本体提案 v1候选对象与关系，每条带证据 —— 没有证据，后面两轨都没法审。
  4. 两轨并行看同一份提案业务轨问客户「这是你们说的设备 / 工单吗」；建模轨问 FDE「主键、基数、拆分对不对」。
  5. FDE 根据反馈调整 KH Agent（不是改本体）这是整套方法论的关键动作 —— 调 Agent 产出的是可复用的方法。
  6. 基于 v1 快照产出增量提案 v2客户对比的是增量，不是两个全新产物。这是能收敛的前提。
  7. 满足任一终止信号 → 冻结覆盖率达标 / 两轮差异收敛 / 客户签字。冻结之后只接受增量，不可覆盖。
注意

环里被调整的是 KH Agent，不是本体。原因在 ③ 的取舍里：调 Agent 是可复用的方法，改本体是一次性的产物。

06POC 与生产：同一套功能，两种开启深度

会议确定：POC 阶段轻量快速跑通、不得设置过高的人员能力要求、无需全量语义建模；生产落地阶段再由专门团队正式建模。

落到功能面上，就是同一套功能域的两种开启深度 —— 不是两套系统，也不维护两套交付流程。

维度POC 阶段生产落地阶段
目标证明「能跑通、真能用」正式交付并持续运营
人员1 个 FDE 即可，无建模专家要求专门团队（含语义建模）
数据局部必要验证数据全量
① 项目管理单项目多项目并行
② 系统接入单数据源，一类 connector多源，多类 connector
③ 知识装载单 KH Agent多 KH Agent，分域
④ 语义抽取范围由决策清单限定；对象 + 关系（动作/函数占位）决策清单 + 全量补充；对象 + 关系 + 动作 + 函数
⑤ 双轨审核建模轨 FDE 全责 + 业务轨可代签（客户须过目）双轨，客户与 FDE 各自独立签字
⑥ 收敛冻结轻量：覆盖率达标 + 客户认可双阈值 + 客户正式签字
⑦ 本体服务只读 MCP只读 + Action 写回 + 权限 + 审计
溯源最小形态：点开类型能看见来源完整证据链，出口对齐标准格式
交付物一页纸本体文档 + 能问答的 Agent正式本体 + 可写回的业务闭环

POC 阶段的审核规则（唯一口径）

审核规则

1. 建模轨（FDE）必须完整执行。主键、基数、拆分合并由 FDE 自己审，FDE 对建模质量负全责。

2. 业务轨（客户）POC 阶段可由 FDE 代签，但客户必须看提案并有机会提出异议 —— 不是免审。

3. 客户签字是收敛冻结的必要条件之一（覆盖率 / 稳定性 / 验收三个信号之一）。交付完成的判据不在 FDE 自己的感觉里。

4. FDE 代签时必须显式记录「已代签」及依据，不得静默跳过。

生产阶段升级为：客户与 FDE 各自独立签字，谁也不能替谁签。

口径修正

早期版本曾要求「客户能在业务轨独立完成审核、无需 FDE 解释建模概念」，与会议「不得设置过高人员能力要求」直接冲突。2026-09-28 已统一为上述口径。

POC 的门槛只有三条

一、FDE 能在一个数据源上跑通一次抽取，产出一份本体提案。

二、客户能在一页纸上看懂「有哪些对象、什么关系、每条从哪来」，并认可。

三、接上 Agent，能回答至少 5 个客户级业务问题。

已明示的一处有意偏离：POC 不含写回

参考方法论把「交付没有动作类型的应用 —— 造出昂贵的仪表盘，把写回问题留给永远不会被资助的二期」列为五大失败模式之一，并主张动作先行。本项目在 POC 阶段明确偏离该主张，Action 推迟到生产阶段。这是有意识的决策，不是遗漏。

项说明
理由① 客户首轮签字的判据是「能回答我的业务问题」，问答价值先于写回价值；② 写回必须先解决权限与审计，POC 阶段客户 IT 未授权时硬塞写回会卡在审批上；③ 信任建立的顺序是先证明「只读也答得好」，反序反而更快获得授权
代价POC 交付物有沦为昂贵仪表盘的风险 —— 这是被警告的失败模式，本项目并未消除它，只是推迟
缓释POC 交付物必须含：① 一页纸本体文档；② 决策清单驱动的问答演示（≥5 个客户级业务问题）；③ 交付时向客户明确呈现「下一步能写回什么」的能力路线
红线生产阶段的 Action 不得再次顺延。若无法启动，须回到设计规格重新评估是否收缩本体范围，而不是把 Action 永久推迟

实体对齐的降级方案

本体不做实例层实体对齐（把文档里的「张三」对到库里的员工记录，是公认的无底洞）。但必须预先约定遇到该问题怎么办，否则会在客户现场临时决策。

降级策略：单库优先 + 显式声明

1. 客户现场只有一个数据源 → 不触发该问题，正常推进。

2. 客户主库与业务库对同一实体（如「设备」）定义不一致 → 本轮不做跨库对齐，改为：

· 抽取范围收窄到决策清单涉及的那一个库（⓪ 范围闸门在此再次生效）
· 在交付物的一页纸本体文档中显式列出「本轮未解决的实体边界问题」：哪两个源、哪类实体、冲突在哪
· 该问题转为生产阶段的立项输入，不是 POC 的阻塞项

3. 禁止的做法：为了让问答跑通而在 POC 临时用规则硬合并两个源 —— 这会造出一个客户不认的本体，且违反「Agent 不能直写本体」。

「动作」和「完整溯源」在 POC 阶段不实现，但位置必须留着 —— 否则生产阶段要推翻 POC 重来。

09功能面的三条设计主线

如果只记三句话：

  • 本体始终在画面中央 七个功能域里，只有三个（④⑤⑥）真正作用于本体，其余四个都在为它们供货或消化它们的产物。任何偏离这条线的功能需求，都应该被问一句：它加速了速度，还是提高了可信度？
  • 速度与可信度是两条主脉，且它们有张力 追速度就会想「让 Agent 全自动跑完」，追可信度就会想「每条都让人审」。功能面的解法是把它们分到不同的位置：抽取（④）全自动、审核（⑤）强制人工、冻结（⑥）用指标而不是用感觉来判停。
  • POC 轻、生产全，但底座是同一套 ⑤ 在 POC 阶段业务轨可由 FDE 代签（客户须过目、代签须留痕）、⑦ 可以只读 —— 但位置不能省。省掉位置，生产阶段就得推翻重来，而推翻重来对一个已经交付过的客户项目是不可接受的。

9.1　本文回应了会议纪要什么

  • 「过于偏向底层技术实现」 本文全文不出现任何技术选型词，主视觉是七个业务功能域和一条交付旅程。
  • 「与本体核心逻辑关联度不足」 §3.1 把本体核心逻辑三条讲透，并作为一条硬约束写进 §4：七个功能域里只有三个直接作用于本体，本体始终在画面中央。
  • 「需进一步向上抽象调整」 抽象的终点是交付，不是更抽象的技术分层。功能面的主语是「FDE 在做的事」，不是「平台有的东西」。
  • 「为什么需要这个平台」（此前没人回答的问题） §3 总图从客户价值倒推：客户买的不是平台，是一个能回答业务问题的 Agent；而 Agent 需要的是语义，不是数据表。
  • 「POC 轻量、快速跑通、不得设置过高人员能力要求」 §6 给出同一套功能的两种开启深度：POC 只需 1 个 FDE、单源、只读；建模轨由 FDE 全责，业务轨客户侧可代签但须过目留痕；§7 显示 ⓪①②③④ 是 FDE 单人区，结构上保证了一个人跑得通。
  • 「生产落地阶段再由专门团队开展正式语义建模」 §6 右侧列：动作、函数、完整证据链、Action 写回都是为这一阶段预留的位置，POC 阶段只占位不实现 —— 且占位是硬性要求，不能省。
  • 「迭代终止条件：数据源映射阈值 + 版本间差异收敛阈值，达标后客户签字」 落在 ⑥ 收敛冻结，三个信号并列，客户签字是其中之一。
  • 「复用」的边界 §4 后验沉淀：可复用的是建模逻辑（KH Agent 里的方法），不是模型本身；行业抽象必须等一个行业做了多个项目之后再归纳。
  • 2026-09-28 新增 · 决策倒推 ⓪ 决策清单作为范围闸门。不先定「本轮服务哪条决策」，抽取会摊薄成「把库扫一遍」—— 这是防止过度抽取最有效的一道闸门，也让收敛有了业务边界。
