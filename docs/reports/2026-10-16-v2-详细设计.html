Ontology Platform v2 · Detailed Design

本体平台 v2 · 详细设计

本体只存类型、关系、规则三层。实例不存 —— 用户 agent 接入时才按绑定现场物化。写操作永不走 DB，只走 API，并按操作人权限调用。

01

目标架构

左右两栏是两种完全不同性质的活动：左边是 FDE 构建期，产出冻结快照；右边是 用户运行期，现场物化实例并执行。两者只通过「本体库」这一个接缝相连。

构建期 · FDE
非结构化接入文档 / 聊天 → 名词聚类→实体、动词→action·function、关系、rule新
结构化接入DB schema + API 目录 → 验证本体、生成读写绑定
合并验证非结构化提的实体，schema 里是否有对应物新
提案通道沿用现有 ItemKind 与双轨审核，不改
冻结快照类型 / 关系 / rule —— 版本化，冻结
运行期 · 最终用户
MCP 端点（带身份）用户经 agent 接入；平台 SSO 识别「谁」改形态
user view（HTTP）只读：展示已构建本体的图关系新
推理层规则求值 → 决定要查什么、调什么新
绑定解析器类型 → SQL(读) / API(读写)新
权限校验按操作人查授权范围，超范围拒绝新
审计落账operator + 端点 + 动作 + 结果新
写入 冻结快照 读出 类型·关系·rule
接缝只有一处：构建期把冻结快照写进本体库；运行期只读本体库 + 读绑定注册表。运行时事实（身份、实例物化结果、审计）一律不进快照。

关键设计：两个抽取器并列生产进同一个提案通道，差别在否决权（非结构化提的实体，结构化可以否掉），不在执行先后。这样双轨审核、快照、冻结一个字都不用改。

04

推理层：从问题到调用

一次业务问答的真实成本往往不是「一次查询」，而是一串依赖查询。这条链的每一步都在做什么：

①②③ 纯本地，零外部调用 —— 规则求值。④⑤⑥ 才碰业务系统，且每跳都可能是一次网络往返。
级联深度不可控：一次问答可能触发一串查询。设计阶段必须算清，否则线上炸。
SQL · 只读生成参数化查询
表列白名单
静态检查（待决 D7）
API · 读GET 类调用
携带操作人凭证
API · 写POST/PUT 类
幂等键必填
永不走 DB
为什么写只走 API：调用用的是操作人员自己的权限，平台没有一份「什么都能干」的服务权限。加一个字段不会让平台静默获得新系统的写能力 —— 得有人真的有那个权限，否则调用失败。平台从「特权写者」变成「委托执行者」。
05

委托执行 vs 特权写入

v1 规格反对自动写绑定的核心理由是「静默多写 = 误操作客户生产数据」。这一栏说明为什么新设计消掉了它。

维度平台直连 DB 写（旧）代操作人员调 API（新）
平台持有的权限
一份平台自己的万能写权限，覆盖所有已绑定系统
没有。每次调用都是某个具体人的权限，用完即弃
加个字段的后果
静默获得新系统的写能力
得有人真的有那个权限，否则调用失败并报错
权限边界谁执行
平台要自己再实现一遍权限判定
业务系统自己执行，平台不重复造轮子
出事的追责
平台的权限，日志里没有自然人
operator + 端点 + 动作全在平台侧可审计
但幂等性从「次要问题」升级为「必须设计」
旧的 conflict_field 乐观锁靠 DB 条件更新原子判冲突，API 没有对应物。重试一次就是多执行一次。需要 Idempotency-Key，或查询-判断-执行的补偿逻辑。
生成 SQL 是全新的安全面
现状：3 处 format! 拼 SQL，表名列名全硬编码。改成按绑定生成 ⇒ 引入规则/模型产出的 SQL 进数据库执行 = SQL 注入面。必须配套参数化 + 表列白名单 + 生成结果静态检查。v1 规格完全没有这一块，因为它不生成 SQL。（待决 D7）

身份与权限

「用户是本体中的一个对象」在设计立场上是成立的，但必须拆成三层才不撞冻结语义。

①「客户」这个类型存在
进快照
这是结构判断，由抽取 + 双轨审核得出。慢变。
冻结边界
②「此刻是张三」
运行时绑定
SSO subject 落到「客户」类型的一个实例上。每请求变，不进快照。
③「张三能调哪个 API」
运行时绑定
该实例上的读写能力。每请求变，不进快照。
② 是整条链的接缝：SSO 登进来的那个 subject，怎么落到「客户」类型的某个实例上 —— 现有代码零身份概念（proposals / proposal_items 表无 actor 字段）。这正是 v1 规格 §2.3 说的那类问题：「数据能告诉你"有什么"，不能告诉你"这算什么"」。
待决 D1：直接用 subject 作 key，还是维护 subject ↔ object 映射表。
07

user view · 只读图检查

只展示已构建好的本体图关系，不做操作入口。目的是让「双轨审核里客户过目」这一条真正成立。

节点上要带完整性标记（complete / partial）—— 因为按需物化的实例不完整，「没查到」不等于「没有」。v1 的封闭世界承诺（答「确定没有」）只在 complete 的类型上成立，这个区分必须显式存在。（待决 D4）
08

分期路线

原则：叠加，不重写。现有 develop 是本设计的一个垂直切片（只读那半），保留；每阶段可独立验收、独立回滚。

  1. 0 · 规则所有权 + 身份解析待决 D1 D2
    规则由谁写、谁审；SSO subject 怎么落到 object key。这两件不定，后面全部悬空。
    产出：rules 审批流程定义 · 身份绑定表
  2. 1 · user view复用最多
    HTTP server + graph view。复用 CustomerView、守门器、html_view.rs、object_types/link_types。不动抽取内核。
    产出：一双看得见问题的眼睛 · 后面每步都能被它检验
  3. 2 · 读绑定待决 D3
    补 v1 规格 §5.2 的悬空引用；object_types 加 source[]；明确读走 SQL 还是 API。
    产出：ReadBinding 模型 · 读路径显式标注
  4. 3 · API 写绑定作废旧设计
    替换 WriteBinding 的 DB 直写形状；补幂等设计。
    产出：endpoint/method/param/idempotency · 乐观锁方案退役
  5. 4 · 动词维度扩类型系统
    扩 ItemKind（现在六个变体里没有 action/function）＋审核面。action_types 的 DDL 与领域类型已占位，缺的是 kind、生产者、以及双轨审核里对它的处理。
    产出：ItemKind +2 · proposal 校验 · CustomerView 投影 · MCP tools · 快照写入
  6. 5 · 非结构化接入并列生产者
    文档/聊天抽取作为第三个 ExtractionAgent 实现接入 orchestrate.rs，不是替换 DB 抽取。
    产出：unstructured agent · 合并验证规则
  7. 6 · 推理层待决 D4 D5 D7
    只读先行；写仍走阶段 3 的审核签字，不直执行。
    产出：规则求值器 · 绑定解析 · 参数化 SQL 生成 · 完整性标记
阶段 1 必须带身份门
把本体库经 HTTP 暴露出去，而系统零身份概念 —— 等于给客户开一扇没锁的窗。这不是「先上线再补」的东西。
拆安全网要分档
tests/test_no_write_path.rs 现在断言 domain 层不得出现 execute / write_back / dispatch / run_action / apply_effect，且 action_types / functions 恒空。每放一档就钉住新的东西 —— 一次全拆 = 拆了防护网还没补上新的。
