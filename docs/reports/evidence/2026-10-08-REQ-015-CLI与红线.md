# ★ 残留 F2（阶段 3+4 仍是规则路径）—— 我的独立判定

## 1. 判断成立吗？成立，且我用数据证明得比 Dev 更硬
我的 VendorModelAgent 经编排后：
    extracted_by.agent = "vendor-model"
    proposal.items      = 与规则 agent **逐字节相同**（3 条 item）
⇒ agent 的候选（含 8 条违规）对提案**零影响**；阶段 3+4 无条件走
   `propose::extract_with_context(report, &[], …)`（orchestrate.rs:268-276），
   全程不看 agent 产出。

## 2. 严重度：不是「REQ-015 没做完」，是**范围边界**；但藏着一个更尖锐的问题
- REQ-015 的题面是「把抽象层**接到生产路径**」+「阶段 2 不可外包」。
  「让提案内容由 agent 产出」属于阶段 1 契约变更（CandidateType 要加
  description/aliases/evidence），**超出本任务**。Dev 的定性正确。
- ★ **但 Dev 的表述偏轻**：他写「提案内容对非规则 agent 是错的」。
  实测更严重的是 **溯源撒谎**：`extracted_by.agent` 记的是 vendor-model，
  而 items 一条都不是它产的 —— 这正是 factory.rs 模块头自己认定的
  「**静默的假溯源**……这正是本项目吃过七次亏的那一类」。
  factory 在**装配层**堵死了回落，orchestrate 却在**盖章层**造出同一类假。
- 当前**不可达**（factory fail-closed ⇒ 只有 inproc 能造出来），属潜伏缺陷。
  ⇒ 作为 REQ-015 验收：不阻断；作为 **RN-2 的开工前置条件：必须先解决**。

## 3. 接真 agent（RN-2）会发生什么 —— 逐步具体化
1. 用户登记 protocol=a2a → factory 造出模型 adapter
2. 阶段 1 逐组问模型，拿到候选类型/属性/映射声明（**模型的话才是提案的真相**）
3. 阶段 2 核对 → 若模型编了列名，报 ⚠ 违规（stderr）
4. 阶段 3+4 **完全无视上面的一切**，本地跑一遍规则管线生成 items
5. 落库 proposal.json：items 是规则的，extracted_by.agent 是模型的
   ⇒ 用户以为采信了模型，实际是规则结果；且 §8.4 的版本锁定/diff 归因全部失真
6. 更糟：若阶段 1 整组失败，failed_groups 非空而 items 仍满，
   「什么都没抽」与「抽得很全」在产物里长得一样（§8.5 已排除它参与收敛判定，
   但产物本身会误导人）

## 4. 有没有更轻 / 更重的解读？
- 更轻：extracted_by 记的是「本轮抽取由谁驱动」，按定义包含 agent 参与 ⇒ 未必算撒谎。
  我**不采信**这个解读 —— §8.4 的用途是归因，且 factory 自己用同一标准判过。
- 更重：无。阶段 3+4 至少仍是**确定性的**（不引网络不确定性），不是正确性灾难。
- 另一条我发现的、独立于残留 F2 的隐患：
  `ontok-propose.rs:158  orchestration.attempts = 1;`
  ⇒ drive_group 的重试在生产路径**等于关闭**。RN-2 接网络 agent 后，
  一次超时就是一次失败，无重试。必须写进 RN-2 前置条件。
