## 3. 两种裁决可分辨吗？「非空 ⇒ 账已经错了」有没有过度声称？ —— 可分辨；**非空分支确有过度声称（非阻断）**

### 3.1 独立渲染（我自己写的探针，非采信 Dev 存档）

我在 `tests/` 下临时造了一个可编排上报序列的 adapter，独立渲染两段。**实际文本与 Dev 归档逐字一致。**

**空 `group_id` 分支（实测渲染）：**

```
组  的第 0 笔上报了两次且**用量不同**：上一读 used=120（没报费用），本次读 used=280（没报费用）。
同一个 (group_id, attempt) 本该**只对应一笔钱**；撞出不同的值说明这个实现在同组重试时**没有递增 attempt**。**这一轮的钱数仍可能是对的**：空 group_id ⇒ 整个 round 只占一个键 ("", attempt)，totals() 取最后一次读到的值。若这个实现报的是**整轮累计**，那正是本轮的正确总额（单键覆盖不会把各组的账叠起来 ⇒ 不会出现 N 倍计入）。坏掉的是 `UsageReport.used` 的**增量契约**，**不是这一轮的账**。⚠️ 但若它报的是**增量**，前面的组已被顶掉、账就少计了 —— 去核对这个实现到底报的是累计还是增量。
```

**非空 `group_id` 分支（实测渲染）：**

```
组 table:t_a 的第 0 笔上报了两次且**用量不同**：上一读 used=120（没报费用），本次读 used=160（没报费用）。
同一个 (group_id, attempt) 本该**只对应一笔钱**；撞出不同的值说明这个实现在同组重试时**没有递增 attempt**。**账已经错了**：这个 group_id 不是空的 ⇒ 被顶掉的那一笔是**这一组自己的**账，而它现在**不在账本任何地方**；于是 used **少计** ⇒ 闸门会按偏低的数放行 ⇒ **真的资金缺口**。
```

汇总行（实测）：`用量上报碰撞（1 处）—— 账本存疑，已停（每处的原因见下）：`

### 3.2 读的人能否一眼分辨？ —— **能，但有观感代价**

- 两段**前缀完全相同**（哪一组、哪个键、两个数各是多少、没递增 attempt），
  **只有裁决句不同**，且裁决句紧跟在同一位置（同一段的末尾）。
- 判定：**可分辨**。裁决句以 `**这一轮的钱数仍可能是对的**：` / `**账已经错了**：` 开头，
  加粗 + 冒号，形态统一，一眼可区分。
- **观感代价（非阻断）**：裁决句被放在**长段落的最末尾**，
  而「哪一组 / 哪个键 / 两个数」在前。排障者扫读时容易先读到数字、后读到裁决。
  这是一个排版取舍，不影响正确性。

### 3.3 ⚠️ 「非空 ⇒ 账已经错了」是否对**所有**非空 `group_id` 成立？ —— **不成立，反例已实测复现**

**反例构造（非空 `group_id`，但账其实完全正确）：**

adapter 上报序列 `(group_id = "table:t_a", attempt = 0)`，`used` 依次为 **120 → 280**，
语义是**本组累计**（第一次 120，第二次 280 ⇒ 增量为 120 与 160，本组真实总花费 = 280）。

**实测输出（我自己的探针）：**

```
预算账 used = 280
该组真实总花费 = 120 + (280-120) = 280
账 == 真实 ? true
stopped = true
渲染文案：……**账已经错了**：这个 group_id 不是空的 ⇒ 被顶掉的那一笔是**这一组自己的**账，
          而它现在**不在账本任何地方**；于是 used **少计** ⇒ 闸门会按偏低的数放行 ⇒ **真的资金缺口**。
```

**账 = 280 = 真实 280，账是对的**；而文案断言「**账已经错了**」「used **少计**」「**真的资金缺口**」。
**三处断言在该场景下全部为假。**

**这个反例可达吗？—— 可达，且是两个独立真实缺陷的叠加：**

1. 「报**组累计**而不是逐笔增量」—— 这是 `UsageReport.used` 契约（`src/agent/mod.rs:288-294`）明文禁止的常见写法；
2. 「忘递增 `attempt`」—— 正是 REQ-050 的复发形态。

两者**独立发生、且极易同时发生**（同一个 adapter 写错了两处）。此时撞键后
`insert` 保留最后一次读到的 280，**恰是本组正确总额**。

**与 AC-001 的关系：** AC-001 原文把第 2 类定义为「键撞上且**前一笔钱已被顶掉**（真正的资金缺口）」。
本反例里「前一笔」（120）**确实**被顶掉了 —— 但它不是一笔**独立的、应计入的钱**，
而是本组累计的一个**中间读数**。所以 AC-001 自身的措辞已经隐含了这个洞，
**Dev 是忠实实现了 AC**。缺陷性质：**规格继承的过度声称**，不是实现走偏。

**为什么仍判非阻断：**

- 两种情形**都照样停**，判定依据完全相同 ⇒ **判别力零变化**（本需求的全部前提）。
- 方向 fail-closed：**停 = 白跑 ≠ 多花钱**（Dev 在 `src/agent/orchestrate.rs:387` 的注释里也写了这一点）。
- 影响的只是**排障文案的一处精度**，不影响任何金额、不影响闸门结论。
- **但这是本轮唯一一处「新的过度声称」**，且与 REQ-052 要消灭的是**同一类**过度声称 ——
  只是从「空分支」搬到了「非空分支」。值得记录，值得下一轮收敛。

**建议（非本轮必改）**：非空分支的 `**账已经错了**` 可弱化为
`**这一组自己的账可能被少计**（若被顶掉的是本组累计的中间读数，账仍可能是对的 —— 与空分支同理，去核对上报语义）`，
与空分支的「仍可能」保持**对称**。

## 4. 「仍可能」措辞够不够诚实？ —— **够；二分法不穷尽但未过度声称（非阻断）**

### 4.1 「仍可能」是否精确

空分支写的是「**这一轮的钱数仍可能是对的**」，并给出条件「若这个实现报的是**整轮累计**」。
我独立核实了这个条件式在该场景下**确实成立**：

- 探针实测：空 `group_id` + 累计语义 120 → 280 ⇒ `used = 280` = 本轮正确总额 ⇒ **「仍可能对」被实证**。
- 用「**仍可能**」而非「一定对」，且明确写出「**去核对这个实现到底报的是累计还是增量**」的下一步 ⇒
  **措辞诚实、且可操作**。判定：**合格**。

### 4.2 「累计 vs 增量」这个二分是否穷尽？ —— **不穷尽（第三种：少算以外的错法）**

独立枚举一个违反契约的 adapter 在空 `group_id` 下可能的行为：

| 行为 | 最后一读 vs 真实 | 与 Dev 文案是否吻合 |
| --- | --- | --- |
| (a) 报**整轮**累计 | 相等 ⇒ 账对 | ✅ 文案说的「对」 |
| (b) 报**逐笔增量** | 偏小 ⇒ 少计 | ✅ 文案说的「少计」 |
| (c) 报**会话生命周期**累计（跨 round 不归零） | **偏大 ⇒ 多计** | ❌ **文案未覆盖** |

**第 (c) 种确实存在**：空 `group_id` 的语义被定义为「整轮合计」（`src/agent/mod.rs:268`），
但一个写坏的 adapter 完全可能把**整个会话**的累计量挂在空 `group_id` 下报上来。
此时 `used` 会**多计**，而文案只教读者在「对 / 少计」之间二选一。

**为什么这不构成过度声称：** Dev 的条件句写的是「若这个实现报的是**整轮累计**」——
**这个限定词本身就把 (c) 排除在外**了。他并没有无条件地说「只要是累计就一定对」。
所以是**完备性缺口**，不是**虚假断言**。

**判定：诚实度合格。** 若要更严谨，可在空分支补一句
「⚠️ 若它报的是**跨 round 的会话累计**，则会**多计** —— 一并核对。」

### 5.2 ⚠️ `:322` 那句「账上是 280，而不是 160」—— **它是错的**

```
322: /// 真实 `LlmAgent` 走**完整编排** ⇒ 账上是 280，而不是 160。
324: fn llm_retry_spend_reaches_the_budget_as_two_separate_entries() {
325-329:  llm_agent(vec![ Ok(llm_resp(None, 120)),
                        Ok(llm_resp(Some(&good_body("t_a")), 160)),

333:        run.stage.budget.used, 370,                                 ← 断言的是 **370**
```

- 这是个**两组**测试（t_a 两笔 120+160，t_b 一笔 90）⇒ 正确数字是 **370**，不是 280。
- **280 = 120 + 160**，那是该测试**还是单组时**的旧总额 —— 典型的**陈旧残留**。

  REQ-052 **未动它**。

**Dev 的不订正理由「单组测试，停不停都是 160」不成立：**

- 该测试**不是单组**，是两组 ⇒ 「停不停都是 160」的前提就是错的
  （不停是 370；停才是 160）。
- 结论：**Dev 没有「错改」**（不改是对的，守住了不该动断言的边界），
  但他**给出的理由是事实错误**，且这**正是 AC-002 要扫的那类缺陷（陈旧数字）**，
  却因为错误判断而漏掉。属于 **AC-002 扫尾不全 + 自述不准确**，非阻断（纯注释，不影响任何断言）。
