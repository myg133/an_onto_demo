## Q1 · 行序真的没变吗？（AC-003）—— **通过**

### 独立复现方法

在 `tests/test_snapshot_write_paths.rs` **末尾临时追加探针测试**（跑完即删；
非新建 probe crate、未设 `CARGO_TARGET_DIR`、未用 `--release`，用同一热 target）：

- `zz_probe_multirow_vs_loop_heap_order` —— 同一 project 下两个 version，
  A 用多行 `QueryBuilder::push_values`，B 用原 `for k in keys` 循环；
  各自读回 `ctid::text`，**按 `(blk, off)` 数值**排序
- `zz_probe_ctid_text_sort_trap` —— 纯逻辑复现文本序陷阱
- `zz_probe_real_ctid_offsets` —— 一次插 20 行让 `offset` 跨过 10，看真实堆上是否分叉

### 实测输出（二进制 `test_snapshot_write_paths-4119f8d8fad5cac3`）

```
A) multi-row INSERT
  numeric-t064 keys = ["z_last", "m_mid", "a_first"]
  ctids = ["(5641,16)", "(5641,17)", "(5641,18)"]
B) per-row loop
  numeric-t064 keys = ["z_last", "m_mid", "a_first"]
  ctids = ["(5641,19)", "(5641,20)", "(5641,21)"]

PROBE_RESULT call_order=["z_last", "m_mid", "a_first"] dict_order=["a_first", "m_mid", "z_last"]
PROBE_RESULT multi=["z_last","m_mid","a_first"] loop=["z_last","m_mid","a_first"] identical=true
```

**结论**：
- 多行 INSERT 物理行序 == 逐条循环物理行序 == **调用点顺序** `["z_last","m_mid","a_first"]`
- 该顺序恰为 key 字典序 `["a_first","m_mid","z_last"]` 的**严格反序**
- **与 Dev 自述的 `heap_order=["z_last","m_mid","a_first"]` 完全一致**

### 独立复现了 Dev 说的 `ctid` 文本序陷阱（属实）

20 行同落一页 `(6148,*)`，offset 3..22：

```
by_text = ["(6148,10)","(6148,11)",...,"(6148,22)","(6148,3)",...,"(6148,9)"]   ← 错
by_num  = ["(6148,3)","(6148,4)",...,"(6148,21)","(6148,22)"]                  ← 对
text_diverges_from_num = true
```

**Dev 的提醒属实且有价值。** 若按文本排序核对，这 3 行恰好落在 offset 16/17/18
（两位数，文本序与数值序一致），换个行数或页填充就会翻车。

### 机制解释（为什么行序必然一致）

`QueryBuilder::push_values(keys, ...)` 按 `keys` 切片顺序展开 `VALUES`；
PG 对单条 `INSERT` 按 `VALUES` 顺序逐行追加到堆。原 `for k in keys` 是同一顺序的三条独立语句。
**两者迭代同一个 `&[&str]`**，顺序漂移在类型层面就不可能发生。

## Q3 · 前提断言贴紧，语义没变吗？—— **逐字未变；移动是语义对齐，不是放松**

### 3.1 事实核对：只挪位置

用 Python 精确抽取 `assert_eq!(` 到 `);` 的**完整原文**做字符串相等比较：

```
BASELINE == NOW  →  True
```

表达式、期望值 `vec![0, 0, 0]`、消息字符串**一个字符都没改**。`git diff` 亦为 `-` 后别处 `+`，无内容变化。

### 3.2 独立判断：移动后是否还在检查它原本要检查的东西？

**结论：是的。但它检查的是「一个不同时刻」的状态 —— 语义上是对齐，不是放松。**

1. **检查对象没变** —— 都是 `v_legacy` 的 3 行 `ordinal` 是否全为 0，
   都读 `ordinals_of(v_legacy)`，都声称「迁移前历史行应当全是 DEFAULT 0」。

2. **原位置检查的其实是「3 个网络来回之后的状态」** ——
   前提断言原本夹在 `v_written` 两次 INSERT 之后。
   假设并发回填把 3 行整批改掉：
   **原位置会红**（`[0,1,2]` ≠ `[0,0,0]`），**紧贴 INSERT 的位置也会红**（同样读到 `[0,1,2]`）。
   ⇒ **两个位置在「整批污染」面前表现相同**，都不放松。

3. **移动真正消除的是「断言所描述的操作 ≠ 它实际观测的操作」这种错位** ——
   前提断言挪到紧邻 INSERT 后，读的就是它所描述的那次插入。

4. **是否「让测试更容易过」？—— 是，但只在一个方向，且方向正确。**
   观测点提前到 INSERT 后 1 个 RTT，确实**降低了被并发回填整批污染的概率** ⇒ 前提断言**更容易过**。
   但这个「更容易过」换来的正是 AC-001 要的东西：
   **前提断言不该承担「检测竞态」的职责** —— 竞态由「多行 INSERT 原子性」从根上消除；
   前提断言只该报告「我刚插的行是不是还是 0」。
   若把前提断言当竞态探测器，它就变成 **flaky 源**，那才是真正的「放松判据」。

5. **反证：若「移动 = 降低门槛」，方向应该相反。**
   想让测试更容易过的改法是把 `vec![0,0,0]` 改成允许子集、或干脆删掉前提断言。
   **Dev 两样都没做** —— 我用 M5/M9 验证了这点（见 Q5）。

**结论：移动是语义对齐 + 减少 flaky，不是放松判据。AC-002 守住。**
补充一点 Dev 没说的：**即使前提断言留在原位置，多行 INSERT 也已消除子集污染**；
移动的额外收益是消除 flaky，同时让「前提断言紧贴它所描述的 INSERT」这个性质得到保证。

## Q4 · 行序自检是不是在范围外？—— **独立看法：范围内，但有一个洞**

### 4.1 范围判断：**在范围内，我同意 BA**

1. **它是 AC-004 修订后的明文要求** ——
   `acceptance.md:115-117`：「**修订为**：在 `insert_legacy_actions` 里**就地加一条前提自检**」，
   并规定「变异 2b（行序改成字典序）须**确定性**变红」。Dev 做的正是这个。
   **不是范围蔓延，是执行修订后的 AC。**

2. **它不放松任何断言，只加严** —— M2b 实测证明它只增不减判别力。

3. **不加它 AC-004 第 2 条确实无法满足** ——
   我独立验证了该论断（`acceptance.md:105-113` 的论证是对的）：
   确定性性质比较的是**回填之后**的状态，而按 key 回填对**任意**插入顺序给出同一答案。
   所以「字典序」这个唯一危险的排列，恰恰是唯一 outcome 断言永远看不见的那个。
   **只有就地前提自检能看见它。** BA 判断成立。

### 4.2 「会不会自我循环（断言一个常量、无论代码怎么改都过）」？

**当前写法：不会自我循环。**

- **M6** = 把自检改成 `assert_ne!(2 + 2, 5, ...)`（纯常量，与 `keys` 无关）→ **存活 3/3**
  说明 M6 本身无法被现有判据杀死（符合预期，它是常量断言，永远过），
  **但当前自检不是常量断言** —— 它读 `keys` 并与 `sort(keys)` 比较。
- **M2b**（调用点改字典序）→ **确定性杀死 5/5**，
  **证明它真的随 `keys` 变化而变化**。
- **M7**（`assert_ne!` 反写成 `assert_eq!`，钉反不变式）→ **杀死 3/3**，
  报错 `left: ["z_last","m_mid","a_first"] / right: ["a_first","m_mid","z_last"]`。
  **证明自检的极性也是对的、且被有效检验。**

### 4.3 它钉的是不变式还是实现细节？

**钉的是不变式，但只看了一半** —— 这是要报的核心问题：

```rust
let mut dict_order = keys.to_vec();
dict_order.sort_unstable();
assert_ne!(keys, dict_order.as_slice(), ...);   // ← 断言的是入参 keys

let mut qb = sqlx::QueryBuilder::new(...);
qb.push_values(keys, |mut row, k| { ... });    // ← 真正决定行序的是这一行
```

自检断言**入参切片 `keys` 不是字典序**，而**真正决定物理行序的是 `push_values` 收到的那个切片**。
两者之间隔着一次**没有被任何断言覆盖的传递**。

两条变异验证这个洞，**都存活**：

| 变异 | 做法 | 结果 | 含义 |
| --- | --- | --- | --- |
| **M10** | `push_values` 传 `keys.iter().rev()` | **存活 5/5 绿** | 物理行序变 `a/m/z` = 字典序，自检查 `keys` 仍过 |
| **M11** | `push_values` 传 `sort_unstable()` 后的切片 | **存活 5/5 绿** | 物理行序**确实变成字典序**，自检查 `keys` 仍过 |

**M11 是「判据有洞」**：它让物理插入顺序**真的变成字典序**（AC-003/AC-004 要防的状态），测试却**全绿**。
按字面 AC-004 第 2 条（「行序改成字典序须确定性变红」），M11 属于该情形的一种，**却没有变红**。

**为什么仍判非阻断**：
- 当前代码**没有这个 bug**（Q1 已实测物理行序 == 调用序 == 反字典序）
- 该洞只在**未来有人改 `push_values` 实参**时才被利用
- 但它确实**削弱了这条自检本该提供的保护**，属「判据不完整」而非「判据错误」

### 4.4 有没有更合适的钉法？

**有，成本 3 行，且不引入 `ctid` 文本序陷阱。**

**方案 A（推荐）**：让自检断言 `push_values` **实际传入的那个切片**

```rust
let mut qb = sqlx::QueryBuilder::new(...);
let rows: Vec<&str> = keys.to_vec();
let mut dict_order = rows.clone();
dict_order.sort_unstable();
assert_ne!(rows, dict_order, "…插入顺序必须与 key 字典序相反…");
qb.push_values(&rows, |mut row, k| { … });   // ← 断言与实参同一个对象
```

把中间变量 `rows` 同时喂给断言和 `push_values`，**洞自然消失**：
M10/M11 类变异必须先改 `rows`，改了就撞断言。

**方案 B（更强但要连库）**：断言 `RETURNING ctid` 数值序 ≠ 字典序。**不推荐** ——
需把 `execute` 换成 `fetch`，且 `ctid` 是物理量、跨页/跨 plan 不是稳定契约。
Dev 拒绝 `ctid` 方案的理由（文本序不可靠）**我已独立复现为真**。

**我的取舍**：方案 A 成本极低、零 flakiness、精确堵住已实测的洞。**建议下一版采纳。**

## Q6 · 第二条污染通道 —— **Dev 的判断成立，我独立确认**

### 1. 该签名确实存在，且可复现

M1（还原逐条 INSERT）120 次采样中，**13 次失败签名全部且仅为**这一条：

```
13 left: [("a_first", 0), ("m_mid", 1), ("z_last", 1)]
13 tests/test_snapshot_write_paths.rs:749:5:
```

与 AC-001 描述的第二通道**逐字符吻合**，**独立于 Dev 的说法**复现出来。

### 2. 根因确认是「回填看到了子集」

生产 SQL（`src/db/pg.rs:437`，**本次未改动**）：

```sql
UPDATE action_types AS a
SET ordinal = sub.rn - 1
FROM ( SELECT id, ROW_NUMBER() OVER (PARTITION BY version_id ORDER BY key) AS rn
       FROM action_types WHERE ordinal = 0 ) AS sub     -- ← 无 version_id 过滤（全局）
WHERE a.id = sub.id AND a.ordinal = 0;                   -- ← EPQ 重检的就是这个
```

子查询**只按 `ordinal = 0` 过滤，无 `version_id` 约束** ⇒ **全局**。
`a.ordinal = 0` 是 EPQ 重检谓词：并发回填提交后，本测试的 UPDATE 重走 EPQ，
该谓词不再成立 ⇒ **静默跳过**（不报错，行保持前值）。

**签名推导**（与实测一致）：并发回填在 INSERT 2 与 3 之间启动，
子查询看到 `z_last` 与 `m_mid`（2 行）⇒ 给它们 0、1。
本测试随后 `migrate()`：`a_first` 仍 0 会被改，但 `m_mid` 已被改成 1 ⇒
EPQ 重检 `m_mid.ordinal = 0` **不成立** ⇒ 跳过，`m_mid` 保持 1。
最终 `a_first=0, m_mid=1, z_last=1` ⇒ **正是实测签名**。机制自洽。✅

### 3. 「同源同解」成立 —— 但说清它成立的**确切**前提

两个签名的**共同必要条件**都是：**并发回填必须看到这 3 行的一个真子集**。

- `[0,0,1]`：回填看到 2 行（`z_last`、`m_mid`），给 0、1；`a_first` 后插仍 0
- `[("a_first",0),("m_mid",1),("z_last",1)]`：同一起点，经 EPQ 静默跳过后固化

多行 INSERT 是**一个隐式事务** ⇒ 对其它会话**要么 3 行全都不可见、要么全都可见**
（PG 的 MVCC 保证语句级原子可见性）⇒ **子集这个前提消失** ⇒ 两个签名同时失去存在条件。

### 4. 修复后两种签名都不再出现 —— 实测确认

修复版 60 次进程运行（AC-001）**0 次失败**；
日志中 `[0,0,1]` 与 `[("a_first",0),("m_mid",1),("z_last",1)]` **两种签名均未出现**。

**结论：Dev 的「同源同解」判断成立，我独立复现了第二通道的存在与消失。**

## Q7 · 残留窗口 —— **我同意 BA 的「接受」，附条件**

### 窗口的代码事实（已核实）

`tests/test_snapshot_write_paths.rs:705`（INSERT）→ `:720`（前提断言）之间
**只有 1 条 SELECT**，即 **1 个 RTT**。Dev 说的 ≈157 ms 与我实测 p50 **158 ms** 吻合。

若恰好在此窗口内启动的回填把 3 行整批改掉，前提会读成 `[0,1,2]`。

### 独立风险评估

| 维度 | 评估 |
| --- | --- |
| 触发条件 | 回填**恰好**在 INSERT 提交后、前提 SELECT 到达前**整批完成** |
| 窗口宽度 | 1 RTT ≈ 158 ms |
| 需要回填命中 3 行**全部** | 是（子集已被原子 INSERT 消除，只剩整批这一种） |
| 后果 | 前提断言红，签名 `[0,1,2]` —— **测试假红**，不是漏检 |
| 性质断言是否受影响 | **不受影响** —— `[0,1,2]` 本就是回填的**正确答案**，①③④ 照常通过 |
| 本轮实测 | **60 次进程运行 0 次命中** |

**关键判断：命中时的表现是「前提断言假红」，而前提失败 ≠ 性质失效。**
这与 AC-001 关注的「性质被污染」是**不同严重度**的问题。

### 为什么同意「接受」

1. **AC-002 想保住的前提语义正是「回表读」** ——
   Dev 说改成 `RETURNING` 会让前提从「回表读」变成「读 INSERT 自己的返回」。
   **我认同**：`RETURNING` 读的是**本事务刚写的值**，
   它**结构上不可能**被并发回填污染 ⇒ 前提断言退化为**恒真断言**，
   等于**悄悄删掉一条有效前提**。这是**放松**，不是修复。**Dev 的取舍是对的。**

2. **代价对比悬殊**：
   - 保留窗口：极低概率的假红，**可被识别**（签名 `[0,1,2]` 一望而知是环境竞态）
   - 改 `RETURNING`：前提断言永久失效，**且失效是静默的**

3. **它不掩盖真缺陷**：前提红会立刻暴露，且 `[0,1,2]` 与真正的代码缺陷签名不同。

### 我的条件（建议 BA 记入已知悉）

- 未来若再出现 `[0,1,2]` 前提失败，**先按环境竞态排查**，不要误判为回归
- 若该窗口在某轮验收中**高频命中**（如 > 5% 采样轮次），应重新评估
- **不建议**为它改生产代码或用 `RETURNING`

**结论：同意 BA 的「接受」。这是有意识的、代价已知的取舍，不是疏漏。**
