Ontology Platform · Architecture View II

能力面架构 平台对外只有四件事，加一条纵切

会议纪要指出：「当前梳理的架构过于偏向底层技术实现，与本体核心逻辑关联度不足，需进一步向上抽象调整。」 向上抽象的落地方式只有两件事：把主视觉从模块换成能力，以及把本体核心模型从术语表提到图的正中央。

两种读法

组件面（2026-09-24-fde-ontology-platform-design.md §4.1）回答「系统由哪些模块组成」，面向工程师。

能力面（本文）回答「平台能做什么事」，面向业务与客户。同一套系统，两种读法，映射见 §07。

01总图

读图三个要点

1 · 只有四件事。建、审、用、动，加一条纵切「溯」。没有第五件。

2 · 实现全部收进内部。connector、采集器、pipeline、抽取引擎、agent-registry 收进「建」，mcp-server 收进「用」—— 它们没有消失，只是不再是主角，各自退到所属能力名下。

3 · 唯一被提到中央的，是本体核心模型。四个能力只是操作本体的四种动作。组件面图里「本体」只以一个叫 ontology-store 的存储抽象出现 —— 这是上一版最被诟病的地方：讲了很多怎么把数据搬进来，几乎没有讲搬进来的东西长什么样。

02四个能力

每个能力用同一套字段描述：谁用 · 做什么 · 产出什么 · 收起来的实现 · 依赖底座什么。最后一项是关键 —— 它说明「能力」和「本体」之间的受力关系。

抽取能力外置：一条边界的两侧

产出候选的生成能力可以外置 —— 通过 A2A 协议调用外部抽取 agent。但这不等于把整件事交出去：

为什么外置

抽取的方法是市场已经归纳过的东西 —— 不必等我们做满 5 个同行业项目再归纳。接入现成 agent 是复用的一条现成路径。

代价是新增三类风险：版本漂移（分不清 diff 是本体演进还是 agent 换人）、静默失败（把「什么都没抽」误判成「已收敛」）、成本不可控。三项对策已定并写入规格。

协议与合规

A2A（Linux Foundation）管 agent ↔ agent，v1.0 稳定版，150+ 组织支持；ACP 已于 2025-08 并入 A2A。MCP（已在用）管 agent ↔ 工具与数据。两者互补，不是二选一。

⚠ 数据出域：接入外部 agent 意味着 schema 与脱敏样本会出客户内网 —— 这与「原始数据不出域」的核心话术相关。三种处理（脱敏出域 / 私有部署 / 合同 sub-processor）逐案确认，不预先选。



范围闸门（2026-09-28 新增）：抽取范围由决策清单限定 —— 客户真正要改善的决策只有几条，起点不是「这个库里有什么」，而是「你希望操作员下个季度做出什么不同的决策？」。清单里没提到的数据源字段，本轮不抽。这是防止过度抽取最有效的一道闸门，也让「收敛」有了业务边界而非数据量边界。

写回的三条硬规则（切片 2 开工前必读）

写回是全项目风险最高的一环。一次「把设备状态改为维修中」看起来是一句话，实际上要同时解决四件事：

规则一 · 写比读严得多

读时身份不确定 → 标注出来，用户能看出来。写时身份不确定 → 必须拒绝。

理由：答错了是遗憾，改错别人数据是事故。

产品承诺：切片 1 允许跨库身份不确定（只读、无损害，但必须带标注）；切片 2 不允许 —— 跨系统回回必须有确定身份，否则只允许写单一系统。

规则二 · 哪些系统被写，必须显式列出

不做「按类型自动推导所有绑定」。若自动推导，则「给设备加了个状态字段」会静默地让某个 Action 从写 2 个系统变成写 3 个 —— 多写 = 误操作客户生产数据。

客户 IT 授权时面对的是一份具体清单，而不是「设备相关的都写」。

规则三 · 不一致不消除，只让它可被列出

跨系统分布式事务做不到，也不假装做。能做的是冲突检测：写回时带上读到的版本号，数据被别人改过就拒绝并如实说「没改成，因为数据变了」，而不是覆盖过去。

在设备运维场景，「最后写的人赢」会造成很贵的错误。宁可拒绝，不可静默覆盖人工决策。

至于「本体说 A、ERP 说 B、MES 说 C」这类不一致，由规则引擎列出来，结论进提案通道等人处理 —— 目标是可检测，不是假装不会发生。

非结构化源（IM / 文档）不被写回，但可以作为触发方：在群里 @某人派一张工单 —— 发起方是 IM，写回目标是工单系统。

03溯 Trace · 唯一的纵切

溯 不是第五个能力，它横跨前面四个：不是一步操作，而是每个操作都必须写下的属性。

每个对象类型 / 关系类型 / 动作都挂四个字段：

  • proposed_by —— 哪一轮、哪个 KH Agent 提出的
  • evidence —— 依据哪条数据 / 哪次抽取（可回到源证据）
  • approved_by —— 谁批的（建模轨 / 业务轨分别记）
  • approved_at —— 何时批的
两条设计决定

1 · 内部保持轻量。自己建表，不引入 RDF / 推理栈。企业本体的实际查询深度通常 ≤ 3 跳，为「理论完备」付的代价，在交付现场收不回来。

2 · 只在出口处付审计端的钱。对外导出时序列化为 PROV-O。内部是工程实现，对外是标准格式 —— 只在边界上做转换，不在内部做妥协。

会议明确 semantica 偏学术化、暂不适配当前需求。这里就是取舍的具体落点：不把 W3C 那一整套（OWL / SHACL / 确定性推理）搬进运行时，只在出口处对齐标准。

04本体核心底座

这是上一版架构最薄的一节，也是「与本体核心逻辑关联度不足」最直接的落点。四根柱子 + 三件治理物：

四根柱子

元素关键字段说明
对象 ObjectType key · display_name · description · aliases[] · parent · disjoint_with[] · properties[]（name / type / nullable / is_identifier / source[]） 一个业务实体。source[] 指向它来自哪个系统；aliases[] 是客户叫法与数据库字段名的翻译表；parent 表达「是一种」的层级
关系 LinkType key · source_type · target_type · cardinality · semantic cardinality：1:1 / 1:N / N:M。semantic：has / belongs_to / depends_on / …
动作 ActionType key · target_object_type · parameters[] · preconditions[] · effects[] · permission · audit_policy 对本体的写入。effects[] 描述「写回哪个外部系统的什么」
函数 Function key · signature · allowed_types[] 派生属性 / 聚合，不改变状态

三件治理物

元素作用
版本 Version快照与冻结的载体。审核通过的那一刻，产生一个不可变版本
提案 Proposal变更的原子单位。KH Agent 产出的是提案，不是直接改本体
证据 Provenance纵切（见 §03），挂在上述所有元素上

三条设计决定

  1. 关系独立成表，不做「实体 + 关系」打包。一旦打包，关系就无法单独携带基数、语义和证据，后面每一次查询和每一次审核都会付利息。
  2. 层级是类型的属性，不是关系。parent 挂在 ObjectType 上，不是一条 LinkType —— 否则「型」与「例」的界限会糊掉。客户说「设备分机器人和手工的，都是设备」，这是「是一种」，不是「有关系」。
  3. ActionType 与 Function 在切片 1 不实现，但模型必须占位 —— 这是硬性要求，不可省略。本体快照（OntologySnapshot）是存储层与领域层之间的唯一数据契约，提案应用、快照 diff、双轨视图投影都直接消费它。若切片 1 不占位，切片 2 引入 ActionType 时必须回头改动快照结构、diff 引擎、apply 逻辑与双轨视图 —— 推翻重来。对应地，本体实现计划必须包含这两个占位模型，以及 parent / disjoint_with。
  4. 证据内建、格式外对齐。内部表 + 出口 PROV-O 序列化 —— 两边都要，但只在出口处付费。

类的结构：层级与互斥

本体的类不是扁平的。层级 parent 表达「是一种」：

三个取舍

单继承 —— 企业场景 90% 是树。多继承带来的菱形歧义与查询复杂度，收益远小于成本。

必须做环检测 —— 环会让遍历查询不终止。写入时校验。

只继承「是什么」，不自动继承「有哪些关系」 —— 子类自动获得父类全部 LinkType 会让本体规模爆炸，且审核时看不出边界。需要显式建模。

互斥 disjoint_with[] 表达类型之间不能同时成立：「在役」和「报废」不能同时是一台设备的状态。

⚠ 互斥在切片 1 能做什么（诚实说明）

能：① 双轨审核时作为提示呈现；② 导出为 OWL 的 owl:disjointWith；③ 数据写入时的校验规则（一个实例同时命中两个互斥类型时告警）。

不能：本平台不做推理，因此不会自动从「A 与 B 互斥」推出「C 只能是 A 或 B」。那是描述逻辑的活。

一句话：disjoint_with 是给人看的和给机器校验用的，不是推理公理。不要因为它存在就以为本体有推理能力。

两者的分工：parent 决定「一个实例查询时能匹配到哪些类型」（向上匹配，扩展召回）；disjoint_with 决定「一次匹配结果是否自相矛盾」（横向校验，防止误召回）。

05标准对照与出口

本节回答一个一定会被问到的问题：「你们用了『本体』这个词，那你们的本体用标准语言怎么写？」

答案不是「我们有一层 OWL」，而是：一张对照表 + 一条出口。把每个设计元素逐一对到 W3C / 学术标准，明确标出哪里有损、损在哪。

为什么自己写这张表

把有损的地方写在自己的文档里，比等客户在采购评审时问出来要好得多。调研报告里 NHS 那个 3.3 亿英镑案例被议会盯上的理由之一，正是「算法黑盒无法审计、成果不可迁移」。主动交代有损，而不是被动解释缺陷。

我们的元素标准对应物无损？缺口与降级策略
对象 ObjectTypeowl:Class + rdfs:subClassOf无损本体的层级通过 parent 映射到 subClassOf
parent（层级）rdfs:subClassOf无损单继承。RDF 支持多重继承，我们主动不做
disjoint_with（互斥）owl:disjointWith无损但只在导出时表达，本平台不做推理
属性 Property数据属性 / RDFS literal基本无损nullable / is_identifier 不是 OWL 概念 → 归 SHACL
关系 LinkTypeowl:ObjectProperty无损—
cardinalityowl:FunctionalProperty部分N:M 与方向在 OWL 靠约定，不是可推理公理
semantic（has / belongs_to）无标准对应有损降级为 rdfs:label 注释，不可推理

汇总

OWL 覆盖 3/4 根柱子中的前两个（对象 / 关系）+ 3/3 件治理物；PROV-O 覆盖全部治理物。两个合起来约八成，剩余缺口集中在「动作」—— 也就是本平台最核心的差异化。

关于「动作」被降级的表态

ActionType 是四根柱子中唯一在语义网标准里完全没有位置的元素：OWL 是描述逻辑，只描述世界、不改世界；SHACL 只做验收、不做副作用。

因此对外表态必须诚实：

我们导出的标准本体，表达的是「这个世界由什么构成」，不表达「Agent 能对它做什么」。
后者是我们刻意保留的运营层能力，如需保留，请同时保留我们的 ActionType 定义 —— 它无法被 OWL 承接。

这不是缺陷，是取舍的公开化。动作优先是我们与纯知识图谱的分界线，导出时被降级是这一分界线的直接代价。

为什么不把推理放进运行时

核心是开放世界假设冲突

本平台的立身之本是「幻觉从不可测变成可测：查询要么命中本体，要么明确失败」—— 这是封闭世界。而 OWL 的根基是开放世界（OWA）：「没有断言 = 未知」，不是「不存在」。

于是「SN-001 没有关联工单」这句话，在本平台是确定没有，在 OWL 里是未知。若让推理结论直接进查询上下文，传给 Agent 的语义就从「确定」退化成「大概」—— 我们花大力力建立的「可测性」会被 OWA 亲手拆掉。

解法：推理进提案通道

不是放弃推理，而是改产物去向。本平台一条通用约束：凡是机器自动做出的语义判断 —— 无论来自 LLM、规则引擎还是 OWL 推理机 —— 产物一律是提案，须有人签字才能进入本体。

这样 OWA 的「未知」永远不会泄漏到查询里：自动化照做，封闭世界完好。而一旦有人签字，那句话就重新变成了「确定」。

附带的好处：规则引擎能算出「合并这三张表会波及哪些实例」，但它无权决定「这三张表就是同一个东西」—— 那个判断仍然要人来下。

出口策略

出口阶段说明
PROV-O 溯源切片 1已在 §03 定：只在此处对齐标准
SKOS 业务术语表POC 后业务轨审核产出的「命名与业务边界」直接导出。比 OWL 轻、客户接受度高得多，建议先做
OWL 本体待定有客户明确要求时再实现；届时照本节对照表实现即可，无需重新设计
SHACL 验收待定与必填 / 非空类约束一起导出

本节的定位：它是沟通资产，不是运行时组件。成本是一张表，收益是「主动交代有损」而非「被动解释缺陷」。

切片 1 的验收只看三件事：

  1. FDE 能在一个数据源上跑通一次抽取，产出一份本体提案；
  2. 客户能在一页纸的本体文档上看懂「有哪些对象、什么关系、每条从哪来」，并签字；
  3. 外部 Agent 能通过 MCP 查到这个本体。
留位规则

「动」和「溯」在切片 1 不实现，但底座留位。「溯」在切片 1 要有的最小形态是：点开任何一个对象类型，能看见它是哪一轮抽出来的、依据什么 —— 不需要推理机，不需要图数据库。

已明示的一处有意偏离：POC 不含写回

参考方法论把「交付没有动作类型的应用 —— 造出昂贵的仪表盘，把写回问题留给永远不会被资助的二期」列为五大失败模式之一，并主张动作先行。本项目在切片 1 明确偏离该主张，Action 推迟到切片 2。这是有意识的决策，不是遗漏。

理由：① 客户首轮签字的判据是「能回答我的业务问题」，问答价值先于写回价值；② 写回必须先解决权限与审计，POC 阶段客户 IT 未授权时硬塞写回会卡在审批上；③ 信任建立的顺序是先证明「只读也答得好」，反序反而更快获得授权。

代价：POC 交付物有沦为昂贵仪表盘的风险 —— 该风险并未消除，只是被推迟。缓释：交付物须含一页纸本体文档、决策清单驱动的问答演示（≥5 个客户级业务问题），并向客户明确呈现「下一步能写回什么」的能力路线。

红线：切片 2 不得再次顺延。若无法启动，须回到设计规格重新评估是否收缩本体范围，而不是把 Action 永久推迟。

实体对齐的降级方案

本体不做实例层实体对齐（公认的无底洞），但必须预先约定遇到该问题怎么办。

单库优先 + 显式声明：客户多源对同一实体（如「设备」）定义不一致时，本轮不做跨库对齐，而是把抽取范围收窄到决策清单涉及的那一个库，在一页纸本体文档中显式列出「本轮未解决的实体边界问题」（哪两个源、哪类实体、冲突在哪），转为生产阶段立项输入，不作为 POC 阻塞项。

禁止：为让问答跑通而在 POC 临时用规则硬合并两个源 —— 这会造出客户不认的本体，且违反「Agent 不能直写本体」。

09这张图回应了什么

逐条对应 2026-09-24 对齐会议纪要：

  • 「过于偏向底层技术实现」 主视觉从模块换成能力。connector / pipeline / store 从图的主干降为能力内部实现 —— §08 有完整映射，可逐条追溯，不是删掉了事。
  • 「与本体核心逻辑关联度不足」 本体核心模型（四根柱子 + 三件治理物）第一次作为独立一节出现在图上和文里（§04），并且被放在图的正中央。
  • 「需进一步向上抽象调整」 抽象的落点是能力，不是更抽象的技术分层。能力是业务和客户能直接理解的语言。
  • 「semantica 偏学术化暂不适配」 明确不把 OWL / SHACL / 推理栈搬进运行时；只在出口处序列化为 PROV-O（§03、§04）。2026-09-28 进一步补齐：§05 给出逐元素标准对照表，标明 ActionType 在语义网里根本没有对应物这一有损事实；并给出化解 OWA 冲突的办法 —— 推理结论只进提案通道，不直接进查询上下文。
  • 「POC 采用轻量模式，不得设置过高人员能力要求」 §07 给出切片 1 的最小门槛：单数据源、单 KH Agent、单轨审核、只读 MCP。四个能力里只需要三个能跑通。
  • 「生产落地阶段再由专门团队开展正式语义建模」 底座里 Function、ActionType、完整证据链都是为这一阶段预留的，切片 1 只占位不实现。
