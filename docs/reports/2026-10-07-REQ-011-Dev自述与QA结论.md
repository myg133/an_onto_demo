```

[BL1-AFTER]      object_types=3 | link_types=1 | action_types=3 | functions=2 | concept_groups=1
```

## 五、四项发现

### F1 · 中 · 迁移不回填历史行 `ordinal`

`ALTER TABLE ... ADD COLUMN IF NOT EXISTS ordinal INT NOT NULL DEFAULT 0` 只补列，**存量行全部并列 0**：

```
[MIG-LEGACY-ROWS] 补列后 3 条历史行 ordinal = [("a_old",0), ("m_old",0), ("z_old",0)]
```

共享库 `action_types` 共 2161 行，其中 **2149 行 `ordinal=0`**。旧版本读序仍由优化器决定 → **不丢行，仅顺序不稳**。切片 1 该栏为占位，故不阻断。

**切片 2 上线前必须清零。**

### F2 · 中 · 两处 INSERT 仍逐字重复 —— Dev 的去重拒绝理由**不成立**

Dev 拒绝去重，理由是「共享会把 apply 的唯一约束冲突从 `StoreError::Db` 变成 `StoreError::KeyConflict`，属错误语义变更，需产品决策」。

QA 逐字比对后指出**这个推理跳了一步**：

- `snapshot_store.rs:129-130` → `.map_err(|err| map_key_conflict(err, &a.key))?` ⇒ 23505 → `KeyConflict`
- `apply.rs:218-219` → `?` ⇒ 23505 → `StoreError::Db`
- 归一化（抹掉执行器）后 **13/13 行完全相同**，差异只在收尾那一行

**共享的是那 13 行，不是那 1 行错误映射。** 存在零语义变化的解法：

```rust
async fn insert_action_row(conn: &mut PgConnection, vid: Uuid, i: usize, a: &ActionType)
    -> Result<(), sqlx::Error>          // ← 返回 sqlx::Error，不碰 StoreError
{ /* 那 13 行原封不动 */ }

// save_snapshot:     .map_err(|e| map_key_conflict(e, &a.key))?   ← 语义不变
// write_snapshot_in: .map_err(StoreError::from)?                  ← 语义不变
```

**这条拒绝的代价不小**：本次缺陷的根因就是「两处各写一份」。Dev 在 commit 里承认「序列化不再各写一遍，避免下一次分叉」——却对结构完全相同的 INSERT 保留了分叉。**转 REQ-012。**

### F3 · 低 · 逐字节断言对「对称共享缺陷」零判别力

BL-2 比较的是 `read(v2)` vs `read(v1)`，两侧过**同一个读取层与同一批序列化器** → 缺陷对称命中时恒成立（M3 变异下 4 条断言全绿，兜底在 `test_snapshot.rs::test_snapshot_roundtrip`）。

加固建议（可选）：基准改用**内存中的 base 快照对象**而非读层结果，即可打破对称。

⚠️ 这**不是**说 BL-2 钉了 bug —— M1 证明它对缺陷本体确有判别力。

### F4 · 信息 · `ORDER BY ordinal` 全库仅一条守卫

M2 显示只有 `test_action_types_order_is_write_order_not_planner_order` 变红。删掉它，顺序缺陷静默回归。
