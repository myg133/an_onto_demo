# ADR-006 · 租户隔离是**产品机制**，口径是**项目声明**

- **日期**：2026-10-23
- **状态**：已接受
- **触发**：用户指出「R2RML 应该是产品能力，你为什么要问业务问题呢？」
- **影响**：REQ-122（SPARQL 端点）、REQ-123（Agent 契约）及一切面向客户的查询

## 我犯的错（记录在案）

我设计了「按表择优注入租户列」的机制，然后**去问业务方「一个客户对应什么」**——把**产品的配置能力**当成了**业务决策**。

正确的分层是三层：

| 层 | 归属 | 内容 |
| --- | --- | --- |
| **机制** | **产品** | 「按声明注入租户过滤」——通用、可配置、缺声明 fail-closed |
| **声明** | **项目/实施** | 租户键列、公共维度表、租户 id 的含义 —— 都是**数据**，不是代码 |
| **决定** | **业务方** | 只负责**填这份声明**，不参与机制设计 |

**判据**：产品的代码里**不得出现 `customer_id` / `main_customer_id` 这类字面量**用于注入决策。换个客户库（租户列叫 `tenant_no`）只需改声明，不改代码。

## 决策：两层分离

### 机制（产品内置，与具体库无关）

1. 读**声明文件** `query-policy.json`
2. 对查询涉及的每张表，按声明决定：**过滤列** / **公共维度不过滤** / **不可查**
3. 注入发生在 SQL 生成之后、执行之前，且**每个涉及的表都要有**
4. **无法判定 ⇒ 整条查询拒绝**（fail-closed），点名表并提示「请在声明里登记」

### 声明（项目提供，人可评审）

```json
{
  "version": "1.0.0",
  "tenantSubject": "customers",          // 租户主体类
  "tenantIdColumn": "id",                // 主体类的 id 列
  "perTable": {
    "deductions":  { "tenantColumn": "main_customer_id" },
    "customer_subscriptions": { "tenantColumn": "customer_id" }
  },
  "publicDimensions": [
    { "table": "package_templates", "reason": "套餐定义为产品目录，对所有客户相同" }
  ],
  "reviewed_by": "…"
}
```

⛔ 没有声明 ⇒ **所有表不可查**，报错提示生成模板。
⛔ 声明里没登记、又不在公共维度的表 ⇒ 不可查。

## 本项目（anspire）的初版口径（业务方 2026-10-23 拍板）

用户的三个回答**落进声明，不进代码**：

| 业务方决定 | 落到声明的哪里 |
| --- | --- |
| 一个客户 = 一个 `customers.id` | `tenantSubject: "customers"` + `tenantIdColumn: "id"` |
| 子账号数据归主账号 | `perTable.deductions.tenantColumn = "main_customer_id"` 等（逐表登记） |
| 套餐/模型/服务商等产品定义表不过滤 | `publicDimensions[]`（逐表登记 + 理由） |

**「有 `main_customer_id` 就优先用它」是这次声明的填写方式，不是产品逻辑。**
别的项目若没有主/子账号概念，就全部填 `customer_id`（或它自己的租户列）。

## 为什么这样分层

| 如果硬编码 | 后果 |
| --- | --- |
| 代码里写死 `customer_id` | 换库就要改代码并重新发布 |
| 代码里写死「优先 main_customer_id」 | 没有子账号概念的客户会被错误过滤 |
| 缺声明时「猜一个列」 | **猜错 = 跨租户泄漏，且不报错** |

## 后果

- **正面**：租户隔离是**产品能力**；换库只改声明；缺声明时失败在安全侧。
- **负面**：每个项目都要写一份声明（但有模板 + 缺声明时明确提示怎么填）。
- **将来**：子账号用户直连时，需要「租户解析」层（把子账号 id 解析成主账号），也应由声明驱动。
