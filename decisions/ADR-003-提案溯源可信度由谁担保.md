## 背景

规格 §8.4 要求每个本体版本记 `extracted_by`（哪个 agent、哪个版本、哪一轮、哪些组失败），
用于**在 agent 升级后解释 diff 的来源**。

ADR-001 规定了**取值口径**：apply 时原样取提案的 `extracted_by`，没有则记 `null`，
**不得推断、不得回退到 base**。

REQ-015~019 这一串的目的之一是消灭「静默假溯源」——`extracted_by` 记的 agent
与 items 的真实来源不一致，且无声。**已封住三条路里的两条。**

### QA-B 的实测（四条路，现状）

| # | 路径 | 状态 |
| --- | --- | --- |
| ① | `orchestrate()` 阶段 3+4 | ✅ 过 REQ-019 能力闸门 |
| ② | `propose::extract_with_context` / `RuleBasedAgent::propose` | ✅ REQ-020 编译期封死（`pub(crate)` / `#[cfg(test)]`） |
| ③ | **`ontok propose import`** | ❌ 从 JSON 原样取，零校验 |
| ④ | `PgProposalStore::create` | ❌ `pub`，`extracted_by` 直接 bind 进 INSERT |

### 实证（QA-B 直接 SELECT 取证，非 CLI 自述）

```bash
ontok propose import --file fake_real_items.json
  → 提案 p1 已导入（共 1 个条目）…（抽取来源：totally-not-a-real-agent 9.9.9-fake）
ontok review decide --accept-all  → accepted
ontok proposal apply              → v2
```

库里原始列：
```
proposals.extracted_by        = {"agent":"totally-not-a-real-agent","round":7,
                                 "version":"9.9.9-fake","failed_groups":["payments","risk"]}
ontology_versions v2.extracted_by = 同上        ← apply.rs:260-263 直写，一路传染
```
**零警告、零校验、零留痕。**

## 决策

> **提案的自我声明（`extracted_by`）默认不被担保；由写入通道负责留痕。**

三条具体裁决：

### D1 · `ontok propose import` 是**闸门之外的第四条路**，不是「绕过」

REQ-019 的闸门只装在 `orchestrate()` 上，REQ-020 守的是 `pub` 可见性。**两处都没漏检** ——
`propose import` 从来不在它们的守卫对象里。定性为「绕过」会把处置带偏。

### D2 · 这**不是安全漏洞**，是数据可信度问题

触发者本来就拥有写库与 `accept-all` 的能力，**不构成权限提升**；
不需要提权、不需要网络、不需要特殊知识——照抄 `fixtures/proposal-demo.json` 改两个字符串即可。

> ⚠️ 实证细节：`fixtures/proposal-demo.json` 里的 `demo-extractor 0.1.0` **同样是我编的字符串，
> 系统照样接受**。它在库里与伪造值长得一模一样 ⇒ **该接口在结构上没有任何真实性信号可判别**。

### D3 · 补齐的是 `concept import` **已有**的纪律，不是新增安全机制

**这是本 ADR 最硬的论据**，Dev 与 QA-1 都没提到：

```rust
// src/cli.rs:298-299 注释原文
// 抽取来源「不是「我」—— 声明是谁做的就记谁」
//   ↓ 配 domain/concept.rs:352-370 的 verify() fail-closed 内容指纹校验
```

实测对照（同一个伪造动作）：
```
$ ontok concept import --file concept_fake.json
✗ 改内容必须改版本：当前内容指纹 51b8689d… 与版本 9.9.9 记录的不一致
exit=1                                    ← 挡住了

$ ontok propose import --file fake_real_items.json
exit=0  静默入库                          ← 没挡
```

⇒ **`propose import` 是全系统唯一的漏网。** 论证基础是**内部一致性**，不是安全威胁。

> 诚实边界：指纹挡的是「改了内容不升版本」，**不挡「声明本身就是假的」**——
> 认真重算 digest 仍能编。

## 后果

### 真实危害（QA-B 逐条判定）

| 维度 | 判定 |
| --- | --- |
| 算不算 REQ-019 要消灭的静默假溯源？ | **算同一类，但不是同一处代码**。REQ-019 没漏检，只是四条路里封了一条 |
| 对 §8.4 归因的危害 | **真实但有限**。`extracted_by` 不参与收敛判定；版本链由 `seq` + 父版本承担，破坏不了 |
| 🔥 **真正危险的字段** | **`failed_groups`**。编造的 `["payments","risk"]` 被照单全收，而 `fully_succeeded()` 据此给出**错误的成功/失败判断** —— 这正是 REQ-019 想挡的「抽取失败可被隐藏」 |

### 处置（按 QA-B 建议，BA 采纳）

| 方案 | 决定 | 理由 |
| --- | --- | --- |
| (a) **文档**：写明「import 是信任边界」 | ✅ **本批做** | 破坏测试 **0** 个 |
| (b) **`source` 留痕**：区分「工具自产」与「外部声明」 | ✅ **本批做** | 内部一致性论证；**与 RN-2 的 `CandidateType` 契约改造同批**，避免二次迁移 |
| (c) **签名凭证** | ⏸️ **推迟** | 性价比差，无签名基建。且 `is_vague_version` 只挡 `latest` 这类模糊版本，挡不住格式良好的 `9.9.9-fake` |
| (d) **收窄 `PgProposalStore::create` 可见性** | ❌ **不做** | `tests/*.rs` 从 crate 外调用 `create` 共 **41 处**，会全断；**更关键是它挡不住本问题** —— `cli.rs:447` 在 crate 内 |

**(b) 的代价（QA-B 盘点）**：打破测试
`test_snapshot.rs`(19 处字面量必编译失败)、`test_apply.rs`(55 处，其中 `:251`
`test_extracted_by_is_not_inherited_on_apply` 逐字节比对必改)、
`test_concept_proposal.rs`(`:406` `assert_ne!` 必改)、`test_proposal.rs:235`、
`test_agent_orchestration.rs`(12)。

> ⚠️ **额外坑**：`extract/propose.rs:70` 有一个**同名不同型**的 `ExtractedBy`
> **已经带 `source` 字段**，与 `snapshot.rs:30` 的不是同一个类型。命名重复本身是隐患，
> 本批要顺手记一笔。

### ADR-001 保持原样

ADR-001 全文 74 行**没有回答**「谁来保证这个值不是编的」—— 逐行核过。
但它的逻辑**自洽**：它规定的是**取值口径**，而「提案自己知道」这个前提它并未声称要担保。
**改 ADR-001 反而越界。** 本 ADR 补的正是它没写的那一格。

## 对 RN-2 的约束

1. **RN-2 必须显式记账这一条**，不能只当 REQ-020 的尾巴 —— REQ-020 守的是路径 ②，已正确闭合。
2. **优先 (b) 而非 (c)** —— 论证基础是内部一致性，ADR 评审更容易过，代价可控。
3. **`source` 字段与 RN-2 的 `CandidateType` 契约改造同批做** —— RN-2 会产出更多程序化提案，
   假溯源会从「偶发」变成「常态路径」。
4. **`failed_groups` 单独提优先级** —— 它比 `agent`/`version` 写错更值得处理。
5. **ADR-003 保留，ADR-001 不动。**
