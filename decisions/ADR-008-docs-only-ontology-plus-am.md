# ADR-008 · 本体只来自云厂商文档，数据只走 access mapping

> 状态：**已接受**（2026-10-25 用户决策）
> 决策人：用户 · 记录：BA

---

## 一 · 决策

**丢掉 Ops360，本体与取数各归一：**

```
① 本体  ← 只从**腾讯云官方文档**抽（数据结构页 → 类/字段/关系）
② 取数  ← 只走 **access mapping**（接口定义页 → action / 模板 / 过滤器 / 迭代器 / 字段）
③ 不再把云资源落到我们自己的库里（`ops360_demo` 那套退役）
```

**一句话**：**语义来自云厂商的文档，数据来自云厂商的 API，平台只负责"说清楚"和"指路"。**

---

## 二 · 为什么这样更对

| 理由 | 说明 |
| --- | --- |
| **一个真相来源** | 不再出现"三套本体并存、名字都叫 ops/extracted" |
| **消灭了一整类问题** | 「文档概念 ↔ 数据库表/列 对齐」（REQ-148 的 G1/G2）**在 AM 路线下不存在**——属性对应的是 **API 字段**，不是列 |
| **数据天然是实时的** | 走 API 拿到的是此刻的真值，不是某次巡检的快照 |
| **凭据不出客户边界** | 我们只给"怎么取"，不碰 AK/SK（ADR-007 同一取向） |
| **平台保持无状态** | 不做数仓、不做联邦 |

---

## 三 · 代价（必须记账）

| # | 代价 | 后果 | 缓解 |
| --- | --- | --- | --- |
| **1** | **丢掉"口径类"** | Ops360 文档里的「备份覆盖率 / 告警总数 / 日均费用」是**算出来的**，API 不直接给 ⇒ **答不了"覆盖率多少"这类问题** | 将来若要，单独立"计算型类"（查询后聚合），⛔ 不能假装它是资源 |
| **2** | 数据来自**账号**而非客户业务库 | 演示看到的是验证账号的 3 台机器 | 演示材料必须标注来源（已有纪律：验证账号 ≠ 业务环境） |
| **3** | 本体广度受**文档覆盖**限制 | 只采了 10 个产品的数据结构页 | 客户用到别的产品 ⇒ 补采对应文档 |
| **4** | AM 的正确性受**接口语料**限制 | 没有入参表就只能猜（已踩：`Zone` vs `Filters[].Name`） | 正在补采接口定义页 |

## 四 · 由此作废/降级的事

| 项 | 处置 |
| --- | --- |
| `ops360` 项目（20 类旧文档本体） | 改为 `legacy-ops360`，不再服务；确认后删除 |
| `ops360_demo` 库（19,414 行巡检快照） | **不再需要**；确认后删库 |
| `extracted` v2（14 类，从表建） | 仅作为"DB 源路径"的历史样例保留，不进演示 |
| **REQ-148 的 G1 / G2** | **取消**（AM 路线下不需要文档↔表对齐） |
| REQ-148 的 G3/G4/G5 | **保留**：文档证据进快照（G3）、属性类型落库（G4）、`sourceKind` 三态（G5）——这三条与"数据从哪来"无关 |
| REQ-146 多方言 | 优先级进一步下降（不再需要把业务数据落库） |

## 五 · 落地顺序

```
① 本体重命名：extracted → <新名>（30 类，腾讯文档本体）
② 补采接口定义语料 → 生成 AM（先 8~10 个核心类）
③ 人签 AM（未签不许取数，REQ-144 已实现）
④ 部署 query serve --access-mapping + 30 类本体
⑤ 端到端：Agent 查类 → @pending + get → 调云 API → 拼答案
```

**待定**：新项目名（候选：`tencent-cloud` / `cloud-resource` / `ops-tencent`）。
⛔ 不建议还叫 `ops360`——那个名字绑定的是已退役的巡检文档集。
