# ADR-007 · 构建面 / 交付面分离（三分段架构）

> 状态：**已接受（决策记录）**，但**本期不实施**——见 §五 触发条件。
> 日期：2026-10-25 · 决策人：用户 · 记录：BA
> 相关：[设计稿](../design/2026-10-24-build-consume-split.md)

---

## 一 · 背景

产品目前是「一个镜像包打天下」：构建（摄取/提案）与消费（查询/门户）跑在同一套二进制里。

三个问题推动这次决策：

| # | 问题 |
| --- | --- |
| 1 | 客户源库需要出网（或在我们的环境里配只读账号）——安全部门通常不批 |
| 2 | 对外只读的容器里躺着能写库的 `ontok-propose` 与能调 LLM 的 `pi` |
| 3 | 每接一个客户，凭据与网络方案都要重谈一次 |

---

## 二 · 决策

**采纳三段式**：

```
① 构建面（客户网络）：把「资料 → 提案」做完
② 契约（跨边界）：一份带哈希的构建包 bundle
③ 交付面（我方）：人签 → 冻结 → 消费（只读）
```

配套三条：

| # | 决策 |
| --- | --- |
| D1 | 连接层（只读适配器）**可选**——保留"给我一个目录/一个只读账号"的最低接入路径 |
| D2 | 数据面（query/portal）用**只读 DB 账号**；控制面（console/接收 bundle）用读写账号 |
| D3 | 证据等级新增 `declared` 档（客户端声明实测）：服务端看不到源库时，`true` 只留给服务端亲测 |

---

## 三 · 为什么不现在做

| 理由 | 说明 |
| --- | --- |
| **时间** | 演示在即；拆分要 2–3 天且要动部署形态 |
| **收益延后** | 当前演示用的是我们自己的演示数据源，不存在"源库出网"问题 |
| **契约未定型** | bundle 的形状依赖 `@pending` / access mapping 这批新东西先稳定 |

---

## 四 · 被否决的替代方案

| 方案 | 为什么否 |
| --- | --- |
| 保持单镜像，靠 RBAC 限制 | 依赖"谁能 exec"；**账号权限比 RBAC 硬** |
| 只拆镜像、不拆流程 | 构建仍在服务端，凭据问题没解决 |
| 连接层必装 | 接入门槛变高（客户要先装服务） |

---

## 五 · 触发条件（什么时候做）

满足任一条即启动：

| # | 条件 |
| --- | --- |
| 1 | 接**第一个真实客户**，且其源库不能出网 |
| 2 | 要对外开放**普通模式**部署（有客户数据） |
| 3 | 项目数 > 3（单套负载的模式开始不经济） |
| 4 | 需要在客户现场跑抽取（FDE 带工具上门） |

---

## 六 · 后果

**正面**

- 源库不出客户边界；我们一根源库连接都不需要
- 交付面可只读，凭据面收敛
- 构建工具可按客户环境单独发版

**负面（必须接受）**

| 代价 | 说明 |
| --- | --- |
| 两个可交付物 | 要维护客户端工具 + 服务端 |
| 证据可信度下降 | 服务端无法复算"值域重叠"，只能比对 digest |
| 支持成本上升 | 出问题时不看得到客户现场 |
