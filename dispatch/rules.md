# 调度规则

## 派单前必做

> **对代码现状不熟时，先派 explore 摸底。**

- 派单成本 > explore 成本时，**必派**
- explore 输出必须包含：`path:line` + 风险点 + 建议方案
- explore 输出作为 briefing 的一部分喂给 Dev / QA

## 选人

| 条件 | 动作 |
| --- | --- |
| 需求状态 ≠ 已就绪 | 不得派单 |

## 1 worktree = 1 req（严守）

- 绝不跨 req 复用 worktree
- 绝不留下历史 worktree（合并即回收）

## 1 worktree = 1 写入者（2026-10-08 补,血泪教训）

**同一时刻，一个 worktree 只允许一个 agent 写。**

- 拆成多个并行 agent 时，**必须给每个 agent 一个独立的 worktree**
  （`git worktree add <name> -b <branch> develop`）
- 两个 agent 共用同一 worktree 会怎样？2026-10-08 RN-1 验收时真发生过：
  - BA 把「运行时实证」和「代码形状审查」拆成两个 verifier，**派进了同一个 worktree**
  - 两个会话同时对 `src/db/agent_registry.rs` 与 `src/agent/group.rs` 做变异测试
  - 一个会话的基线指纹**记录到了另一个会话的变异体上**（`group.rs` 记成 `67223789…`，
    实为对方 MUT4b 的中间态；靠与对方的 `RESTORED_SHA=9d0af42d…` 交叉比对才发现）
  - 差点让「并发安全的对照数字」取自被污染的源码
- **只读任务可以共用 worktree；任何会写文件的任务（变异测试、改代码、建临时测试文件）都不行。**
- 若无法拆 worktree，就**串行派**，不要图快。

## 子 agent 冷编译会拖死会话

- **必须要求子 agent 只用 worktree 自带的热 target**，`CARGO_TARGET_DIR` / `--release` / 另建
  probe crate 一律禁止。子 agent 的「我会注意」不可靠，**要用禁令式措辞写进 briefing**。
- 实证：2026-10-08 有两个 verifier 会话先后死在冷编译上（一次吐了 2393 个构建产物文件、638M
  后整个会话消失，输出全丢）。
- **要求「每验完一项立刻落盘」**，别攒到最后一次性输出 —— 输出会随会话一起没。
- 会话丢失后**第一件事查 worktree 是否被留下脏状态**，不能假设它干净。

## 门禁输入前置检查（REQ-048，2026-10-09 补）

> **跑全量测试之前，先跑前置检查。**

- **为什么要有这道**：`tests/drop_rate.rs` 与 `tests/test_fk_naming.rs` 都是 **fail-closed**
  门禁 —— 读不到脱敏 `schema.json` 就判失败，而不是安静跳过。这道纪律是对的，
  但它把「输入没了」推迟到**跑测试时**才暴露，而那份输入**不在版本控制内**。
- **输入不在版本控制内**：`.review-workspace/` 在仓库之外且被忽略，
  清理临时目录就会没 —— 本会话已被 BA 清理过 5 次，每次都可能把门禁输入一起带走。
  **`.review-workspace/fix-props/schema.json` 绝不可删。**
- **怎么跑**：

  ```bash
  export ONTOK_SOURCE_DATABASE_URL="postgresql://…"   # 口令只走环境变量，不入库
  cargo run --bin ontok-gate-preflight                # 现拉 + 落盘 + 校验
  cargo run --bin ontok-gate-preflight -- --verify-only   # 只校验已有产物，不连库
  ```

  退出码 0 = 通过（两个门禁现在都读得到）；非 0 = 失败，且命令会打印补救指引
  （含「设 `ONTOK_SCHEMA_JSON` 指向 X」），**不是**安静跳过。
- **落到哪**：默认写 `.review-workspace/fix-props/schema.json`。`drop_rate.rs` 的
  `../.review-workspace/…` 与 `test_fk_naming.rs` 的绝对路径**解析到同一个文件**，
  所以一个位置喂饱两个门禁，不用设任何环境变量；设了 `ONTOK_SCHEMA_JSON` 则以它为准。
  两条路径**分叉**时命令会**拒绝猜**并报错要求设 `ONTOK_SCHEMA_JSON`。
- **拦什么**：产物不是合法 JSON / 表数 < 80（对齐 `drop_rate.rs` 的 `MIN_TABLES`）/
  列数 < 900 / `tables` 数组与表头计数对不上（防「拉了个空壳也算通过」）。
- ⚠️ **源库 ≠ 测试库**：`ONTOK_SOURCE_DATABASE_URL`（源库）与
  `ONTOK_TEST_DATABASE_URL`（测试库，`.env` 里有）**刻意分开命名**。
  **⚠️ 源库连接串目前本会话不可得**（`.env` 只有测试库的，且其库名在实例上不存在）——
  所以本命令的「现拉」路径**尚无端到端实证**，只有 `--verify-only` 跑通过。
  详见 `dispatch/req-registry.md` REQ-048 行的登记。

## 变异施加器的两条硬规则（2026-10-11 立，来自 REQ-076/077 的 3 次事故）

**背景**：`src/domain/review_view.rs` 的测试侧 helper `prod()` 在 `#[cfg(test)]` 处**截断源码**。
变异若插在它**之后**，会把编译错误当成「红」—— **3 次 / 2 个需求 / 2 个角色**都踩了同一个坑
（REQ-076 的 Dev、REQ-076 的 QA、REQ-077 的 Dev）。
**三次都被当场识别、污染轮次全部丢弃，缺陷从未进入交付件。**

### 规则一 · 施加器必须自检插入位置

任何对该文件的变异施加器**必须内建**：

```
assert pos < src.index_of("#[cfg(test)]")
```

否则施加器**拒绝执行**。

### 规则二 · 编译错误**不算**变异执行

每轮变异跑完后必须：

```
grep -cE '^error(\[|: could not compile)' build.log    # 非 0 ⇒ 该轮无效，重跑
```

**编译失败不是「红」，是这一轮没跑成。**
依据本项目纪律：「编译失败不算变异执行」——这条早就写在 AC 里，
但**没有落到施加器里**，于是同一个错错了三次。

⚠️ **2026-10-11 修正模式本身**（来自 REQ-071 的 Dev）：
原来的 `grep -c '^error'` 会**误报** —— cargo 的测试失败汇总行是
`error: test failed, to rerun pass '--lib'`，
它以 `error:` 开头但**不是编译错误**。
⇒ **必须锚定编译错误自己的两种形态**：`error[`（如 `error[E0308]`）与
`: could not compile`。
⚠️ **2026-10-11 再补**（来自 REQ-071 的 QA 实测）：
`grep -cE '^error(\[|: could not compile)'` 对真编译错误 **3/3 命中**、
对 cargo 的测试失败汇总行 **0 命中**（旧模式误报 2），**不漏检** ——
因为 cargo 对**任何** target 失败都会补一行 `error: could not compile …`。
但裸编译还会出现 `error: aborting due to N previous errors` 与
`error: linking with … failed` 两种形态，**它们本身不匹配**。
⇒ 稳妥写法：把三个模式一起数，**任一非 0 即该轮无效**：

```
grep -cE '^error(\[|: could not compile|: aborting|: linking)' build.log
```

### ⛔ 为什么不是「更小心」

三次事故的共同点：**人都会检查「结果对不对」，
但没人检查「这一轮到底跑没跑成」**。
靠自觉已经失败了三次 ⇒ 必须变成**机制**。

### 规则三 · `sha256sum -c` 接得住「还原错了」，接不住「施加器构造本身错了」

2026-10-11 又一条工具层事故（M1w）：
`Value::to_string()` 会把控制字符**转义**成反斜杠 + n，
所以 `chars().any(|c| c == '\n')` **恒为 false**
⇒ 那个本该测「只封见证形状」的变异，实际退化成「**封条完全不生效**」，
**测的根本不是问的那一格**。

⚠️ **`sha256sum -c` 抓不到这类** —— 它只保证「文件被原样还原」，
不保证「变异构造的是你要问的那个问题」。
本会话三条工具层事故（M2 编译错误 / M1w 转义陷阱 / `restore.py` 回滚）
**缺陷永远在工具层、从不进交付件**，但**只有 `restore.py` 那条是被 `sha256sum -c` 接住的**。

⇒ **补一条纪律**：
**当「预期颜色」与「实测颜色」矛盾时，先怀疑自己的构造，不要先怀疑被测物。**
本会话两次靠这条识破误判（`faked==0` 前提、REQ-062 的「37/1」对照值）。

**为什么不能靠更小心**：靠自觉已经失败三次 ⇒ 必须变成机制或明确规则。

## 2026-10-11 补充 · 统计与回滚类事故（REQ-084 一轮出 4 次）

> **共同形态：一条看起来能用的命令/写法，安静地给出「零」或「假绿」，
> 而零与真值在这个场景里长得一模一样。**

### ⛔ 纪律 A · 禁 `git ls-files -z -c core.quotePath=false`

`-c` 放在**子命令之后**时，在本机 git 2.56.0 上**不被当作全局配置**，
该命令**静默返回 0 个文件** ⇒ 任何基于它的泄漏扫描都报「零泄漏」。

✅ 正确：`git -c core.quotePath=false ls-files -z`（`-c` 必须在子命令**之前**）。

⚠️ **这条错命令是 BA 写进 AC 和派单 briefing 的，Dev 与 QA 都照抄过**；
QA 因为结果可疑地等于 0 才抓到。**BA 的错误配方会一路传染给下游 agent。**

### ⛔ 纪律 B · 禁 Python `re` 的 `\b` 统计中文语料

Python 的 `\b` 在 **CJK 字符旁不成立**（`应` 被当作 `\w`），
`关联模型ID(对应llm_model.model_id)` 这类**中文夹标识符**会被系统性漏掉。

✅ 必须用 `(?<![A-Za-z0-9_])…(?![A-Za-z0-9_])`。

> 本项目因此错报一次：BA 实测 682 处，Dev 实测 **695 处**，差 13。
> **不是谁数错了，是口径不同且其中一个口径漏了。**

### ⛔ 纪律 C · 变异回滚若保留 mtime，必须 `touch` 强制重编

用 `shutil.copy2` / `cp -p` 回滚会**保留旧 mtime**，
cargo 据此判定 `include_str!` 输入未变而**不重编** ⇒
跑出的是**陈旧二进制**的假红假绿。

⚠️ 本次 Dev 先撞上这个，两条「失败」都是陈旧二进制假象，`touch` 后全绿。
**任何用保 mtime 的方式回滚后再断言测试结论的流程，都必须先 `touch`。**

### ⛔ 纪律 D · `.review-workspace/` 必须进 `.gitignore`

该目录沉淀 `classify/rows/inventory/备份`，**含全部 91 个真实客户表名**。
`workspace` 分支靠 `/*` 隐式覆盖，但 **`develop`/`demand`/`deploy` 原本都没覆盖** ——
一句 `git add -A` 就让整轮脱敏归零。

> REQ-084 QA 判 N1·高危。已补齐三处并实测 `check-ignore` 生效。
> **补任何 worktree 级临时目录时，同步查 `.gitignore` 覆盖，不要只改根目录。**

### ⛔ 纪律 E · 扫描结果为「零」时，先怀疑扫描器

本会话四次（quotePath 转义 / 扩展名白名单 / `xargs -0` 与 `-d` 冲突 / 本条的 `\b`）
都是**扫描器报零**而非**内容为零**。**零是异常值，不是结论。**

### ⛔ 纪律 F · 「不存在」同样是异常值

2026-10-12 我断言「QA 报告没落盘」，**是错的**——文件就在仓库根的 `.review-workspace/req087qa/QA.md`，
我只是**从一个 worktree 里去找**。当天的错误还有：`quotePath`、以及凭路径存在性下的结论。

⇒ **动手前先确认路径基准**：worktree 里没有仓库根的目录。

### ⛔ 纪律 G · 「变异二进制名」不是证据（REQ-086 QA 实测证伪）

`cargo test --lib mcp::tools` 选中的二进制路径 `target/debug/deps/ontok-<hash>`，
**每次 `cargo test` 都会按当前源码重建它**。

⇒ 变异 → 回滚 → 重建后，该二进制的 sha 与**干净构建逐字节相同**。
实测：Dev 报「二进制 `ontok-d86956d3ae2af69c`」，其 mtime 是 **11:35（QA 重建时）**
而非 Dev 跑变异的时刻 ⇒ **该路径无法区分「跑过变异」与「没跑过」**。

⚠️ Dev 的**条数是真的**（QA 独立复现了），但**形式上等于没交**。

⇒ **变异证据必须是三元组**：
1. **变异期间的二进制 sha256**（不是路径名）
2. **patch 的 sha256 或内容本身**
3. **运行条数与逐条结果**

只给「二进制名 + 条数」在当前工具链下**不可审计**。

### ⚠️ 纪律 H · 一致性守卫抓不到「忠实的重复实现」

REQ-086 的 AC-004 比对「MCP 与页面输出相等」。
若有人把被复用的函数**复制一份、内容完全一致**，两边照样相等 ⇒ **永远绿**。

⇒ 与 REQ-066 残留 S6 同一类：**一致性 ≠ 无重复**。
此类一律**登记为已知限制**，不得写成「已封堵」。

## 2026-10-12 补充 · 调用环境类事故（同日栽 6 次以上）

### ⛔ 纪律 I · 每条命令自带 `cd` 或用绝对路径

实测：`ontok project list` 的输出走 **stderr**，不是 stdout。
加 `2>/dev/null` 会把全部输出吞掉，看起来像「没有项目」。

⇒ 采集 CLI 输出时用 `> file 2>&1`，**不要**用 `2>/dev/null`。

### ⚠️ 纪律 K · 本机 worktree 的入库文件可能是脱敏版

`code/src/extract/table_names.json` 在本机是 **skip-worktree 的真版**，HEAD 里是脱敏占位版。
worktree 与克隆仓库**拿到的是不同内容**。

⇒ 做「入库版 vs 本地版」对照时，必须用 `git show HEAD:<path>` 取入库版，
**不能直接读工作区文件**（否则 A/B 两组用同一份文件，对照无效——本次就发生过）。

### ⛔ 纪律 N · skip-worktree 是**每个 worktree 独立**的位，建新 worktree 必须重放

2026-10-12 REQ-090 实测踩中。

| worktree | `git ls-files -v` 位 | `src/extract/table_names.json` |
| --- | --- | --- |
| `code/`（develop） | `S`（skip-worktree） | `version 1.2.0` · source `<业务库名>` —— **真版 91 条** |
| `feature-REQ-090`（新建） | `H`（普通） | `version 1.3.0-desensitized` —— **脱敏占位** |

⇒ **`git worktree add` 不传播 skip-worktree**。每个新 worktree 都**静默**拿到 committed 的脱敏占位版。

**后果**：真实 schema 与占位翻译表 **91 个表名零重叠** ⇒ 覆盖率 0% ⇒ 丢弃率 96.9% ⇒
`tests/drop_rate.rs` 与 `tests/test_fk_naming.rs` 两条**红线**测试必红。
Dev 一度判为「仓库状态问题」并要求 BA 在三条路里选一条 —— **三条都不对**，
真正成因是这个位没重放。

⇒ **建 worktree 后第一件事**（或派 Dev 前）：

```
cp <develop worktree>/<资产路径> <新 worktree>/<资产路径>
cd <新 worktree> && git update-index --skip-worktree <资产路径>
git ls-files -v -- <资产路径>      # 必须显示 S
git status --short                 # 必须为空
```

⇒ **基线数字必须标明在哪个 worktree 测的**。`780/0/1/59` 是 `code/` 的数；
同一个提交在新 worktree 里可能是 `795/3/1/60`，**差的不是代码，是本地资产**。
⇒ 这是纪律 K（「worktree 与克隆仓库拿到的是不同内容」）的**成因侧**，K 只说了现象，L 补了机制。

### ⛔ 纪律 O · 基线必须与 commit 绑定，不许记裸数字
2026-10-16 实证：我把门禁基线记成 `780/0/1/59`，之后**再没更新过**，
而 REQ-086 是在 REQ-087 **之后**才合并的，它往 `src/mcp/tools.rs` 加了 6 条测试把基线抬到 786。
于是 `780` 这个数字**静默过期了 20 条**，而我用它卡了整整三个需求。

```
f8c7240 [合并] REQ-087 → 780   ← 我一直拿这个当门禁
0b32dff [合并] REQ-086 → 786   ← 排在 REQ-087 之后，+6
0977719 REQ-090 新增   → 798
a7f424c REQ-090 修契约 → 800
```

⚠️ **这次查出来结论是好的**（没丢测试，静态 `#[test]` 计数 `782→802` 与运行时 delta 一致）。
但**过程本身证明了一件事**：救回来的是 **QA 报了两次 798、我对不上眼**，
**不是**我自己的核对。**如果这次真是丢了 20 条测试，我同样会看到「对得上」就放过。**

⇒ **基线的记法**：`passed/failed/ignored @ <commit 短 hash>`，缺 hash 的基线视同无效。
⇒ **每次合并 develop 后**，基线数字必须刷新，且**在登记表的验收结论里重述一遍**，
  不要指望下一轮还记得去查 `git log`。
⇒ ⚠️ 与纪律 E/F 同源：**「对得上」不是一个结论，是一个该被怀疑的状态**。

### ⛔ 纪律 P · 证据输出里混着与被测物无关的噪声

`cargo test` 的输出是本项目**验收证据的载体**（变异证据、数量统计、失败清单都靠它）。
输出里混进无关警告 ⇒ 读者每次都要重新判断「这条算不算数」⇒ 证据的信噪比被稀释。

⇒ 新增/修改代码后，**顺手扫一眼编译警告**。发现既有警告就**单独立项清掉**，
  不要攒着 —— 攒着的结果就是每个读证据的人都要替它做一次判断。

### ⛔ 纪律 Q · 源码扫描型守卫，变异证据取**工作区文件 sha256**，不是二进制 sha256

REQ-093 的 QA 用变异实测发现：守卫 `server_has_no_write_path_to_the_ontology`
是**拼写黑名单**（扫 `src/server/` 里有没有 `INSERT` / `UPDATE` / `DELETE` 这几个词）。
注入一条真实的 `delete from snapshots`，改成 `query_scalar` + 小写 ⇒ **全部放行**。

⚠️ **这里暴露了纪律 G 的一个边界**：
那个守卫的 `read_source` 是**运行时读工作区文件**，不是编译进二进制的。
⇒ 变异 B1 与 B2 的**测试二进制 sha256 完全相同**（`b8884eb2…`），
**「变异二进制 sha256」在这类守卫上根本不构成证据**。

⇒ **规矩**：守卫若在运行时读源码，变异证据取**被扫文件的工作区 sha256**；
编译进去的守卫才取二进制 sha256。**分不清是哪种，就两种都记。**

⇒ **更根本的推论**（REQ-093 QA 已独立验证）：
「HTTP 面无写路径」这个结论**本身为真**，但它是靠**人读代码**得出的，不是靠那条测试。
⇒ **纪律 H 的加强版**：守卫强度不足时，**结论的真伪要单独取证**，不许拿「测试全绿」当结论已证的证据。

### ⚠️ 纪律 R · 「只读」要写清是**哪个面**只读

`cli.rs:703` 对**所有**子命令无条件跑 `migrate`（DDL + 回填 UPDATE）—— 基线既有。
所以 REQ-093 的 `ontok serve` 进程**启动时仍需库写权限**。

⇒ 它的准确说法是「**HTTP 暴露面只读**」，不是「这个进程只读」。
⇒ 下一个人看到「只读服务」四个字就以为不需要写权限 ⇒ 会配错部署。
**凡是说「只读」，必须写清是哪个面。**

### ⛔ 纪律 S · AC 自己也会是错的，先跑一遍再发出去

同一轮 BA 发出两条 AC，**QA 用实测把两条都推翻**：

| BA 的 AC | 为什么错 |
| --- | --- |
| 「`grep 'sqlx\|PgStore\|db::' src/domain/` 必须无输出」 | **基线已有 9 处命中**（全在注释里）。这条判据在写下它时就已经不成立 |
| 「图内容与 `ontology overview` 逐条比对」 | `graph.rs` 的 `project` **零过滤** ⇒ 二者必然恒等 ⇒ **比对是空转**（纪律 H） |

⇒ 派单前，**每条可机械检验的 AC 自己先跑一遍**。跑不出结果的判据不是判据。
⇒ 这不是 Dev/QA 的问题，是需求方的问题 —— 而需求方不会有人来纠正你。

### ⛔ 纪律 T · `pkill -f` 会匹配到自己

QA 与 BA **各自踩了一次**：命令串里含被匹配的模式串，`pkill -f` 把自己所在的 shell 杀了。
⇒ 用**精确 PID**（先 `pgrep -f` 拿 PID，确认不是自己，再 `kill <pid>`）。
⇒ ⛔ 更要紧的是：**不许误杀别人的进程**。QA 发现 `127.0.0.1:18812` 上有他人进程，全程未碰 —— 这个判断是对的。




## 提交前自检（2026-10-21 新增，源于 REQ-110 的误删事故）

> **事故**：Dev 做测试绕行时把 `src/bin/ontok-gate-preflight.rs` 挪出工作区、未挪回；

2. **挪文件的绕行必须在 `finally` 里挪回**，并在命令末尾同时打印 `sha256` 与 `Test-Path` 两项确认；

**为什么记在这里**：这类事故**不会被任何测试抓住**（本地全绿），只有「看 diff」能抓。


## 失败路径必须能区分「做完了」和「没做完」（2026-10-22 新增）

> **事故**：REQ-118 首轮，模型调用**超时**时三命令 `exit 0` + 落一份**可导入的空提案**，concept 还打印「可直接 import」。
> 用户导入空提案会以为成功。—— 与「隐藏 .pdf 静默跳过」「闸写好没接线」同属**装作处理过**。

**硬规定**：

1. 任何批处理命令必须有**三态**：`complete=true` / 部分失败（`complete=false` + `failed_batches` + **exit≠0**）/ 全部失败（**不产产物** + exit≠0）。
2. ⛔ 禁止在未真正完成时打印「可直接使用」「已导入」「已生成」这类**结论式提示**。
3. 判据要能构造出这三种情形各验一次。

## 测试库必须独立（2026-10-22 新增）

## Windows 上跑测试的正确绕行（2026-10-22 订正）

> **旧规程是错的**：「把 `src/bin/ontok-gate-preflight.rs` 挪开再跑」——**在本仓不成立**。

**正确做法（QA 实测有效）**：用**行号不变的 3 行 shim**——给 unix-only 代码加 `#[cfg(unix)]`，给依赖它的测试加 `#[cfg(all(test, unix))]`，跑完还原并校验 sha256。
**或者**：直接跳过该套件并在报告里写明「Windows 绕行代价」，⛔ 不许把「没编译」当成「通过」。

**为什么值得写下来**：这条错误规程被 Dev/QA 各自「重新发明」了至少 4 次，每次都花时间，且每次都要重新解释「为什么挪走会编不过」。


## 安全规则必须「全路径 fail-closed」（2026-10-22 新增）

> **事故**：REQ-120 的「租户键禁止继承」闸只做在**提案生成**阶段；QA 实测：**手工改签字文件就能把一条 tenant inherit 注入**，且无警告。
> 设计说明写着「闸只影响生成阶段」，于是 QA 按字面判为非阻断。

**裁定（BA 改判阻断）**：

> **规则能被文本绕过，就不算规则。** 签字文件是文本，谁都能改。

**硬规定**：任何安全类约束必须在**每一层**复核，且 fail-closed：

| 层 | 要求 |
| --- | --- |
| 生成 | 不产生违规项 |
| **签字 / 导入** | **复核**违规项 ⇒ **拒绝整份文件** + 点名 |
| 注入 / 落库 | 纵深防御，再拦一次 |

⛔ 不许「警告后继续」；⛔ 不许「在文档里说明范围」当成已处理。


## 派单前必须查 agent 状态（2026-10-23 新增）

## 提交前必须验「分支上真的有东西」（2026-10-23 新增）

> **事故**：REQ-123 首轮，分支 `develop..HEAD` 计数为 **0** —— 实现（7 个新文件 + 测试）全是 untracked。
> 本地 `cargo check` 照样绿（工作区里有文件），`git merge` 却只会合入「分支上的提交」⇒ **合并会丢掉整个功能**。

**硬规定**：交付前必须验三件：

1. `git rev-list --count develop..HEAD` **> 0**
2. `git status --short` **为空**（无 untracked 的实现文件）
3. 在**独立 worktree / clone** 里能 `cargo check`

⛔ 不许把「我本地能编译」当成交付完成。


## 变异实验要用独立 CARGO_TARGET_DIR（2026-10-24 新增）

> **事故**：REQ-130 的 QA 在**共享 `target/`** 的条件下做变异，遇到一次**缓存假象**（改完代码仍是旧结果）；
> `cargo clean -p ontok` 重建后才得到正确结论。

**为什么危险**：缓存的假象是**两个方向**都会错——可能让"该红的没红"（放过真问题），也可能让"该绿的显示红"（白改一轮）。
而变异实验的全部价值就在于"红/绿可信"。

**硬规定**：

1. 变异 worktree 一律设 **独立目标目录**：
   ```powershell
   $env:CARGO_TARGET_DIR = "D:\tmp\cargo-mut-<REQ>-<n>"
   ```
2. 改完必须确认**真的重编**（看 `Compiling ontok` 行，而不是 `Finished` 一闪而过）
3. 与既有的 `Copy-Item` mtime 坑同类：**还原后也要 touch/clean**，否则下一次跑的是旧二进制

> 这条和「检查不生效」「假回执」是同一个母题：**我们的观测手段本身要先可信**。


## 子 agent 的临时目录必须在 workspace 里（2026-10-24 新增）

> **事故**：REQ-135 / REQ-137 的 QA 把 cargo target 与证据建到了 **`D:\qa-req137-target`（9.5 GB）**
> 和 **`D:\tmp\cargo-mut-135-*`（15.7 GB）** —— 盘根目录 + 24.6 GB 垃圾，靠人提醒才清掉。

**为什么这不能靠自觉**：

| 问题 | 后果 |
| --- | --- |
| 建在盘根 | 没人知道它是谁的、能不能删 |
| 一次 5–10 GB | 几次就把盘塞满，别人构建失败 |
| 交付时不清理 | 越积越多，最后没人敢删 |

**硬规定**：

1. 子 agent 的所有临时产物（cargo target / 证据 / 日志）一律放 **workspace 的 `.local/`** 下：
   ```
   .local/cargo-mut-<REQ>-<n>/     # 变异用的独立 CARGO_TARGET_DIR
   .local/qa-<REQ>-artifacts/      # 证据
   .local/tmp/                     # 其它临时
   ```
2. ⛔ 不许在 `D:\`、`C:\` 根或用户目录下新建目录
3. **交付前自查**：报告里必须写「临时目录：`.local/…`（已清理 / 保留）」+ 用 `git status` 确认 `.local` 不在版本库
4. BA 派单时**明确写死路径**，别只写「用独立 target」

> 这条和「变异必须用独立 CARGO_TARGET_DIR」是同一条规程的两半：
> **独立是为了结果可信，放在 .local 是为了不祸害别人的机器。**

## 两个 worktree 共用一个 CARGO_TARGET_DIR ⇒ cargo 会复用别人的产物（2026-10-25 确认）

> **事故**：REQ-143 的 QA 第一次跑出「sha 与基线相同、`--help` 里没有 `--allow-doc-only`」的**假特性二进制**，
> cargo 还打印 `Fresh ontok … feature-REQ-143`——它把**另一个 worktree** 的产物当成了自己的。

**为什么危险**：这会让"新功能没生效"看起来像"功能没实现"，而实际是**你测的不是你改的那份代码**。
两个方向都会错：该红的没红、该有的特性看不到。

**硬规定**：

1. **每个 worktree 一个 target dir**：`.local/cargo-<REQ>-<worktree 名>/`
2. 跑验收前先看 `cargo build` 的输出：出现 `Fresh` 就要怀疑；**必须看到 `Compiling ontok`**
3. 二进制自证：改完功能后先跑一次能暴露新功能的命令（如 `--help | grep <新参数>`），再开始正式验收


## 一个行为只能在一个文档里定义（2026-10-25 新增）

> **今天犯的同类错误**（三次）：
>
> | # | 错法 | 后果 |
> | --- | --- | --- |
> | 1 | AC 里写死数字（83 类 / `properties≥67` / lib 719） | 数字错 ⇒ Dev/QA 按错的判 |
> | 2 | 裁定写在 `acceptance.md`，`demand.md` 正文没同步 | 下一个读 demand 的人读到**已被推翻的口径** |
> | 3 | **同一个行为在两份文档里写了两套**（契约 §3.2 跨源 pending 带 `get` vs REQ-145 AC-006 不带） | Dev 实现时**无法判断哪个算**，只能来问 |

**根因**：我在"写得多"和"写得一致"之间没有机制，只有记忆。

### 文档职责（**每个事实只有一个家**）

| 文档 | 唯一负责 | ⛔ 不许包含 |
| --- | --- | --- |
| `BA/design/*.md` | **跨需求的协议与形状**（TTL/JSON-LD/@pending/access 契约的形状） | 某条需求的判据 |
| `demands/REQ-*/demand.md` | **这条需求要做什么、不做什么、裁定** | 重复定义协议形状（引用 design） |
| `demands/REQ-*/acceptance.md` | **可执行的判据** | 重述形状（引用 design） |
| `demands/REQ-*/status.md` | **状态与结果** | 重述判据与形状 |
| `Deploy/skills/*`、`BA/runbook/*` | **面向使用者的话术与步骤** | 定义协议（引用 design） |

### 硬规定

1. **写任何"形状/行为"之前先问**：它已经在哪里定义了？
   - 没有 ⇒ 定义在 `design/`
   - 已有 ⇒ **只写引用**（`见 BA/design/xxx.md §3.2`）
2. **裁定改变既有定义时**：⛔ 只在 acceptance 里加裁定 ——
   **必须同时改 `design/` 里那份**，或在 design 里标注「已被 REQ-xxx 裁定 R-A 覆盖」。
3. **数字**：需求文档里不写"当前基线数字"（会过期）；只写"判据形态"，基线由 Dev/QA 自报。
4. **判据检查**：派单前 grep 一遍新需求文本里的形状关键词（`@pending` / `sourceKind` / `mapping_version` …），确认**没有第二处定义**。


## 验证命令必须覆盖**全部判据类别**（2026-10-25 新增）

> **事故**：REQ-144 的 Dev 用 `cargo test --lib --tests` 跑"全量"，
> **把 doctest 排除在外** ⇒ 漏报了一条新增的 doctest 红（`src/access/mod.rs:23` 的裸代码围栏）。
>
> 它自己复盘得很准：**「验证命令比判据窄」**——不是判据弱，是**没跑到**。

**硬规定**：

| # | 要求 |
| --- | --- |
| 1 | 说"全量"就**裸跑** `cargo test --no-fail-fast`（含 Doc-tests / doc 示例） |
| 2 | 交付里写清**跑了哪些目标类别**（lib / tests / doc / 集成），⛔ 不许只写一个数字 |
| 3 | 任何 `--lib` / `--test xxx` 的单跑，必须在交付里标"这是子集，不是全量" |

> 同一类病的另一面：**判据写在两处而只维护一处**（REQ-144 的 fixture 与生成脚本各有一份"岗位说明"，README 说"同代码同字节"，实际 sha 不同）。

## 夹具里的"说明字段"必须与实际数据一致（2026-10-25）

> REQ-144 的 fixture 有个 `_comment` 写着「奇数行 `ap-guangzhou-3`」，
> 而数据实际是**奇数行 `ap-guangzhou-2`**。

**规定**：夹具里的注释/溯源字段，**必须由生成脚本自己算出来**（不是手写），否则它迟早与数据不符。
并且必须标清**哪些键不是真实 API 返回**（同一份夹具里还混进过一个真实 API 不存在的 `InstanceStateRaw`）。


## 基线对拍：**SKIP 不许记成 passed**（2026-10-25 新增）

> **事故**：REQ-144 阶段 1 的 QA 发现，基线二进制那轮有 3 条 live 用例显示**绿**——
> 实际是提取的基线树里 `code/out/schema.json` 相对路径不存在，走了 `*** SKIP`，**而 SKIP 被计入 passed**。

**为什么危险**：这会让"基线也绿"的结论变成**假绿**——
你以为是"两边一样好"，实际是"基线那边根本没跑"。

**硬规定**：

1. 基线对拍必须**单列** `passed / failed / SKIP` 三个数，⛔ 不许合并
2. 任何用例的 SKIP **必须在报告里点名**（哪条、为什么跳）
3. "0 新增失败"的结论，前提是**两边 SKIP 集合相同**；不同就要解释

> 这与「判据既要能红也要能绿」是一体的：**一个不跑的用例，既不会红也不会绿。**


## live 测试必须带 `ONTOK_REQUIRE_FIXTURES=1` 跑（2026-10-25 新增 · **这条抓到了一个假绿**）

### 事故

REQ-145 交付时报「`test_req145_live` **9 passed**」，QA 也在报告里引用了这个 9/9。
**但实际是 9 条 `*** SKIP: … 这条判据没有执行，不是通过 ***`** —— 缺 `ONTOK_REQ123_TENANT` / schema / policy。

**在 `ONTOK_REQUIRE_FIXTURES=1` 下重跑，9 条全部 FAIL。**

⇒ 「9 passed」是**框架默认行为**：`tests/common/skip.rs::missing()` 默认只打一行标记然后**正常返回**，
Rust 测试框架于是把它算成 **passed**。

### 为什么这是最坏的一类假绿

| 它和之前那些假绿的区别 | 说明 |
| --- | --- |
| 之前：判据写错 / 数据是造的 | 至少**跑了** |
| **这次：根本没跑，却显示通过** | 屏幕上还留着"这条判据没有执行"的字，**但汇总数字把它抹掉了** |

**看汇总的人只会看到 9/9 绿。** 这不是某个人的疏忽，是**机制默认值选错了**。

### 硬规定

1. **任何 live / 端到端测试，必须带 `ONTOK_REQUIRE_FIXTURES=1` 跑**；不带就**不许**把结果写进交付
2. 交付里报测试数字时，**必须分三列**：`passed / failed / SKIP`（⛔ SKIP 不许并进 passed）
3. 看到 `*** SKIP:` 行 ⇒ 该判据**视为未执行**，⛔ 不许当"通过"引用
4. 如果环境确实不具备（缺 DB / 缺 tenant）⇒ 写成 **「未执行（缺 X）」**，并列入遗留

> **汇总数字会撒谎。** 判据到底跑没跑，要看逐条输出里有没有 `SKIP`。


## 对拍用的基线**必须包含生成物**（2026-10-26 新增）

> **事故**：REQ-151 的 QA 复制基线源码时**漏了 `out/` 与 `code/out/`**，
> 于是同一批 live 用例走了 **vacuous ok**（拿不到夹具就当通过）⇒ 基线 34 failed、HEAD 33 failed，
> 看上去"HEAD 少一个红"，实际是**基线少跑了**。

**硬规定**：

1. 用 `git archive` 导基线时，**必须**同时带上生成物（`out/`、`code/out/`）或先跑一次生成步骤
2. 报告里写清「基线是怎么得到的」（archive / clone / worktree + 哪些生成物）
3. 看到"基线比 HEAD 多一个红"时，**先怀疑基线没跑全**，不要先怀疑代码

> 这是第三个同类假绿：`SKIP→passed`、`fixture 必填→反向造`、`生成物缺失→vacuous ok`。
> **共同点：判据在"没有输入"时默认通过。**


## Dev 任务必须**分检查点提交**（2026-10-26 新增）

> **事故**：REQ-152 阶段 2 的 Dev **中途崩溃**（无收尾报告），留下 5 个文件 / 705 行未提交改动、
> **32 个编译错误**。因为一次改了 412 行（`source_gate.rs`），崩在半路时**没有任何可用产物**，
> 只能整体丢弃、重来。

**硬规定**：

1. 任务拆成 2–4 个**检查点**；**每个检查点结束必须 `cargo check` 通过并 `git commit`**
2. ⛔ 禁止"改完所有文件再一起提交"——中途崩了等于零
3. ⛔ 单个文件一次改动超过 ~200 行时，先提交一个"结构就位但不接线"的中间态
4. 交付报告里列出检查点提交号（`git log --oneline` 应能看到 2–4 条）

**为什么**：Agent 会崩（上下文耗尽 / 超时 / 工具异常）。**检查点决定崩了之后还剩多少。**

## 验收口径（2026-10-27 立，来自 REQ-159 构建端事故）

**教训**：Dev 报「29 passed」，BA 复跑**同一条命令**也绿，但 `cargo test --lib bundle::` 在 HEAD 上是 **13 passed / 1 failed** ——
一条库内单测从提交起就是红的，两边都没跑。全量 `cargo test` 必然失败。

**为什么会漏**：Dev 只跑了自己新增的集成测试文件，BA 只复跑了 Dev 点名的那一条。
**「跑过测试」≠「跑过会红的那个测试」。**

**硬规定**（每次验收都要走完）：

| # | 要求 |
| --- | --- |
| 1 | 必须同时跑：**库内单测**（`cargo test --lib <模块>::`）+ **目标集成测试**（`--test <file>`）+ `cargo check --lib` |
| 2 | ⛔ 不许只复跑 Dev 指定的那一条命令 —— 那是复述，不是验收 |
| 3 | **报错文案也要验**：字段路径 / 错误码 / 点名对象，肉眼核一次（REQ-159 的 F-01 就是「路径被拼成 `manifest.json.manifest.json.files[0].sha256`」，测试红、文案也错，但没人看文案） |
| 4 | 交付报告里的测试数字要写**命令原文**，不许只写「全部通过」 |
| 5 | QA 退回后必须**回给同一个 QA 复验**，不许自己判「已修」就合 |

## 守卫变红时：**补登记**，⛔ 不许**改代码迎合守卫**（2026-10-27，来自 join 的自纠）

**事件**：join 派去修守卫的 Dev 为了让 `test_retained_names_req084` 变绿，把 `src/domain/concept.rs` 里
真表名 `customers` / `licenses` 改成了 `t2` —— 那是**抹掉证据**。join 自己发现并回滚，

**为什么危险**：两者**看起来一样绿**。

| 做法 | 守卫变绿 | 「这条性质曾经被测过」 |
| --- | --- | --- |
| 改代码迎合守卫 | ✅ | ❌ **消失**（而且没人会知道它消失过） |
| 补登记 + 更新计数 | ✅ | ✅ 保留 |

同类问题：`assert!(!valid_project_name("a_b"))` —— 实现已放宽，测试还钉旧结论。
不翻它的话，`cargo test --lib` 会红在「代码改了、测试钉旧结论」，而**集成测试根本测不到它**。

**硬规定**：守卫红时先问「是**实现**错了，还是**登记/计数**旧了」。
拿不准就**停下来问 BA**，⛔ 不要为了让灯变绿去删断言、抹名字、放宽判据。

### 补充（2026-10-27，QA 两轮踩坑）：共享 `CARGO_TARGET_DIR` 会串**测试二进制**，也会串**被测二进制**

| 面 | 现象 | 破解 |
| --- | --- | --- |
| 测试 exe | 副本变异后，cargo 复用**原仓**编译好的测试二进制（内嵌 `CARGO_MANIFEST_DIR`）⇒ 判据读未变异文件 ⇒ **假绿** | 副本 `Cargo.toml` 改版本号（强制独立构建单元）或换独立 target；自查：测试 exe 里搜 `CARGO_MANIFEST_DIR` |
| **被测二进制** | `debug/ontok-builder.exe` 是**同一个输出路径**；fingerprint 没变就不重写 ⇒ 你以为跑新二进制，实际跑的是**变异版** | 删 exe + `touch` 一个源文件再 build；并用**只有新提交才有的字符串**验明正身（例：新版 `--help` 里的一句话、日志段落顺序） |
| 反向还原 | 用备份覆盖变异文件后 **mtime 变旧** ⇒ cargo 认为没变、继续用变异版 | `touch` 后重编；或干脆每次换 target 目录 |
