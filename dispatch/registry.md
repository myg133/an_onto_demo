# 子 Agent 注册表（Dev / QA / Deploy）

> 与 `agent-registry.md` 区分：那份登记**在线的 BA session**，本表登记**可被派单的子 Agent**。

## 可用子 Agent

| 角色 | 类型 | 负责范围 | 工作区 | 状态 |
| --- | --- | --- | --- | --- |
| BA | root | 需求 / 架构 / 派单 / 状态跟踪 | `BA/` | online（见 agent-registry.md） |
| Dev | worker | 编码与自验证 | `feature-REQ-xxx/` | 按需创建 |
| QA | verifier | 测试用例生成 + 代码审核 | `feature-REQ-xxx/` → `code/` | 按需创建 |
| Explore | explore | 摸底：path:line + 风险点 + 建议 | 按需 | 按需创建 |
| Deploy | deploy | 部署配置 | `Deploy/` | 暂不启用（切片 1 无部署） |

## 派单规则

见 [`rules.md`](rules.md)。要点：

1. **派单前若对代码现状不熟，先派 explore** —— 派单成本 > explore 成本时必派
2. **1 worktree = 1 req** —— 绝不跨 req 复用
3. **Dev 不改 status.md，QA 不改 status.md** —— 状态仅 BA 更新
4. **绝不跳过 QA 直接 merge**

## 拆 briefing 的要求

派子 agent 时必须给**完整 self-contained 的 briefing**，包含：

- 需求编号与文档路径
- 相关设计文档的**具体小节**（不是「见设计文档」）
- 明确的任务边界（改什么 / 不改什么）
- 验收标准中对应的 AC 编号
- 禁止事项

> **不要泄父会话历史** —— 子 agent 看不到它，上下文必须自足。

## 派单教训（累积中）

| # | 教训 |
| --- | --- |
| 1 | **派 QA 生成测试用例应派 `worker` 而非 `verifier`。** Verifier 的职责是判定，撰写交付物会触发角色门禁 |
| 2 | **QA 子 agent 的产出（审计结论）本身很有价值**，即使它没完成被派的任务 —— 上一轮它抓出的 4 条缺陷全是真 bug |
| 3 | **Dev 编码本轮由 BA 直接代做，未派 Dev 子 agent** —— 流程第 8 步的偏差，已在 Sprint 回顾位记录 |
| 4 | **假命题测试只有在实现出错时才会暴露 —— 而作者写测试时实现是对的。** `test_hierarchy_descendants_exclude_self` 用「设备」（恰好无子节点）断言 `is_empty()`，无论 `descendants_of` 是否排除自身都通过；于是「环下把自己算成后代」这个真 bug 藏了三个 commit。**修法：断言必须选有判别力的输入**（取有后代的节点 + 断言不含自己） |
| 5 | **判定器本身也是代码，也要有测试 —— 而且要有「注入缺陷」测试。** 本轮累计 6 次误判，第 6 次最致命：`cargo test \| grep -qE FAILED` 在 `set -o pipefail` 下永远判假（grep -q 提前退出 → cargo 收 SIGPIPE → 管道非 0），**测试真的失败也报 ✓**。用「注入一个已知缺陷 → 判定器必须报 ✗」来验证，比人工读脚本可靠 |
| 6 | **判定器必须区分三态：通过 / 未通过 / 未实现。** 「文件不存在」是任务没开工，不是「写坏了」—— 混为一谈会让进度看起来像回归 |
| 7 | **单测测不出端到端的 bug。** Sprint 1 抓到 2 个：① `available` 集合混用展示名与系统 key（单测里两个命名空间恰好相同，所以绿）② 提案别名按正序解析到测试库历史老数据（单测不经过 CLI）。**端到端不是「再跑一遍」，它是唯一的检查手段** |
| 8 | **计划里的示例代码也要跑。** 计划给的 `OnceLock<PgPool>` + `get_or_init(async {...})` 编译不过（get_or_init 收同步闭包）；`SELECT 1` 用 `i64` 接会 ColumnDecode（PG 里是 INT4）。**TDD 文档里的「失败测试」示例本身可能就是错的** |
