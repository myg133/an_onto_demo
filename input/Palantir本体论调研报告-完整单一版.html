00摘要

本报告对 Palantir 的"本体论"（Ontology）进行系统性调研，覆盖其官方定义、技术架构、AI 时代定位、商业验证、交付机制与批判性视角，并在此基础上提炼出一套可用于构建 FDE（Forward Deployed Engineer，前置部署工程师）服务的方法论底座。核心结论有六条。

第一，Palantir 本体论不是数据库、不是语义层、也不是传统知识图谱，而是一个"决策为中心"的企业运营模型：官方文档将每一个运营决策拆解为数据、逻辑、行动、安全四个成分，并把对象、属性、链接（名词）与动作、函数、动态安全（动词）建模在同一个层里（Palantir 官方文档）。第二，本体论的技术本质是把"企业的名词与动词"显式化为可治理的软件资产——对象类型、链接类型、动作类型、函数、接口、共享属性六类资源，加上双层权限模型与决策血缘，构成一个可被人和 AI 智能体共同操作的数字孪生（Palantir 官方文档）。

第三，AIP 的爆发让本体论从"数据整合层"升级为"LLM 的世界模型与工具目录"：大模型通过数据工具、逻辑工具、动作工具三类接口在受治理的本体上推理和行动，这是 Palantir 把 LLM 从"聊天界面"变成"运营代理"的关键设计（Federal DS Handbook）。第四，商业上这一模式已被验证：2026 年 Q2 营收 19.35 亿美元、同比增长 93%，美国商业收入增长 149%，Rule of 40 得分 155%，AIP Bootcamp 把以年计的销售周期压缩到数天（Futurum、SEC 文件）。

第五，本体论与 FDE 是一体两面：本体是 FDE 交付的核心工程对象，FDE 是本体得以在客户现场落地的组织机制——Day 0-1 建模、Day 2 接入 AIP、Day 3 交付可运行的工作流，之后持续迭代（GetPerspective）。第六，对自建 FDE 服务而言，最重要的方法论迁移是：以"决策清单"而非"数据清单"驱动建模、以"名词-动词-权限"三件套结构化需求、以"动作分级自治"管理 AI 放权、以本体资产复用支撑产品化与定价。

01本体论的定位：Palantir 到底在卖什么

1.1官方定义的三重表述

要理解 Palantir 的本体论，最可靠的入口是它自己的三份文本，三者措辞并不完全一致，恰好暴露了这套概念的演进轨迹。

第一份是 2025 财年 10-K 年报的定义："本体论一般指将数据系统性地映射到有意义的上下文"（Ontology generally refers to the systematic mapping of data to meaningful context），而 Palantir 的版本"远超传统概念"，因为它把一个决策背后的数据、逻辑与行动折叠进了对组织的同一个表示之中（DVDMaru 对 10-K 与官方文档的逐句考据）。这份定义面向投资者，强调的是"超越数据映射"。

第二份是 Foundry 官方文档"Why create an Ontology"页面，这是最完整的产品化表述：本体论是"组织的运营层"（operational layer for the organization），位于被集成进平台的数据集、虚拟表与模型之上，把它们连接到现实世界中的对应物——货件、患者、交易、飞机；它"表示的是企业中的决策，而不仅仅是数据"（Palantir 官方文档）。同一页面明确把每个运营决策建模为四个成分：数据（做决策所用的信息）、逻辑（评估决策的启发式与计算过程）、行动（被选定决策的编排与执行）、安全（决策符合运营政策的保证），并自动捕获端到端的"决策血缘"——一个决策何时作出、基于哪个版本的企业数据、通过哪个应用作出，对人类开发者和 AI 智能体都可安全访问（Palantir 官方文档）。

第三份是 CEO Alex Karp 在 2026 年 5 月 4 日股东信中的哲学化表述："本体论牢牢扎根于现实——在这里，存在一种地面实况（ground truth）、部落知识（tribal knowledge）与增强（enhancements）之间的辩证法"（DVDMaru）。这句话对 FDE 服务尤其重要：它承认企业的"现实"不是一个静止的数据库快照，而是地面数据、员工头脑中的隐性知识与系统增强三者持续相互修正的过程——本体论工程的实质，就是把这三者的辩证法固化为软件。

值得注意的是，Palantir 自己的文档体系内部也存在口径漂移：2022 年 10 月的博客列了六个必备服务，2024 年 1 月首席架构师 Akshay Krishnaswamy 的博客用"数据、逻辑、行动"三件套，2026 年的文档才固定为四件套；本体概览页又用"语义元素 vs 动能元素"的二分法（DVDMaru）。这说明"本体论"对 Palantir 不是一个有严格形式化定义的标准，而是一个持续演化的产品哲学——调研应取其稳定的结构性内核，而非某一句话。

1.2三个"不是"：划清概念边界

不是数据库。本体论不存储原始数据的权威副本，而是坐在既有数据集、虚拟表与模型之上的运营层；它服务的是决策而非查询。官方 FAQ 明确说"本体论不是数据库……它把数据、逻辑、可执行动作与权限规则绑在一起。它服务决策，而非查询"（DVDMaru）。当然，从工程实现看，数据确实会被索引进 Palantir 自己的对象数据库（Object Storage V2），而非虚拟化直连源系统——这一点第六章批判性部分会展开（Elementum）。

不是语义层。官方架构文档直接写道："本体论不是一个'语义层'；数据、逻辑、行动与安全的四重整合与操作化，不是一个薄语义层或一个单体设计能完成的。"对比 dbt、Looker、Databricks、Snowflake、Microsoft Fabric 五家的语义层定义，全部只谈指标与语义模型的统一定义，没有一家提到"把动作写回任何东西"（DVDMaru）。中国数据社区对此有一致观察：传统中台是"后视镜"，只能看过去；Palantir 是"导航仪"，告诉你该做什么——传统中台告诉你"库存不够了"，本体论直接帮你把采购单下了（腾讯云开发者社区、新浪财经）。

不是学术意义的知识图谱/本体。它不使用 RDF/OWL/SPARQL 这一整套 W3C 语义网技术栈，没有形式化推理机，其"本体"二字借自哲学与知识工程，但实现是完全务实的产品工程。有研究者的概括很精到：学术本体（RDF/OWL）的主目的是"严格描述世界的结构"，Palantir 本体的主目的是"描述世界结构的同时让它动起来"（omen-kai）。Databricks 内部开源项目 OntoBricks 在竞品分析中把"无 W3C 标准（OWL/RDF）、私有平台、昂贵许可、锁定"列为 Palantir 的明确短板（GitHub/databrickslabs）。

1.3概念谱系：从哲学本体到运营本体

把 Palantir 本体论放进知识表示的六十年脉络里看，它的创新不在于发明了"本体"，而在于把本体从"知识的静态描述"改造为"运营的可执行模型"。哲学中的 Ontology 讨论"存在的本质"；1993 年 Tom Gruber 给出 AI 领域的经典定义——"本体是对概念化的显式规约"；1997-2009 年语义网运动建立了 RDF、RDFS、OWL、SPARQL 的完整技术栈；2010 年代，IBM Watson 医疗的失败、Google 转向轻量的 Knowledge Graph 并弃用 SPARQL，暴露了"学术上的逻辑正确性"与"工业上的实时操作能力"之间的根本矛盾；2021 年之后，Palantir 把 Ontology 重新定义为"组织的运营层"，开启了所谓"运营本体"时代（UML 中文社区综述、Pebblous）。

学术界也注意到了这一转折。新南威尔士大学的研究把 Foundry 称为"开箱即用的数字孪生作为企业操作系统"，指出 Palantir 把数字孪生从工厂、仓库、港口等物理环境扩展到了构成企业的"更抽象、信息化、分布式的系统"（UNSW 研究论文）。从公司史看，本体论不是为商业市场发明的新故事，而是从情报场景长出来的：2003 年成立后，CIA 在 2005-2008 年是 Palantir 唯一的客户，工程师与情报分析师在同一场景里迭代出 Gotham；Gotham 早期就用"对象与关系"组织情报数据，后来这些能力被逐步抽象、扩展为今天公开的 Ontology 与开发工具链（The AI Opportunities、CSDN 技术链路分析）。这段历史对方法论有直接影响：本体论天生是为"人在高压运营现场做决策"设计的，而不是为"数据分析部门出报表"设计的。

02技术架构拆解：决策四要素与"名词-动词"体系

2.1决策为中心：Data / Logic / Action / Security + 决策血缘

Palantir 架构的第一性原理是：企业软件的原子单位不是数据记录，而是决策。官方 why-ontology 页面把这一框架展开为四个成分（Palantir 官方文档）：

成分官方定义在本体中的载体对 FDE 方法论的含义
数据 Data做决策所用的信息，含决策过程自身产生的"决策数据"（上下文、评估过的选项、后果）对象、属性、链接；实时同步 ERP/MES/WMS、IoT、边缘、文档、地理空间数据需求调研要问"这个决策需要什么信息"，而不是"你有哪些表"
逻辑 Logic评估决策的启发式与计算过程：规则、约束、预测模型、优化与仿真Functions（TS/Python 代码）、模型绑定、规则引擎；确定性函数与非确定性 LLM 推理互补隐性业务规则（tribal knowledge）必须被显式化、代码化、版本化
行动 Action被选定决策的编排与执行动作类型（Action Type）：单事务编辑集 + 副作用（webhook、通知、写回）交付物以"可执行动作"闭环，而非以"看板上线"告终
安全 Security决策符合运营政策的保证标记/目的/角色三维策略、行列级限制、运行时计算的动态权限权限设计前置到建模阶段，而非上线前补做

贯穿四者的是第五条暗线——决策血缘（decision lineage）：一个决策何时、基于哪个版本的数据、通过哪个应用作出，被自动记录，对人和 Agent 都可审计（Palantir 官方文档）。这套设计的深层意图是"决策复利"：每次决策的上下文、选项与结果回流为本体的新数据，成为下一次决策（以及 AI 学习）的输入——传统企业里决策过程是消散在会议、邮件和人脑里的"尾气"，本体论把它回收为资产（Anblicks）。

2.2语义元素（名词）：对象、属性、链接、接口、共享属性

本体概览文档把资源分为六类，其中"名词"部分构成语义元素（Palantir 官方文档、类型参考）：

  • 对象类型（Object Type）：现实世界实体或事件的模式定义——飞机、供应商、订单、患者、合同、机器、工单。对象不是数据库表，而是运营世界中的实体；每个对象类型有主键、属性集合与行为配置，可由用户编辑，并可与外部系统集成。
  • 属性（Property）：实体的特征，带类型化取值；属性系统支持基类型、聚合归约器、派生属性、仅可编辑属性、必填约束、条件格式化，以及带主字段的复合结构体（structs）。
  • 共享属性（Shared Property）：可跨对象类型复用的属性定义，保证一致建模与集中元数据管理——这是大型本体避免口径漂移的关键机制。
  • 链接类型（Link Type）：两个对象类型之间有方向、有语义的关系，支持一对一、一对多、多对多。
  • 接口（Interface）：对对象类型"形状与能力"的抽象描述，提供多态建模（如"可定位 Locatable"接口约束任何有经纬度的对象），支持多级继承与编程化引用。
  • 对象类型组（Object Type Group）：组织容器，用于本体的搜索与探索分类。

这套词汇表的设计哲学是"收敛名词与动词"：传统模式把对象（Customer）与动作（Purchase）分开建模，Palantir 让同一张图同时捕获状态与行为（UBOS）。建模工具是 Ontology Manager；也存在代码化路径——OSDK 的 Maker 包提供类型安全的编程式本体定义，2025 年底社区已有"Ontology as Code"的 Beta 讨论（GitHub/palantir/osdk-ts）。

2.3动能元素（动词）：Action Type、Functions 与动态安全

如果语义元素回答"世界是什么"，动能元素回答"世界能被怎样改变"。这是 Palantir 本体与一般数据建模的决定性差异（E7Coding 架构解读）。

动作类型（Action Type）的官方定义是"一组对对象、属性值与链接的变更/编辑的定义，用户可一次性执行——一个单事务"。其架构组件包括（Palantir 官方文档）：参数（用户输入、带过滤的下拉、默认值）；两种执行模型——规则式（声明式状态迁移）与函数支撑式（调用已部署的 TS/Python 函数，支持批量执行，单次动作默认上限 1 万个对象）；提交判据（提交前的条件校验、授权检查、一致性强制）；副作用（通知、webhook、调度触发、级联编辑）；以及可观测与治理（执行日志、撤销/回滚、编辑历史追踪）。动作可从 Object Explorer、Object Views、Workshop 应用、接口以及外部系统 API 调用——它是本体对外的"写接口"。

函数（Functions）是代码化的本体逻辑，用 TypeScript v1/v2 或 Python 编写，可绑定到本体类型并版本化发布，被嵌入动作、Workshop 应用与 AIP Logic 流中（PuppyGraph）。官方称之为"逻辑绑定（logic binding）范式"：为构建工作流提供一致接口，把分布在本地机房、企业云、SaaS 与 Palantir 平台自身的异构逻辑资产组合进同一个人机共用的决策上下文（Palantir 官方文档）。

动态安全（Dynamic Security）被官方明确列为本体的动能元素而非外挂功能：标记（marking）、目的（purpose）、角色（role）三类策略组合，加行列级限制，在每次交互时运行时计算；工具调用被同一安全架构强制约束，任何工具调用都依赖于对底层对象、属性、链接的访问权；Agent 产生的遥测日志的访问同样被数据标记治理（Palantir 官方文档）。

2.4底座工程：OSv2、Object Data Funnel 与双层权限

本体之下是一套为"运营读写混合负载"设计的存储查询底座（Palantir 官方文档/对象后端）：

  • Object Storage V2：当前代对象数据库，索引与查询解耦、水平扩展，单对象类型支持至多 2,000 个属性、数百亿对象，默认增量索引；前代 V1（Phonograph）已于 2026 年 6 月 30 日停止服务。
  • Object Data Funnel：编排服务，负责从数据源摄入索引，处理动作驱动的用户编辑，与上游变更保持同步，支持低延迟流式。这意味着本体是对数据的索引副本工作，而非就地虚拟化查询——这是架构上的主动取舍，也是被竞品攻击的主要靶点（Elementum）。
  • Object Set Service（OSS）：读取服务，支持过滤/搜索、聚合、对象加载；对象集分静态、动态、临时（24 小时过期）、永久四类；Search Around 默认上限 10 万对象。
  • Ontology Metadata Service（OMS）：模式定义层，管对象类型、链接类型、动作类型规范与实体元数据。
  • 多数据源对象（MDO）：把多个数据源合成复合对象，支持属性级权限粒度与列级访问控制。

权限是双层授权模型：第一层是本体资源（模式），第二层是对象与链接（数据），数据层通过受限视图（Restricted Views）支撑行列级控制，加对象安全策略做基于策略的强制（Palantir 官方文档/对象权限）。本体自身有完整开发生命周期：分支（版本化 + 提案-评审工作流）、变更持久化、跨本体迁移、版本管理；访问组织上区分私有本体（单组织）与共享本体（多组织池 + 安全隔离）（Palantir 官方文档）。

2.5消费层与开放接口：Workshop、OSDK 与 MCP

本体之上是应用消费层：低代码应用构建器 Workshop、分析工具 Contour 与 Quiver、图可视化与仿真工具 Vertex（支持场景/what-if 推演、时序与媒体标注、动作调用）、对象检索工具 Object Explorer（TechnologyBlog）。

对开发者与外部生态，Palantir 提供两层接口。OSDK（Ontology SDK）把本体类型生成为类型安全的 SDK，供自建前端与外部系统调用，官方叙事称其为"把软件开发锚定在企业的运营真相上"（Microsoft Marketplace/AIP）。MCP 接口分两个面向：Palantir MCP 面向"建设者"——提供 70+ 工具让 AI IDE/Agent 自主设计、构建、编辑、评审端到端应用（可修改本体类型，但不能写本体数据）；Ontology MCP（OMCP，2025 年 7 月推出）面向"消费者"——把对象类型、动作类型、查询函数暴露为 MCP 工具，让外部 AI 系统安全地读写本体数据，并通过应用级限制约束 Agent 可执行的动作集合（Palantir 官方文档/MCP、Palantir 官方文档/OMCP）。这个"建设者/消费者"二分本身就是方法论信号：本体的建设治理与消费授权是两类不同问题，要用两套接口与权限分开管理。

03AI 时代的本体论：从数据平台到智能体操作系统

3.1本体作为 LLM 的世界模型与工具目录

AIP（Artificial Intelligence Platform，2023 年 4 月发布）的本质是把 LLM 接入本体。当整个行业的主流做法是把概率模型指向向量数据库做 RAG 时——结果是语义上似是而非、结构上无根、幻觉率不可接受——Palantir 选择把 LLM 嵌入一个双向知识图谱，让 AI 通过一个原生理解关系、逻辑与运营约束的受治理语义层与企业交互："优先世界模型而非语言模型（prioritizing the world model over the language model），把 LLM 从易变的查询接口变成受治理的运营代理"（Towards AI）。

工程上，这通过给 LLM 三类工具实现（Federal DS Handbook）：数据工具（读本体：查询对象、属性、链接）、逻辑工具（执行 Foundry Functions 中的确定性业务逻辑）、动作工具（写回本体：安全地触发动作）。关键约束是：AIP Logic 函数不能执行任意写操作，只能调用本体中已被显式定义并批准的动作——"这就是'什么都能做的 LLM'与'只能做你的组织已批准之事的 LLM'之间的区别"。由此形成的产品栈包括 AIP Logic（用 Use LLM Block 搭建 LLM 函数）、Agent Studio（有记忆、多轮、可多步规划的会话智能体）、AIP Evals（评估体系）、AIP Machinery（2025 年 2 月推出的人机协同工作流产品：定义哪些步骤需要人工批准，置信阈值随模型在特定决策类型上的表现动态调整）。

3.2人在回路与动作分级：默认不放权

Palantir 对 AI 自主性的官方姿态是渐进放权。官方文档的示例（虚构制造商 Onyx）写明：授予一组 AI 智能体访问有限动作集合的权限，"默认情况下，这些动作（如改变工单状态或推送再分配计划）只能被 AI 预演（staged），然后交给人做最终评审"；只有当可信、经过良好测试的流程赢得信心之后，才可能让其中一些动作脱离人类闭环（Palantir 官方文档、DVDMaru）。在军事场景（Gotham + AIP + Apollo），LLM 在架构上被禁止触达动能行动，每条建议都需要人工确认（Towards AI）。这套"默认预演、证据放权"的节奏被实施伙伴进一步工艺化为可复用的交付纪律，见 5.3 节（BD Emerson）。

3.3模型无关与"商品化认知"叙事

Palantir 刻意把 AIP 做成模型无关（model-agnostic）：同一环境可配置 GPT、Claude 等多个模型，按能力、成本或政策要求为不同 Logic 块或 Agent 选择不同模型；换模型不需要重写 AIP Logic 或 Agent，因为本体接地与工具层在模型变更下保持恒定（Federal DS Handbook）。这套架构与 Karp 的"商品化认知"（commodity cognition）叙事互为表里：当大模型能力趋于商品化，稀缺资产从"模型"转移到"模型作用的运营上下文"——也就是本体（SEC：Palantir Q4 2025 财报）。2026 年 Q2，Karp 把这套叙事升级为"AI 主权"（AI sovereignty）：企业要拥有自己的模型、数据与决策，而不是把它们喂给第三方基础模型（Futurum）。

对方法论的意义：模型是插件，本体是底盘（The LLM is a component; the Ontology is the chassis）（TheByteDive）。2026 年 6 月 Palantir 还与英伟达合作推出面向物理隔离环境的"主权 AI 操作系统"，把同一架构推向涉密与主权场景（Wall Street Times）。

3.4非结构化数据与检索的融入

本体的对象世界并不限于结构化数据。官方文档处理管线支持：媒体/文档→文本抽取→带重叠的分块（chunking）→展开→嵌入→生成与源对象链接的 Chunk 对象→语义检索；结合多模态与嵌入模型集成，形成"本体增强生成"（ontology-augmented generation）的检索路径（Palantir 官方文档）。也就是说，RAG 在 Palantir 体系里不是独立于本体的旁路，而是被收编为本体上的一类对象与链接——文档块链回业务对象，使非结构化知识同样进入权限与血缘体系。

被各家反复引用的洞察是：没有客户特定本体的 LLM 应用注定失败——通用模型给通用答案，企业价值要求接地到客户的名词与动词，而那是工程，不是提示词（GetPerspective）。配套的战术原则包括：从一个前五名的业务结果倒推；≤10 天做出依赖真实数据的活 demo（"demo as spec"），用它暴露接缝、统一各方对"就是这个东西"的认知；先修"碎石路"（最小可用路径），再把暴露出的可复用原语铺成平台（Per Aspera FDE playbook）。

5.3本体建设的工艺规程

官方与实施伙伴的实践可以合成一条七步工艺（PuppyGraph、Palantir 官方文档）：①数据入 Foundry（连接源、建管道、注册数据集/虚拟表/模型作为对象类型的基底）→ ②创建对象类型（主键、属性、显示配置）→ ③声明链接类型 → ④配置动作类型（可做的编辑、校验逻辑、副作用）→ ⑤编写函数（TS/Python 服务端逻辑）→ ⑥在需要多态处引入接口 → ⑦施加安全（角色 + 敏感属性的对象安全策略）。

实施伙伴 BD Emerson 把 AI 落地的节奏进一步细化为七条纪律（BD Emerson）：选一个工作流而不是选一个模型；先接地再生成（本体、权限、检索先行）；用证据门控自治（每个 Agent 从被监督开始，自治范围随评估与生产历史逐动作类型扩大）；把模式工业化（模板化交付）；每次调用留证（提示词、检索上下文、执行动作、审批全量日志）；先只读（写动作逐个在审批步骤后开启）；尽早映射到治理框架（如 ISO 42001 / NIST AI RMF）。

"如果你在为一个本体划范围，从'你希望操作员下个季度做出什么不同的决策'开始，倒推回这个决策需要的对象、链接与动作。"（BD Emerson）

5.4五大失败模式

同样来自一线实施方的失败清单（全部为组织与建模问题，没有一条是纯技术问题）（BD Emerson）：

  1. 按源系统而非按业务建模——对象类型以表命名，模型出了数据团队没人认识；
  2. 从企业级大模型开始而非一两条工作流——首个应用必然延期，且建在没有操作员验证过的对象上；
  3. 把本体当数据仓库——因为"可能有用"而加载每个系统的每个属性，为索引和混乱双重付费；
  4. 交付没有动作类型的应用——造出昂贵的仪表盘，把写回问题留给永远不会被资助的"二期"；
  5. 未解决的身份问题——两个源系统对"什么是客户"意见不一，本体把分歧继承为重复对象。

第三方观察还补充了组织维度的告诫：本体建模者需要"有权裁定定义争议的人，而不仅是有技术能力实现的人。难的部分是决定'一个账户是什么'；把答案编码进去相对容易"；以及"不要从建本体开始——先建一条真实工作流需要的对象，跑起来，再据所学扩展。从运转中的软件向外长出的模型能保持诚实，白板上画出来的则不能"（UbiGrowth）。

06批判性审视：护城河与代价

6.1技术批判

锁定是第一性问题。本体活在 Foundry 内部：不采用 Foundry 就无法采用本体，也无法把本体模型导出到别处运行；Databricks 的开源项目把"私有平台、昂贵许可、无 W3C 标准、锁定"明确列为 Palantir 方案的短板（PuppyGraph、GitHub/databrickslabs）。数据必须被集成而非被引用——本体不就地查询运营库或湖仓，数据经管道流入、由 Funnel 索引进对象数据库，多出一个集成步骤与新鲜度问题（Elementum）。此外还包括：不支持跨本体链接（对联邦式多业务单元建模是硬伤）、与 Foundry 管道强耦合（上游变更会级联进本体行为）、无形式化推理引擎（没有 OWL 式描述逻辑推理，所有"智能"来自函数与 LLM，而非逻辑演绎）（PuppyGraph、Towards AI）。成本与实施复杂度同样有据可查：高集成复杂度与长实施周期、高总拥有成本，对中小企业构成门槛（Goover/Saltlux 对比报告）。

6.2治理批判

NHS FDP 案例集中暴露了治理维度的风险：3.3 亿英镑合同签下后，公众与医学界信任缺失、效益证据不足被议会点名；分析师反映代码只兼容 Foundry、算法黑盒无法审计；历史上 NYPD 合同终止时的分析成果迁移争议也被重新翻出（Medact 简报）。对任何以"本体+AI"为叙事的服务商，这是必须预置答案的问题域：数据主权、算法可审计性、成果可迁移性、退出条款。有评论者把 Mercury Systems 案例中"Palantir 将帮助 Mercury 建设作为公司运营数字孪生的企业本体"这句话挑出来追问——这份本体到底属于谁？谁在建模一家上市公司实际如何运转，又代表谁？（csidia）这个问题对 FDE 服务商与客户同样尖锐。

6.3中国语境：中台、语义层与本体论之争

中国数据产业对 Palantir 本体论有一场高质量的概念辩论。Aloudata CEO 周卫林的观点代表"语义层务实派"：本体论与语义层"本质是一个东西，都是统一语义，最终目标都是决策和行动。区别在于场景：Palantir 侧重运营决策，我们侧重管理决策……中国市场环境下，依托已有中台基础设施，更容易落地"（爱分析访谈）。Aloudata 的技术分析进一步区分了两者的驱动模型：本体论要对每个业务事件做自动化决策、尽量避免人介入，是 Event-Driven，要求毫秒/亚秒级响应、日执行量亿级起步；语义层多由人或 Agent 按需发起，是 Demand-Driven，秒级响应、日查询量百万级——两者在响应时长与计算量级上差一个数量级以上（Aloudata）。

本体论落地的组织门槛也被点破："本体论的落地需要涉及多个业务系统之间的业务流打通，这种跨部门、跨厂商的协同，往往是企业一号位才能真正推动执行，这也是 Palantir 商务上选择 CXO 人群从上往下找'流血场景'打的原因"（博客园/Aloudata）。对已有数据中台的企业，务实的集成路线是分层归属：原始层与汇总层留在中台（中台是口径权威），语义层（对象图谱）与决策层（Agent）由本体体系新建，治理层双方共建（腾讯云开发者社区）。

07方法论底座：从 Palantir 本体论提炼 FDE 服务方法论

7.1概念底座：用"决策四要素"重构需求分析

传统需求调研问"你要什么功能/报表"，本体驱动的需求调研问四组问题，直接对应决策四要素（Palantir 官方文档）：

这套问法把 FDE 的"价值翻译"从软性沟通能力变成结构化工艺。Karp 的"地面实况、部落知识与增强的辩证法"提示了一个关键工作方法：本体建模不是把数据库翻译成对象，而是三方对账——系统数据（地面实况）经常与业务实际（部落知识）冲突，FDE 的工作就是主持这场对账并把裁决结果编码进本体。这也解释了为什么本体 owner 必须是"有权裁定定义争议的人"（UbiGrowth）。

7.4组织底座：双人组、反馈飞轮与反 SI 化

最小作战单元是双人组：Echo 型角色（发掘真问题、定义价值、经营关系、主持定义争议裁定）+ Delta 型角色（管道、本体、应用、Agent 的建造者）；规模化后演化为 Partner（需求与优先级）/Delta（建造）/Echo（可持续与采用度）三人结构，以交付速度、缺陷返工率、可复用组件贡献为考核（AI Native、Talent.com/Acrisure JD）。

反馈飞轮是组织级机制：FDE 是产品团队的第一输入通道——客户现场的洞见、边缘案例失败、复用原语回流总部，塑造平台路线图；这正是 Anthropic、OpenAI、Databricks 抄走的组织设计（GetPerspective）。拒绝 SI 化是商业模式的护城河：Palantir 拒绝"更好的埃森哲"式合同，坚持客户拥有应用而非购买人头工时；对自建 FDE 服务的中国团队，这对应一个清醒的选择——按"本体资产 + 动作能力 + 价值分成"计价，而不是按人月计价。

7.5商业化底座：Bootcamp 节奏与价值证明

Bootcamp 的本质是把 P0-P3 压缩成一次 1-5 天的封闭式价值证明：客户带真实数据来，FDE 现场建模、接地、跑通一条决策工作流。Palantir 的数据证明其效率——2024 年底累计超千场，转化率达 75-85%，两个月内出现七位数 ACV（GetPerspective、Octagon AI）。对中国市场的适配要点：入口找 CXO 与"流血场景"（跨系统业务流打通只有一号位推得动），用"下周能不能跑起来"替代"未来可以怎样"的叙事（博客园/Aloudata、36氪）。

定价锚点随之清晰：Bootcamp（低门槛获客）→ 首条工作流项目制（本体 + 动作库初建）→ 平台订阅 + 持续 FDE 服务（动作能力扩展、自治分级提升）→ 价值分成（按被量化证明的决策改进分成）。每一级都以本体资产的增量为计价单位。

08结论与行动建议

Palantir 本体论的真正创新，是把企业软件的原子单位从"数据记录"换成"决策"，并为决策配备了完整的工程体系：名词（对象/属性/链接）描述世界，动词（动作/函数/动态安全）改变世界，权限与血缘让世界可被安全地改变且可追溯，LLM 则通过工具化接口在同一模型上与人协同。这套体系与 FDE 交付机制互为表里——本体是 FDE 的工程对象，FDE 是本体的落地组织。

对构建自有 FDE 服务方法论的团队，建议的落地顺序是：

  1. 第 1-2 周：概念对齐。团队内部统一"决策四要素 + 名词动词"语言，用五大失败模式做反面教材培训；
  2. 第 3-4 周：选赛道做样板。挑一个供应链/调度/运营类高频决策场景，按 P0-P3 流程做出第一个"本体 + 动作库 + 可运行应用"样板，全程记录工时与卡点；
  3. 第 2 个月：产品化交付物。把样板中的六类资产模板化，形成 Bootcamp 式价值证明包与"能力清单"报价单；
  4. 第 3 个月：建立放权与治理规程。动作分级自治标准、决策血缘审计方案、本体资产归属与退出条款（直面 NHS 式质疑）；
  5. 持续：飞轮与复用。每个项目强制沉淀可复用对象/动作/函数入库，用"复用资产贡献率"考核 FDE 团队，把服务毛利建立在资产复用而非人力堆叠上。

最后一则提醒：本体论不是万能药。它适合"高频、高价值、跨系统、需闭环"的运营决策场景；对纯分析型、管理报表型需求，语义层路线更轻更快（爱分析）。FDE 服务商的专业性恰恰体现在进场前就能判断客户属于哪种场景——这本身就是方法论底座的第一块基石。

09终审：本体论是商业包装、故弄玄虚吗？

这是写完整份报告后必须正面回答的问题。我的方法是把"言过其实"这个模糊指控拆成四个可独立检验的命题——概念是否原创？技术是否真实？价值是否成立？命名是否诚实？——逐条裁决，再给出总判词。先亮结论：七分实，三分名；工程为真，拔高为真，两者并不矛盾。

9.1命题一：概念是否原创？——裁决：不新，是集成创新

拆开看，本体论的每一层都有现成的对应物：对象/属性/链接 ≈ 知识图谱与对象关系建模；动作类型 ≈ BPM/工作流引擎与业务规则引擎的写操作；函数 ≈ 服务端业务逻辑；行列级权限 ≈ 数据治理标配；"数字孪生" ≈ 工业界旧词。学术标准下它甚至不配叫本体——Gruber 定义要求"概念化的显式规约"，RDF/OWL 体系要求形式化语义与推理机，Palantir 两者皆无，Databricks 的竞品分析直言其不采用任何 W3C 标准（GitHub/databrickslabs、omen-kai）。如果一家公司说"我们做了知识图谱+工作流+权限+数据集成"，没人会觉得性感；"本体论"这个词完成了从"工程拼装"到"哲学高度"的跃迁。

但"部件不新"不能推出"系统不新"。iPhone 没有发明任何部件。判断标准应该是组合是否产生了此前不存在的系统属性——本体论的系统属性是决策闭环：读写一体、血缘可追溯、人机共治、权限内生。这个属性在 BI、语义层、数据中台的世界里确实普遍缺失：五家主流语义层厂商的定义里没有一家提到"把动作写回"（DVDMaru）。裁决：词汇是借来的，系统属性是真的。

9.2命题二：技术是真是假？——裁决：真，但有被话术淡化的代价

真实性有硬证据：文档级的工程承诺（OSv2 数百亿对象、单类型 2,000 属性、动作的单事务语义、OMCP 接口规范）造假成本极高；独立实施伙伴基于真实交付总结出的五大失败模式（5.4 节），只有被高强度真实使用过的系统才沉淀得出来；竞品公司（Databricks）专门立项仿制，是另一种形式的承认（GitHub/databrickslabs）。

但官方话术确实系统性地淡化了三件事：数据必须复制进 Palantir 的存储（所谓"operational layer"之下是实打实的索引副本，新鲜度与一致性由平台口径单方面定义）；没有跨本体链接、没有形式化推理（联邦式建模与逻辑演绎都不支持）；本体模型不可导出——你的"企业数字孪生"寄生在 Foundry 里（PuppyGraph、Elementum）。裁决：技术为真，但这些不是"言过其实"，是被精心措辞隐藏的架构取舍——读 Palantir 的文档要像读招股说明书一样读风险章节。

9.3命题三：价值是否成立？——裁决：商业证据强到难以伪造，但要打三重折扣

支持"实"的证据是硬指标：连续 12 个季度营收增速环比加速（+39%→+93%）、NDR 150%、Rule of 40 达 155%、Bootcamp 75-85% 转化率、BP 十年 12 亿美元续约（SEC、Futurum）。营销可以包装故事，但包装不了净收入留存率和经营现金流——客户在用真金白银续费。

但必须打三重折扣。折扣一：幸存者偏差——宣传页上是 Airbus 和 BP，NHS 式的僵局（3.3 亿英镑合同被议会要求中断）不会出现（Medact 简报）。折扣二：归因杠杆——财务高增长由本体论、FDE 组织、Bootcamp 销售法、AI 行业周期、国防开支顺风多因素共同驱动，把功劳记给"本体论"单一因素是 Palantir 自己的叙事策略。折扣三：叙事溢价——66 倍市销率的估值里，"本体论"作为一个难以证伪的好故事贡献了可观的想象成分（StockOracle）。在资本市场层面，它确实是包装——而且是非常成功的包装。裁决：客户价值为真，因果叙事被夸大，估值故事含大量水分。

9.4命题四：命名是否诚实？——裁决：刻意的语义拔高，而且这招值得学

"Ontology"在哲学与知识工程里有严格含义，Palantir 借用了它的庄严感、放弃了它的严格性。更说明问题的是定义自身的漂移：2022 年六服务、2024 年三件套、2026 年四要素（DVDMaru）——一个被持续打磨的营销概念，而不是一个被发现的客观真理。同样的操作还有"商品化认知""AI 主权"：Karp 深谙一个词如何重述一门生意。

但命名的力量是真实的："本体论"把对话从"数据集成项目"（IT 采购层级，拼价格）重述为"企业认识论工程"（CXO 层级，拼愿景），直接改变了议价结构、销售路径和人才叙事——这门手艺本身就是 FDE 服务商最该抄的作业：你的方法论需要一个配得上野心的名字。同时它也是反面教材：名字与兑现之间的差距，就是信任破产的地方——NHS 的麻烦一半来自交付，一半来自叙事跑得比交付快。

PROV-O：溯源本体

W3C Provenance Ontology · Recommendation 2013

它是什么。PROV 是 W3C 在 2013 年发布的一族标准，专门回答一个问题：「这个东西从哪来、谁经手过、经历了哪些步骤」。这族标准包括概念数据模型 PROV-DM、用 OWL 2 表达的本体 PROV-O、人类可读的 PROV-N 记号，以及 XML / JSON 映射。其中 PROV-O 是机器可推理的形态——数据世界的「族谱学」规范。

标准地位
W3C Recommendation，2013-04-30
回答的问题
从哪来（derivation）· 谁负责（attribution）· 经由什么活动（activity）
核心三要素
Entity 实体 · Activity 活动 · Agent 代理
序列化
Turtle / RDF-XML / JSON-LD / PROV-N / PROV-XML
Semantica 角色
每条事实与决策自动挂 PROV-O 溯源，可导出 Turtle / JSON-LD 直交监管方

Core三要素与七种核心关系

PROV 的世界观极简：世界里只有物（Entity：一份数据、一份合同、一个决策）、事（Activity：一次抽取、一次审批、一次模型调用）和负责者（Agent：一个人、一个系统、一个组织）。所有的溯源陈述，都是这三者之间七种基本关系的组合：

PROV-O 核心关系速查
关系方向读法
prov:wasGeneratedByEntity → Activity「这份物」由「这件事」产生
prov:usedActivity → Entity「这件事」使用了「这份物」
prov:wasDerivedFromEntity → Entity「这份物」派生自「那份物」（如报告派生自原始数据）
prov:wasAttributedToEntity → Agent「这份物」归因于「这个责任者」
prov:wasAssociatedWithActivity → Agent「这件事」与「这个责任者」相关联
prov:actedOnBehalfOfAgent → Agent「这个代理」代表「那个主体」行事（AI Agent 代人决策的关键）
prov:wasInformedByActivity → Activity「这件事」承接自「那件事」（活动之间的接力）

Example最小例子：一次「云厂商选型」决策的溯源

Turtle · PROV-O 
@prefix prov: <http://www.w3.org/ns/prov#> .
@prefix ex:   <http://msp.example.com/> .

ex:decision_042        a prov:Entity , ex:Decision ;
    prov:wasGeneratedBy   ex:act_vendor_review ;      # 决策由评审活动产生
    prov:wasDerivedFrom   ex:cost_report_q2 ,         # 依据：Q2 成本报告
                          ex:latency_benchmark ;
    prov:wasAttributedTo  ex:agent_fde_alice .        # 责任人：FDE Alice

ex:act_vendor_review   a prov:Activity ;
    prov:used             ex:cost_report_q2 ;         # 评审使用了成本报告
    prov:wasAssociatedWith ex:agent_fde_alice ;
    prov:startedAtTime    "2026-08-14T09:30:00"^^xsd:dateTime .

ex:agent_fde_alice     a prov:Agent ;
    prov:actedOnBehalfOf  ex:org_client_acme .        # Alice 代表客户行事

Limits长处与边界

长处：它是中立的出口格式——监管方、审计方、下游系统都能用同一套词汇消费你的溯源链，不需要理解你的内部实现；Qualified 形式的限定关系还能给「关系本身」挂角色与时间（例如「Alice 以评审主席的身份参与」）；Bundle 机制甚至支持「关于溯源的溯源」（这条谱系记录是谁在何时声称的）。

边界：PROV-O 只保证「谱系可被陈述」，不保证「陈述为真」——垃圾进、垃圾出在溯源世界依然成立；它描述的是结构，记录的真实性取决于上游的事件日志纪律。此外，完整的限定关系表达会让三元组数量膨胀数倍，工程上要在「表达精度」与「图体积」之间做取舍。

02

OWL：本体语言

Web Ontology Language · 2004, OWL 2 in 2009 / 2012

它是什么。OWL 建在 RDF 的地基上。RDF 把一切知识说成「主语—谓语—宾语」三元组，并用全局 IRI 给每个概念唯一命名——数据第一次有了跨系统的统一拼写；RDFS 给出 class、subClassOf、domain、range 的雏形词汇。OWL 在此基础上，用描述逻辑（Description Logic）把「一个词在业务里到底是什么意思」写成机器可推理的公理。

标准地位
W3C Recommendation；OWL 初版 2004，OWL 2 为 2009 / 2012 第二版
逻辑底座
描述逻辑（SROIQ），一阶逻辑的可判定子集
世界假设
开放世界（OWA）+ 非唯一名假设
代表推理机
HermiT · Pellet · ELK · FaCT++
Semantica 角色
从图谱自动生成 OWL 本体与 SKOS 词表，实体语义显式化

Core四件表达工具

  • 类表达式：intersectionOf / unionOf / complementOf——「关键工作负载 = 工作负载 ∩ 部署在生产环境 ∩ RTO 小于 1 小时」。
  • 属性特征：TransitiveProperty（依赖关系可传递）、SymmetricProperty（互联）、FunctionalProperty（一个负载只有一个主负责人）、inverseOf（「依赖」与「被依赖」互逆）。
  • 限制：someValuesFrom（至少有一个取值来自某类）、allValuesFrom（所有取值都来自某类）、hasValue、基数约束。
  • 公理：equivalentClass（两个类外延相同）、disjointWith（互斥，如「生产环境」与「测试环境」）、sameAs（跨系统实体对齐的钥匙）。
心智
钥匙
开放世界假设（OWA）：数据库里「查无此记录 = 不存在」；OWL 里「没有断言 = 未知」。缺一个字段在数据库里是错误，在 OWL 里只是「不知道」——所以 OWL 永远不会替你把关数据质量，那是 SHACL 的岗位（见 03）。理解 OWA，是理解 OWL 一切行为的钥匙。

Example最小例子：给「关键工作负载」下可推理的定义

Turtle · OWL 2 
@prefix owl: <http://www.w3.org/2002/07/owl#> .
@prefix msp: <http://msp.example.com/onto#> .

msp:dependsOn  a owl:TransitiveProperty .          # 依赖可传递：A→B→C 则 A→C

msp:CriticalWorkload  a owl:Class ;
    owl:equivalentClass [
        a owl:Class ;
        owl:intersectionOf (
            msp:Workload
            [ a owl:Restriction ; owl:onProperty msp:deployedIn ;
              owl:hasValue msp:Production ]
            [ a owl:Restriction ; owl:onProperty msp:rtoHours ;
              owl:someValuesFrom [ a rdfs:Datatype ;
                owl:onDatatype xsd:decimal ;
                owl:withRestrictions ( [ xsd:maxExclusive 1 ] ) ] ]
        )
    ] .
# 推理效果：任何一个部署在 Production 且 RTO<1h 的 Workload，
# 会被推理机自动归类为 CriticalWorkload——无需人工打标签。

Limits长处与边界

长处：语义不再藏在代码注释和文档里，而是成为可被机器执行的公理；实体的自动归类、概念间蕴含关系的自动发现、跨系统同义词对齐（sameAs），都是推理机的副产品。

边界：表达力与可判定性是永恒的 tradeoff——全量 OWL 2 DL 推理在最坏情况下代价极高，所以才有三个 Profile 的官方「降级路线」；本体工程是手艺活，建模失误会让推理机推出荒谬结论；且 OWL 回答「能推出什么」，不负责「数据合不合格」。

SHACL：形状约束语言

Shapes Constraint Language · W3C Recommendation 2017

它是什么。如果 OWL 是「立法者」——定义世界的语义，SHACL 就是「质检员」——按「形状」（Shape）验收数据。它是 W3C 2017 年的正式标准，干一件 OWL 刻意不干的事：在封闭世界的意义上检查数据合不合格，不合格就拦在图谱之外，并产出一份结构化的校验报告。

标准地位
W3C Recommendation，2017-07-20
核心概念
Shape 形状 · Target 目标 · Constraint 约束 · Validation Report 校验报告
严重级别
Violation（违规）· Warning（警告）· Info（提示）
代表实现
pySHACL · Apache Jena SHACL · TopBraid
Semantica 角色
SHACL Studio 可视化编辑 + 写入前校验 + 冲突检测的规则闸门

Core四步工作法

  1. 定义形状（NodeShape / PropertyShape）：某类节点「应该长什么样」。
  2. 选定目标（targetClass / targetNode / targetSubjectsOf）：这份形状适用于哪些节点。
  3. 施加约束：minCount / maxCount（必填与上限）、datatype（类型）、pattern（正则）、in（枚举）、nodeKind（IRI 还是字面量）、hasValue，以及 not / and / or / xone 逻辑组合。
  4. 产出报告：校验结果本身也是 RDF——是否 conforms、每条违规的严重级、位置与说明，可直接进流水线做门禁。

Example最小例子：工作负载入库前的验收形状

Turtle · SHACL 
@prefix sh:  <http://www.w3.org/ns/shacl#> .
@prefix msp: <http://msp.example.com/onto#> .

msp:WorkloadShape  a sh:NodeShape ;
    sh:targetClass msp:Workload ;

    sh:property [
        sh:path msp:hasOwner ;          # 必须有负责人，且恰好一个
        sh:minCount 1 ; sh:maxCount 1 ;
        sh:nodeKind sh:IRI ;
        sh:severity sh:Violation        # 缺负责人 = 违规，拒收
    ] ;
    sh:property [
        sh:path msp:complianceLevel ;
        sh:in ( "L1" "L2" "L3" ) ;      # 合规等级枚举
        sh:severity sh:Violation
    ] ;
    sh:property [
        sh:path msp:costAnomalyScore ;
        sh:maxCount 1 ;
        sh:severity sh:Warning          # 缺失只警告，不拦
    ] .

确定性推理四件套

Forward Chaining · Rete · Datalog · SPARQL

共同的承诺。这四件套的共同点：同样的输入永远得到同样的输出，且每一步推理都可以展示给人类看。这与 LLM 的概率推理是根本性的分野——没有温度参数，没有幻觉空间，推理路径就是审计证据。Semantica 把自己包装成「确定性基础设施」，底气正来自这里。

4.1前向链：事实一变，规则点火

产生式规则（Production Rule）的形式是 IF 条件 THEN 动作。前向链是数据驱动的推理：引擎不断执行「匹配（match）→ 冲突消解（resolve）→ 执行（act）」循环——每条新事实进来，所有前提被满足的规则被点燃，动作产生新事实，新事实再去点燃别的规则，直到不动点。它的镜像后向链（Prolog 的方式）是目标驱动：为了证明结论，反查需要哪些前提。前向链适合监控告警、合规闸门、策略执行——「只要图里出现 X，就立刻做 Y」。代表系统：OPS5、CLIPS、Drools。

4.2Rete：让万条规则仍然够快的算法

前向链的朴素实现有个致命伤：每个周期都要做「每条规则 × 每条事实」的笛卡尔积匹配。1982 年，Charles Forgy 在 CMU 的博士研究中给出 Rete 算法（拉丁语「网」）：把所有规则的条件编译成一张有向判别网络——α 网络做单条件测试并用 α 记忆缓存命中，β 网络做跨事实连接并用 β 记忆缓存中间结果；新事实只需沿网络增量传播，不再全量重算。本质是用内存换时间。代价也由此而来：内存随事实数膨胀，且对递归规则不友好（那是 Datalog 的主场）。Drools、CLIPS、Soar 的内核都是 Rete 或其变体。

4.3Datalog：递归闭包的天选工具

Datalog 是 1970 年代数据库理论对 Prolog 的「安全化」改造：禁止函数符号、要求分层否定，换来一个黄金性质——任何查询保证终止。它区分 EDB（外延事实库，已知的边）与 IDB（内涵规则库，可推的边），用自底向上的半朴素求值（semi-naïve evaluation）迭代到不动点。它的杀手场景是递归闭包：传递依赖、血缘可达、影响面分析——「这次变更最终会波及哪些系统」一条规则就能算完：

Datalog · 血缘可达 
# EDB：已知的直接依赖边
edge(order_svc, payment_db).
edge(payment_db, ledger_db).

# IDB：可达性规则（递归）
reachable(X, Y) :- edge(X, Y).
reachable(X, Z) :- edge(X, Y), reachable(Y, Z).

# 查询：order_svc 变更会影响谁？→ payment_db, ledger_db
?- reachable(order_svc, Who).

它并未老死：Soufflé 把它编译成高性能 C++，RDFox 以它为推理内核，GitHub 的 CodeQL 本质就是「用 Datalog 查代码」——这是学术血统在工业界最成功的潜伏之一。

4.4SPARQL：RDF 世界的 SQL

SPARQL 是 W3C 2008 年（1.0）与 2013 年（1.1）标准化的 RDF 查询语言。四种查询形式：SELECT（取表）、ASK（问真假）、CONSTRUCT（造新图）、DESCRIBE（取描述）；图模式匹配配合 OPTIONAL / FILTER / UNION；1.1 引入属性路径（msp:dependsOn+ 表示一跳以上传递）与联邦查询（SERVICE 关键字跨端点查询）。严格说它是查询语言而非推理机——但 CONSTRUCT 可以把推理结果物化回图里，entailment regime 则允许查询直接在推理闭包上进行，是查询与推理之间的桥。

SPARQL · 三跳内的决策先例

WHERE {
  msp:decision_042 (msp:follows|msp:references){1,3} ?precedent .  # 1~3 跳属性路径
  ?precedent msp:outcome ?outcome .

一句话
读法
构建 Agent 把客户的业务变成「名词」，MSP Agent 在这些名词上执行「动词」；动词留下的痕迹（PROV-O 决策谱系）回流为新的先例，反哺下一次建模。这正是主报告里「迁移是建模，运维是动作」的图形化——两个阶段不再是两张皮，而是同一套本体上的两个时态。
02

八条流向逐一注解

Annotated Flows · Hover to Highlight

架构图上的每个编号对应下面一张卡片。前四条是「输入侧」（知识从哪里来），后四条是「输出与闭环侧」（系统往哪里去、如何演化）。

①
访谈 · 对齐 · 评审

业务专家不直接碰本体工具，而是与构建 Agent 对话：Agent 把访谈纪要转成候选概念，专家在评审界面上逐条「签字」。对齐不是开会，是在本体草案上留痕的确认。

②
元数据勘察

CMDB、ERP 表结构、历史工单、Wiki 文档批量摄入，NER + 模式识别生成候选对象类型；人工只处理低置信度的边角——勘察从「周」压缩到「天」。

③
本体发布 · Ontology as Code

本体即 Git 仓库：草案 = 分支，评审 = PR review，发布 = merge 主干。每次变更可 diff、可追溯、可回滚——本体治理复用软件工程的全套纪律。

④
感知摄入

AWS Config / Azure Resource Graph / 阿里云 Config + 账单 + 监控，持续映射为本体实体。云资产天然 API 化，这是 MSP 场景相比传统行业的本体红利——不用部署采集 agent。

⑤
MCP 读写

MSP Agent 通过 MCP Server 查询实体、关系与可用动作类型，每次访问经 OpenFGA 逐条裁决——Agent 能看到什么、能提议什么，由权限层而不是提示词决定。

⑥
动作执行与写回

动作类型实例化为 Temporal 工作流：L1 走审批，L2 策略内自动；所有写回幂等、可重试、可回滚，出口是云平台 API 或 ITSM 工单。动作必须穿过「动能元素」，不允许绕行。

⑦
决策留痕

每个决策调用 record_decision(category, scenario, reasoning, outcome, confidence)，以 PROV-O 落入谱系库，可导出 Turtle / JSON-LD 直交客户审计或监管。

⑧
先例回流 · 本体演化

运行期沉淀的决策结果、故障模式与成本基线，按季度回流为构建 Agent 的输入：新增对象类型、修订关系、调整动作自治级别。闭环让本体「越用越准」，而不是交付即折旧。

04

动作自治等级 L0–L2

Graduated Autonomy for Actions

MSP 场景的核心信任机制：自治不是开关，是阶梯。每个动作类型独立定级，以 PROV-O 留痕的历史成功率作为晋级依据——先证明可靠，再放开手脚。

自治等级 · 每级的前提与出口
等级定义典型动作晋级前提
L0只读 / 建议巡检报告、成本分析、依赖影响面查询、变更风险预估——只出结论，不动资源默认起点，无门槛
L1审批后执行扩容、快照、升降配、切换——Agent 生成完整执行计划，值班工程师一键批准后由 Temporal 执行L0 期建议被采纳率 ≥ 约定阈值
L2条件自治策略边界内自动执行：夜间缩容、标签治理、过期快照清理；越界自动降级为 L1 走审批L1 期成功率 + 回滚演练通过

为什么不能跳级：第九章裁决里说过，Palantir 的 AI 自主权是「默认分阶段」的——这不是保守，是把信任当作需要用数据赢得的资产。MSP 场景同理：客户在第一个月绝不会接受 Agent 直接动生产资源，但会接受一份高质量的巡检建议。L0 建立口碑，L1 建立记录，L2 水到渠成。自治等级的晋升表，本身就是一份可卖给客户的「信任路线图」。
